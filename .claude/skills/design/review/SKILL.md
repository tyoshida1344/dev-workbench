# 設計のレビュー

読む時: `design/SKILL.md` の振り分け(設計をレビューする)と、フェーズの表の「設計のレビュー」の行から来る。

`<作業フォルダ>`(`design/SKILL.md` の「作業フォルダと読むもの」)の成果物を読み、実装に入ってから困る点を、先に見つける。**指摘だけを返し、成果物は直さない**(直すかどうかは、ユーザーに確かめる)。
レビューの共通の進め方・重要度・出力の形は `review/SKILL.md`。

## 手順
1. `<作業フォルダ>` の成果物を読む(`spec.md`、`impl.md`、`impl/`、`acceptance.md`、`test.md`、`test/`、`spec/`、`search/`、`images/`。途中のフェーズなら、あるものだけ)
2. 次の3つの観点で、指摘を洗い出す
3. 指摘を、重要度の高い順に並べて返す

## 観点

### 1. 詰め漏れ
- 詰め漏れの観点([completeness.md](/.claude/skills/design/reference/viewpoints/completeness.md))の進め方と観点で確かめる
- 読んだ成果物のフェーズについて、各フェーズの完了条件(`design/reference/NN-*.md` の「完了条件」)を満たしているか

### 2. 成果物どうしの食い違い
- `spec.md` の決まったことに、`acceptance.md` の条件が対応しているか(漏れ)。`acceptance.md` の条件に、`spec.md` の根拠があるか(`spec.md` に無い条件が混じっていないか)
- `acceptance.md` の「`spec.md` の節」が、正しい節を指しているか
- `spec.md` の各項目が、`impl.md` の実装方針(データ構造・機能・データの流れ)の、どれかの変更に結びついているか(漏れ)。実装方針に、`spec.md` に無い動きが混じっていないか
- `acceptance.md` のすべての AC が `test.md` の計画に載り、層・手段・担当が決まっているか。計画に、AC に無いテストが混じっていないか
- `spec.md` と `impl.md` の中身が矛盾していないか
- `spec.md` と変更仕様(`spec/`)、`search/` の中身が矛盾していないか。取り消した決定が本文に残っていないか(下書きに残す時は、打ち消し線などで、取り消したことが分かるか)
- 仮・未決が、`QA.md` と対応しているか

### 3. 書き方の決まり
`design/SKILL.md` の共通の決まりの各項目に照らす。要点は次のとおり。
- 確定した文書(`spec.md`・`impl.md`・`test.md`・`acceptance.md`)に、未確認のこと・根拠の `path:line`・ほかの成果物への参照が混じっていないか。`spec.md`・`acceptance.md`・`test.md` に、コードの識別子・実装の方法が書かれていないか
- 「できないこと」「正常系以外の動き」が書いてあるか。仮に「仮」と書いてあるか。記号だけで指さず、同じものを同じ名前で書いているか
- ビューアで読めるか(`docs/design-folder.md`)。ひな形の説明(`> 書き方:`)が残っていないか。Markdown が崩れていないか(閉じていないコードブロック、表の列のずれ)

## 出力

`review/SKILL.md` の出力の形で返す。観点は **詰め漏れ / 成果物どうしの食い違い / 書き方の決まり**。場所は `ファイル の「節」`。

- 指摘は、「何が、どこで、困るか」を、具体例つきで書く
- 指摘のうち、決める人の判断が要るものは、`QA.md` に起こす形(質問・選択肢・推奨案)で提案する
