# ライト版(段1〜3)

読む時: `design/SKILL.md` の振り分け(ライト版で進める)から来る。

小さい変更のために、フェーズ1〜10を3つの段にまとめて進める。どの版で進めるかの目安は `design/SKILL.md` の「版の選び方」。作業フォルダ・読むもの・全フェーズ共通の決まり・ひな形は `design/SKILL.md` のとおりで、フル版と違うのは、この手順に書いたことだけ。

## フル版と違うこと

- **下書きを作らない。** `search/`・`spec/`・`impl/`・`test/` は作らず、決まったことを直下の文書に直接書く。調べた根拠(`repo名:path:line`)とコードの検索の結果は、文書に書かず、段の報告でユーザーに示す
- **フェーズの手順は、決まりと完了条件だけを当てる。** 段に入る時、まとめたフェーズの手順(`design/reference/NN-*.md`)を読み、「決まり」と「完了条件」を当てる。下書きのファイルを作る手順と、下書きに関わる完了条件(ファイル名・`path:line` を下書きに残す、など)は除く
- **未決は、段の終わりにまとめて聞く。** 共通の決まりの「1つずつ聞く」の代わりに、段の中で出た未決を `QA.md`(書式はフェーズ6)に起こし、段の終わりに `AskUserQuestion` でまとめて聞く。答えを文書に反映してから、`QA.md` の項目を消す
- **確かめは3回。** 始める前(版とライト版で進めること)・段2の終わり・段3の終わり。段1の終わりでは確かめず、段2へ進む
- **設計のレビューは1回。** 段3を書き終えた時に、設計のレビュー(`design/review/`)を当てる

## 段1: 読む・要件・影響範囲(フェーズ1〜3)

成果物: `index.md`

1. イシューを、フェーズ1の読み方で読む
2. `index.md` に、フェーズ1の中身(イシューの概要とリンク、決まったこと / 未決)に加えて、次を書く
   - 見出しのすぐ下に `進め方: ライト版` の1行(版を見分けるため)
   - 「要件」の節: 何を・誰が・なぜ。イシューの事実と自分の解釈を分ける。末尾に「適用する観点: …」の1行(フェーズ2の判定)
   - 「影響範囲」の節: 影響しうる画面・機能・データと、その理由。似た機能(無ければ「類似なし(探した範囲)」)。調べたリポジトリの名前(フェーズ3)
3. フェーズ2で関係すると判定した観点の読み物と、既存データへの影響([viewpoints/existing-data.md](/.claude/skills/design/reference/viewpoints/existing-data.md))を読む

## 段2: 今の動きと変更後(フェーズ4・5・7)

成果物: `spec.md`(ひな形 `design/templates/spec.md`)

1. 今の動きを、コードを読んで確かめる。表の軸(結果を変える条件・既存データの実際にありうる状態)はフェーズ4の「表の作り方」「表の軸」のとおり。確かめられないことは推し量らず、`QA.md` に起こす
2. `spec.md` の「1.2 主な動き」を、ひな形の書き方(ライト版の時)で書く。できないこと・正常系以外の動きを先に書く
3. ほかの節は、ひな形のとおりに書く(フェーズ7の決まり)
4. 未決をまとめて聞き、反映する。仮が残る間は段3へ進まない
5. 設計のビューアの URL を渡し、**段3へ進んでよいか確かめる**(確かめ②)

## 段3: 受け入れ基準・実装の方針・テストの計画(フェーズ8〜10)

成果物: `acceptance.md`・`impl.md`・`test.md`(3つとも作る。ひな形は `design/templates/`)

1. `acceptance.md` を、フェーズ8の手順とひな形で書く
2. `impl.md` を、フェーズ9の決まりとひな形で書く。既存機能への影響(1.4)は、コードを検索して洗い出し、検索した言葉と件数を報告に添える
3. `test.md` を、フェーズ10の決まりとひな形で書く。`acceptance.md` のすべての AC を、1 の表に番号で載せる
4. `check-cases.mjs <作業フォルダ>`(`<dev-workbench>/.claude/skills/test-cases/scripts/check-cases.mjs`)を動かし、`acceptance.md`・`test.md` の表の形の誤りが出ないことを確かめる(`cases/` はまだ無くてよい)
5. 設計のレビュー(`design/review/`)を当て、指摘を直す
6. 設計のビューアの URL を渡し、**設計ができあがったことを確かめる**(確かめ③)。`issue-handler` から来た時は、その手順に戻る

テストケースは、`test-cases` の手順を通さず、`acceptance.md` から作る(`test-cases/SKILL.md` の「ライト版の設計から作る」)。

## フル版に移る

ライト版の途中でフル版の目安(`design/SKILL.md` の「版の選び方」)に当たると分かったら、根拠を伝えてユーザーに確かめ、それまでに書いたものを引き継いでフル版に移る。

1. `index.md` の「要件」「影響範囲」の節を、`search/01_requirements.md`・`search/02_related.md` に移す。`index.md` からは、その2つの節と `進め方: ライト版` の行を消す
2. `spec.md` の「今」の列で書いた動きは、フェーズ4の形(根拠つきの表)で `search/` に書き直す
3. `design/SKILL.md` の「進め方」の2〜3で、どのフェーズから進めるかを推し量り直し、ユーザーに確かめる
