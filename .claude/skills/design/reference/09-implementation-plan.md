# フェーズ9: 実装の方針・計画

作業フォルダ(`<作業フォルダ>`)の場所と共通の決まりは [SKILL.md](/.claude/skills/design/SKILL.md)にある。

以下の「1.1」などの番号は、ひな形 [templates/impl.md](/.claude/skills/design/templates/impl.md) の節の番号。何をどの節に書くかは、ひな形の `> 書き方:` に従う。

## 前提
- `spec.md` に仮が無く、`acceptance.md` がある(無ければ、ユーザーに伝える)

## 手順
1. 最終仕様を実現するために**手を加える対象**を、関係するリポジトリ(画面・API・インフラなど)のコードを読んで洗い出す(読むだけ)
2. ひな形の節(1.1 データ構造の変更 〜 2. 実装計画)ごとに、変更に関係するものだけ、下書きを `impl/NN_<slug>.md` に書く。**調べたこと・コードの根拠・検討の過程は、下書きに書く**
3. 既存機能への影響(1.4)は、**コードを検索して洗い出す**
   - 変える列・制約・モデルは、名前で検索して、参照している箇所をすべて挙げる(API の入出力の定義・ルート・管理画面・管理コマンド・バッチ・ほかの機能・テスト)。検索の結果を `impl/` に残し、1件ずつ「変更 / 変更なし(理由)」を決める
   - 制約・型・既定を変える時は、それに頼っている仕組みの動きが変わらないかを確かめる(例: フレームワークが制約から自動で付ける検証、管理画面の一覧、API の入出力の定義が自動で作る項目)
   - 修正対象の入口(1.2)に挙げるファイルは、中身を読んで、変更が要るかを決める。名前から推し量って挙げない
   - 本文・設定を順に探すもの(個別 → 全体共通 → 初期値など)は、各段を使うか使わないかを、はっきり書く
4. 画面の文言(1.5)で「既存と同じ」と書くものは、既存の画面・テンプレートを実際に読んで一致を確かめ、読んだ場所を `impl/` に残す(既存の文言を推し量って書かない)
5. 下書きから、**決まったことだけ**を、ひな形を埋めて `impl.md` にまとめる

## 成果物
- `<作業フォルダ>/impl/NN_<slug>.md`(話題ごとに1ファイル)
- `<作業フォルダ>/impl.md`(決まったことだけをまとめた、実装の方針・計画)

## 決まり
- 最終仕様に無い動きを足さない。足したくなったら QA.md に起こし、`spec.md` を直してから方針に書く
- 今の仕組み(似た機能の作り)に揃える。揃えない時は理由を書く

## 完了条件
- [ ] データ構造の変更、手を加える機能(入口つき)、データの流れ、既存機能への影響、実装計画(作業の分け方)が書いてある(変更に関係しないものは「該当なし(理由)」)
- [ ] テーブル間の関係(どちらから見て1対いくつか、もう一方から取る列)が読み取れる
- [ ] 新しいテーブルのすべての列(型・NULL・既定・制約)と、各列の理由が読み取れる。既存のテーブルの追加・変更と、その理由が読み取れる
- [ ] 参照(外部キー)の先が、消された・無効・不正の時の動きが書いてある
- [ ] 既存機能への影響が、コードの検索で洗い出してある(変更 / 変更なし)。変える列・制約・モデルの参照箇所が、すべて挙がっている。順に探すものは、各段を使うかが書いてある
- [ ] 「既存と同じ」と書いた画面の文言・作りが、既存を読んで確かめてある(根拠は `impl/`)
- [ ] 手を加える機能のすべてに、入口(ファイルのパスと名前)がある。最終仕様のすべての項目が、どれかの変更に結びついている(漏れが無い)
- [ ] データの流れに、失敗した時がある
- [ ] 画面の文言が決まっている(決まっていないものは QA.md にある)
- [ ] 作業の分け方に、順序の矛盾が無い
- [ ] 実装者に任せること(「実装で決める」)が、決めたことと区別できる
- [ ] 未確認のこと・根拠が `impl.md` に混じっていない(未確認は QA.md に起こしてある。根拠は `impl/`)
- [ ] 設計のレビュー(`design/review/`) で確かめた
- [ ] `impl.md` にまとめた(ひな形の説明 `> 書き方:` が残っていない)
