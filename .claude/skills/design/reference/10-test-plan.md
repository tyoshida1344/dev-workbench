# フェーズ10: テストの方針・計画

作業フォルダ(`<作業フォルダ>`)の場所と共通の決まりは [SKILL.md](/.claude/skills/design/SKILL.md)にある。

以下の「1」「2」などの番号は、ひな形 [templates/test.md](/.claude/skills/design/templates/test.md) の節の番号。何をどの節に書くかは、ひな形の `> 書き方:` に従う。

## 前提
- `acceptance.md` と、`impl.md` の実装方針がある(無ければ、ユーザーに伝える)

## 手順
1. ひな形の節ごとに、検討を下書きとして `test/NN_<slug>.md` に書く
2. 受け入れ基準(AC)を1つずつ、層・手段(自動 / 手動)・担当・データの準備に割り当てる(1)。AC の中身は書き直さず、番号で指す。「既存機能への影響」の AC は、今ある自動のテストで足りるか、新しく要るかを決め、手段に書く
3. 特殊な環境の準備(2)を洗い出す。外に出るもの(メール、チャットへの通知、外部の API、ファイルの出力)は、出先が本番と同じ(宛先の上書きが無い、決まった BCC がある、通知先がすべての環境で同じなど)かを、コードで確かめる
4. **性能を確かめる AC があれば、計る前に指標(4)を立てて、ユーザーと合わせる**(下の「性能の指標」)
5. 実機でしか確かめられず、設計の判断に影響するものは、`test.md` に書かず、QA.md に起こす(推奨案つき)。判断に影響しない確認は、手動のテストとして、AC の表(1)に載せる
6. 下書きから、決まったことだけを、ひな形を埋めて `test.md` にまとめる

## 性能の指標
性能を確かめる AC がある時に、ひな形の 4 で決めること。
- 指標: 時間を左右する軸(例: 行数・列数・追加か変更か)と、その組み合わせ。目安の時間と、その根拠(例: 打ち切りの 900秒から、通信や実行ごとのばらつきの余裕として 120秒を引いた 780秒)
- 比べ方: 修正の前と後で、同じファイル・同じ環境で計る組み合わせ。修正前が打ち切られる見込みなら、それも結果として扱う
- 実際の運用を想定した限界の動き: 本番の最大の規模(人数・項目数など)と、軸を両端まで振った組み合わせ(例: 多い行×少ない列、少ない行×多い列、多い行×多い列)。どこまで通るかの目安を出すなら、計る点と式(切片が何を表すか)を先に決める
- 載せ方: PR・イシューに載せる表の形(行・列の見出し)を先に決め、計った値をそのまま埋められるようにする

## 成果物
- `<作業フォルダ>/test/NN_<slug>.md`(話題ごとに1ファイル)
- `<作業フォルダ>/test.md`(テストの方針・計画)

テストケース(手動のテストの1件ずつの手順と期待する結果)は、`test.md` をもとに `test-cases` で作る(置き場は `<作業フォルダ>/cases/`)。

## 決まり
- 受け入れ基準に無いテストを足さない。足したくなったら QA.md に起こし、`acceptance.md`・`spec.md` を直してから計画に書く
- 自動で確かめるものと、手動で確かめるものを、理由つきで分ける

## 完了条件
- [ ] すべての AC が、表(1)で、層・手段・担当・データの準備に割り当てられている。表はひな形のとおりに書いてある(`check-cases.mjs <作業フォルダ>` が、表に無い AC を出す。コマンドは `test-cases/reference/format.md` の「正本と証跡を作る」)
- [ ] 「既存機能への影響」の AC の確かめ方が決まっている
- [ ] 特殊な環境の準備(外に出るもの、日付、検証用データ)が、方法・時期・確かめ方・戻し方つきで書いてある(あてはまらなければ節ごと消してある)
- [ ] 遮断を外してよい操作が、限って書き出されている
- [ ] AC が、動かせない日付・外に出る動きに関わる時、表(1)に、使う準備が書いてある
- [ ] テストデータ(既存データの実際にありうる状態の作り方)が書いてある
- [ ] 性能の AC がある時、指標(軸・目安とその根拠)、修正前との比べ方、実際の運用を想定した限界の動きの組み合わせと載せ方が書いてあり、ユーザーと合わせてある(性能の AC が無ければ節ごと消してある)
- [ ] 実機でしか確かめられないものに、時期と担当がある(設計の判断に影響するものは QA.md)
- [ ] 未確認のことが `test.md` に混じっていない(QA.md に起こしてある)
- [ ] 自動と手動の分け方に理由がある
- [ ] 設計のレビュー(`design/review/`) で確かめた
- [ ] `test.md` にまとめた(ひな形の説明 `> 書き方:` が残っていない)
