# フェーズ8: 受け入れ基準の作成

作業フォルダ(`<作業フォルダ>`)の場所と共通の決まりは [SKILL.md](/.claude/skills/design/SKILL.md)にある。

## 前提
- `spec.md` に仮確定が無く、`QA.md` が無い(または空)こと(残っているなら作らない。ユーザーに伝える)

## 手順
1. `spec.md` の確定したことを1つずつ、確かめられる条件に変える
2. 「できないこと」「異常系」を先に書く([SKILL.md](/.claude/skills/design/SKILL.md)の共通の決まり)
3. 条件は「前提 → 操作 → 期待する結果」で書く
4. 変更後の表(フェーズ5)の変わるセルは、すべて条件に対応させる
5. 変わらないはずの動き(すでに確定したデータ・既存データの実際にありうる状態ごとの結果)も、変わらないことを条件に入れる

## 成果物
`<作業フォルダ>/acceptance.md`。ひな形 [templates/acceptance.md](/.claude/skills/design/templates/acceptance.md) を埋める(3つの見出しごとの AC の表)。

- 変わらないはずの動き(手順5)は「既存機能への影響」に、要件に無く設計で決めた動きは「設計で追加した仕様」に書く
- フェーズ2 で適用すると判定した観点(権限・データ移行・API と画面の責務・UI など)は、それぞれ条件を持つ。UI は画面の状態(空・エラー・読み込み中・権限なし)も含める

## 決まり
- 期待する結果は、実装を見なくても正しいか判定できる書き方にする(「適切に表示される」のようなあいまいな言い方は書かない)
- `spec.md` に無い動きを条件に足さない。足したくなったら QA.md に起こし、`spec.md` を直してからにする
- 前提・操作・期待する結果は、画面・メール・データで確かめられることで書く。コードの識別子(クラス名・カラム名など)は書かない([SKILL.md](/.claude/skills/design/SKILL.md)の「文書ごとに、コードの内容をどこまで書くか」)

## 完了条件
- [ ] `spec.md` の確定したことすべてに、対応する条件がある
- [ ] 各見出しの中で、できないこと・異常系の条件が先にある
- [ ] 変わらないことの条件が「既存機能への影響」にある
- [ ] ひな形の見出しと列のまま書いてある(`check-cases.mjs <作業フォルダ>` を動かすと、表の形の誤りが出る。コマンドは `test-cases/reference/format.md` の「正本と証跡を作る」)
- [ ] すべての条件の期待する結果が、判定できる書き方になっている
- [ ] `spec.md` に無い条件が混じっていない
- [ ] `spec.md` の、名前・置き場所・既定値・リリース直後の状態・止め方・手で動かす方法・実行の記録の記述に、対応する条件がある
- [ ] コードの識別子が書かれていない
