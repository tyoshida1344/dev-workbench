# イシューへのコメントと PR の本文の型

`issue-handler/SKILL.md` のステップ5とステップ11で使う。中身はイシューに合わせて過不足なく書き、決まったことの無い節は省く。

## 確定仕様のコメント(ステップ5)

```sh
gh issue comment <番号> --body "$(cat <<'EOF'
## 確定仕様

### 概要
<1〜2行で、何を作る/直すか>

### 詳しい仕様
- <確定した仕様を箇条書き>

### 確認した不明点と決定
- Q: <聞いたこと> → A: <決まったこと>

### 実装の方針
- <変えるファイル / 足すもの / 使う既存の型>

### 既存機能への影響
- <変える共通の処理と、それを使う画面・機能。変わってはいけないこと>
EOF
)"
```

- 設計の流れで進めた時は、「詳しい仕様」を `spec.md` の要約にし、設計ビューアのURLを添える(仕様の本文はコメントに写さない)
- 「詳しい仕様」「確認した不明点と決定」「既存機能への影響」は、ステップ10で受け入れ項目の出どころになる

## PR の本文(ステップ11)

リポジトリに `.github/PULL_REQUEST_TEMPLATE.md` があれば、そちらの節を埋める。無ければ次の形にする。

```sh
git push -u origin <ブランチ>
gh pr create --title "prefix: #<番号> 説明" --base <base> --body "$(cat <<'EOF'
## Summary
- <変更の中身を、利用者・レビュアーの目で箇条書き>

## Test plan
### 受け入れ
- [x] <★ の項目の id> <項目の文>

ほか M 項目(✓a / !b / ✕c)はビューアで

## Evidence
受入確認: 全 N 項目(✓x / !y / ✕z)
<エビデンスビューアのURL>

Closes #<番号>
EOF
)"
```

- **Test plan は、受け入れ項目の一覧(正本)を写したもの。** 順番も文言もそのまま写し、**エビデンスで ok だった項目にだけ**チェックを付ける(`partial` / `ng` と、エビデンスの無い項目には付けない)
  - テストケース(`test-cases`)で作った時: 見出し「受け入れ」の下に、★(`review: true`)の項目だけを、正本(`manifest.json`)の順に `<id> <項目の文>` で1行ずつ。その下に、★ の無い項目の数と結果を「ほか M 項目(✓a / !b / ✕c)はビューアで」の1行で書く(M が 0 なら書かない。Evidence の「全 N 項目」とは別の数)
  - 受入確認のまとめ(`test-run/evidence/`)で作った時(★ が無い): 見出しを3つの見方(`### 要件`・`### 既存機能への影響`・`### 設計で追加した仕様`)にし、`00-cases.md` の節と項目をそのまま全部。流れの節(`<見方>: <流れの名前>`)の項目は、その見方の見出しの下に、節の順のまま並べる。1つのチェックボックスが1つの項目
  - 正常系・異常系・境界と流れは、Test plan には出さない
- Evidence: ビューアのURLと件数。`partial` / `ng` があれば、番号と理由を1行ずつ。設計の流れで進めた時は、設計ビューアのURLも添える
- 直しきれなかったセルフレビューの指摘があれば、節を足して書く
- 複数のイシューをまとめた時は、タイトルを `prefix: #33 #34 ...` にし、`Closes #<番号>` をイシューごとに1行ずつ書く
