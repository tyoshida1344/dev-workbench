# イシュー対応

GitHub イシューを「ブランチ準備 → 読む → 不明点を潰す → 仕様を確定して記録する → 実装する → 検証する → セルフレビュー → コミット → エビデンス → PR → 完了報告」の流れで対応する。

このスキルの価値は、**実装を急がず、イシューに潜む曖昧さを実装の前にすべて解消すること**にある。
イシューの多くは「やりたいこと」を口語で書いただけで、判断の要る仕様がいくつも決まらないまま残っている。
そこを勝手に決めて作ると手戻りになるので、必ずユーザーに確認してから手を動かす。

## 入力

イシュー番号を受け取る。引数(`issue-handler 8`)でも、文中(「#8 を対応して」)でもよい。
番号が読み取れない時は、どのイシューを対応するか先にユーザーに確認する。

- **リポジトリ**: 既定は cwd のリポジトリ。リモートが `origin` 以外(`upstream` など)で `gh` がリポジトリを解決できない時、別のリポジトリのイシューの時は、`gh` のコマンドに `--repo <owner>/<name>` を付ける
- **複数のイシュー**: ステップ4の確認に、**ブランチと PR の分け方**(イシューごとに分けるか、1つのブランチ・1つの PR にまとめるか)も含めて聞く。まとめる時は、ブランチ名を `issues/<番号>-<番号>-...`、コミットのタイトルを `prefix: #33 #34 ...` にする(PR は `reference/templates.md`)。仕様のコメント(ステップ5)は、まとめる時もイシューごとに投稿する
- 以下、作業のブランチの名前を `<ブランチ>` と書く(1つのイシューなら `issues/<番号>`。プロジェクトに決まりがあればそれに従う)

## 進め方

下の順に進める。**ステップを飛ばさない。** 特にステップ4(不明点の確認)を省いて実装に入らない。

### 1. ブランチ準備

`git status` で今の状態を確かめる。次のどれかに当たる時は、**警告してユーザーに確認**してから進める。

- まだコミットしていない変更(staged / unstaged / untracked)がある
- 土台にするブランチ以外のブランチにいる

作業の土台にするブランチ(`<base>`)を決める。

1. プロジェクトの決まり(CLAUDE.md・`RELEASING.md`・`CONTRIBUTING.md` など)に、土台のブランチの決まり(リリースのブランチ、`develop` など)があれば、それに従う。候補が複数あればユーザーに聞く
2. 決まりが無ければ、リポジトリの既定のブランチ: `gh repo view --json defaultBranchRef --jq .defaultBranchRef.name`

```sh
git fetch origin --quiet
git checkout <base>
git pull origin <base>
git checkout -b <ブランチ>
```

**`<base>` はステップ8(セルフレビューの比べる先)とステップ11(PR の base)でも使う。**

### 2. イシューの取得と理解

本文と既存のコメントを取る。コメントには、過去の議論や後から決まったことが入っていることがあるので必ず読む。

```sh
gh issue view <番号> --comments
```

`--comments` の出力が空になる環境では、JSON で取る。

```sh
gh issue view <番号> --json title,body,comments,labels,state
```

タイトル・本文・コメントから、「何を新しく作るのか / 何を直すのか」「背景・動機」をつかむ。本文やコメントにリンクされたイシュー・PR も読む。
取れない時(番号が無い、など)は、その旨を伝えて番号を確かめる。

### 3. プロジェクトの決まりをつかむ

実装が決まりから外れないよう、先に書き方の手本を読む。

- `CLAUDE.md`(あれば最優先。作り・命名・置き場所・検証の方法が書かれている)、`.claude/rules/`
- `README`、および**同じ種類の既存のファイル**(新しい機能なら、近い既存の機能のソースを1〜2本読み、作りを踏襲する)
- 検証のコマンド(型チェック・ビルド・lint・テスト)が何か

ここでつかんだ型(共通の部品・ファイルの置き場所・登録の作法など)に、実装を合わせる。

### 4. 不明点の洗い出しと確認 ★最重要

イシューの記述を、**実装するなら必ず答えが要る粒度**まで分解し、決まっていない点をすべて挙げる。
曖昧になりやすいのは:

- 機能の範囲(どこまでやる / やらない、任意の要望の優先度)
- 具体的な数値・上限・初期値(「上限を設けたい」→ 何個?)
- 操作・入力の方法(キーボードでの操作の要否、ボタンの有無など)
- 画面での配置・名前・表示する文言、既存の機能との関係
- 狭い幅での見せ方
- 参照されている外の固有名詞(「○○と同じような画面に」→ それは何を指すのか)
- 異常系・境界の扱い(データが空、権限が無い、失敗した時)

不明点を洗い出す時は、あとで受け入れ項目を作る3つの見方(`test-cases/reference/perspectives.md` の「3つの見方」)も意識する。

- **要件**: イシューの各要件について、「何が起きたら満たしたと言えるか」が答えられるか。答えられない要件には、曖昧さが残っている
- **既存機能への影響**: 変えそうな共通の処理(複数の画面・機能が使う関数・CSS・保存のキー)があるか。あれば、影響する範囲と、変わってよいこと・変わってはいけないことを確かめる
- **設計で追加する仕様**: 要件には無いが実装に要る動き(既定値・無効の時・異常系・境界の振る舞いなど)。勝手に決めず、論点として聞く

挙げた不明点は **AskUserQuestion でまとめて出し**、ユーザーの答えですべて解消してから次へ進む。
一問一答で往復を増やすより、関係する論点をまとめて聞く方が、ユーザーの負担が小さい。
本当に解釈の余地が無い点まで確かめる必要は無いが、迷ったら聞く側に倒す。

**「妥当な既定値を思いつく」ことは、確認を省く理由にならない。**
ユーザーはこのスキルを通じて *自分で仕様を決めたい* のであって、もっともらしい既定値で代用されたいわけではない。
仕様を左右する判断(範囲・数値・振る舞い・画面の形など)を勝手に確定すると、動くものができても、意図と違えば作り直しになる。
決めるのはユーザーで、こちらの役割は「決めるべき論点を漏れなく差し出すこと」。
答えがすぐ得られない時も、その論点を勝手に確定して先回りせず、確認待ちであることを示して止まる。

#### 大きなイシューは設計の流れに切り替える

次のどれかに当たる時は、このステップで「`design` の設計の流れ(作業フォルダに要件・影響範囲・今の振る舞い・変更仕様・最終仕様・受け入れ基準を書く)で進めるか」をユーザーに聞く。

- 影響する画面・機能・リポジトリが複数ある
- データの形・保存されたデータ・権限・外とのやりとりが変わる
- 今の振る舞いを調べないと、変更後を決められない
- 決める人がユーザー以外にもいる

設計の流れで進めると決まったら、`design` でフェーズ1から進める。

- **行うフェーズ**: フェーズ8(受け入れ基準 `acceptance.md`)まで行い、仮・未決が0件になったら、このスキルのステップ5に戻る。フェーズ9・10(実装の方針・テストの計画)は、影響する画面・リポジトリが多い時やテストの準備が特殊な時に、行うかをユーザーに聞く
- **聞き方**: 設計の流れの中では、`design/SKILL.md` の聞き方(決める人への質問として、1つずつ詳しく)に従う
- **イシューへのコメント**: ステップ5の1回だけ。設計の側からは別に投稿しない
- **実装中に決めた・変えたこと**: 設計の流れで進めた時は、ステップ6〜8で決めた・変えたことを `design/reference/11-feedback-from-impl.md` の手順で設計の文書に返す

### 5. 仕様の確定とイシューへの記録

ユーザーの答えを反映して最終の仕様をまとめ、**実装に入る前に**イシューへコメントとして残す。
「何を作ると合意したか」の記録になり、後から実装の意図を追えるようにするため。

イシューへのコメントは外に公開される。**本文をユーザーに見せ、了承を得てから投稿する。** 型は [reference/templates.md](reference/templates.md) の「確定仕様のコメント」。

### 6. 実装

**ステップ4の確認が済むまで、ファイルは編集しない。** 実装に着手するのは、ユーザーの答えを得てから。
確定した仕様と、ステップ3でつかんだ決まりに沿って実装する。既存の共通の部品・型を使い、独自の実装を増やさない。
不具合の修正のイシューでも流れは同じ(原因を特定する → 直し方を仕様として確定する → 直す)。

### 7. 検証

完了とみなす前に、プロジェクトの検証の方法で確かめる。

- `CLAUDE.md` に検証のコマンドがあれば、それを使う。無ければ、ステップ3で見つけた型チェック・ビルド・lint・テストを行う。どれも無いプロジェクトでも、構文と明らかな破綻が無いかは確かめる
- エラーが出たら直してから次へ進む
- lint は、既存のファイルに警告が残っていることがある。土台のブランチの同じファイルと比べ、**今回の変更で新たに出た警告だけ**を直す(既存の部分を整えて差分を膨らませない)
- 型やビルドが通っても、画面の振る舞いは分からない。**画面に関わる変更は、開発用のサーバーを起動して実際に動かして確かめる**
  - 狭い幅(375px など)で、横のスクロールが出ないこと・要素の大きさを確かめる
  - 表示の条件がデータ次第の機能は、一時的に値を差し替えて確かめ、**確かめた後に必ず元に戻す**(戻したことを `git diff` で確かめる)

### 8. セルフレビューと修正

実装と検証が終わったら、`review` でセルフレビューし、**指摘を直すところまで**行う(このスキルから呼ぶ時は、直すところまで頼んだことになる)。

1. `review` を、比べる先にステップ1の `<base>` を渡して当てる。どの観点を当てるかは `review/SKILL.md` の「当てるレビュー」のとおり
2. P1・P2 の指摘を直す。P3 は、直すか残すかを決め、残すものは理由を添える
3. 直したら、ステップ7の検証をもう一度行う
4. 直しきれなかった指摘は、完了報告と PR に書く

### 9. コミット

セルフレビューが終わったら、変更をコミットする。エビデンスはこのコミットを対象に撮る。

```sh
git add <変えたファイル>
git commit -m "prefix: #<番号> 説明"
```

- prefix はイシューの中身で決める(`feat` / `fix` / `refactor` / `chore` など)。プロジェクトにコミットメッセージの決まりがあれば、それに従う

### 10. 受入確認のエビデンス(必須)

受入確認のエビデンスを作業フォルダ(`docs/workspace.md`)の `evidence/` に作り、エビデンスビューアの URL を得る。**省略しない。**
画面を持たない変更(文書・内部の整理など)でも、動いた結果を残せるもの(既存の機能が今までどおり動くこと、など)は項目にする。

- 設計の流れでテストの計画(`test.md`)まで作った時は、`test-cases` でテストケースを作り、`test-run` で行う
- それ以外は、受入確認のまとめ(`test-run/evidence/`)の手順で作る。項目の出どころは、イシューの本文、ステップ5の確定仕様のコメント、ステップ6〜8で実装中に決めた細部と、セルフレビューで足した修正。項目の一覧は、ユーザーに確認しない代わりに、その手順の「撮る前の見直し」を自分とサブエージェント(別の目)の両方で必ず行う
- どちらの時も、**受け入れ項目の一覧(`00-cases.md` と `manifest.json`)が正本**で、ステップ11の PR の Test plan はそれを写す
- `manifest.json` の `source` には、リポジトリ・ステップ9のコミット・イシューの URL を書く(PR はまだ無い)
- 撮っている途中で不具合が見つかったら、直してステップ7からやり直し、コミットを足してから、影響する項目を撮り直す
- `partial` / `ng` が残った時は、その理由を完了報告と PR に書く

### 11. PR の作成

PR の作成は外に公開される操作。ユーザーがこのスキルでイシューの対応を頼んだことを、PR を作る了承とみなしてよい。ただし、ステップ4〜10のどこかで、ユーザーが PR の前に見たいと言った時は、それに従う。

本文の型と、Test plan の写し方は [reference/templates.md](reference/templates.md) の「PR の本文」。`--base` にはステップ1の `<base>` を指定する。

### 12. 完了報告

最後に、次を短く報告する。

- 確定した仕様の要約(と、イシューにコメントしたこと)
- 変えたファイルと、何をしたか
- 検証の結果
- セルフレビューの結果(残った指摘があれば)
- エビデンスの結果(件数、撮る前の見直しで足した項目、`partial` / `ng` とその理由)とビューアの URL
- PR の URL

## やらないこと

- ステップ4を飛ばして、曖昧なまま想定で実装すること
- エビデンス(ステップ10)を省いて PR を作ること
- イシューの要望を超えた余計な変更(気づいた改善点は報告に留め、別に相談する)
- ユーザーに見せずに、イシューへコメントを投稿すること
