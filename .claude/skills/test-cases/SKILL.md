# テストケースを作る

dev-workbench の場所(以下 `<dev-workbench>`): `${CLAUDE_SKILL_DIR}/../../..`。中の手順・コマンド・サブエージェントに渡すパスは、ここを絶対パスにして使う(決まりは [docs/workspace.md](/docs/workspace.md) の「dev-workbench の場所」)。

## 振り分け

頼まれたことで、読む手順を選ぶ。

| 頼まれたこと | 読む手順 |
|---|---|
| テストケースを作る・作り直す・観点を洗い出す | このファイル |
| ライト版の設計(作業フォルダの `index.md` に `進め方: ライト版`)から作る | このファイルの「ライト版の設計から作る」 |
| 作ったテストケースをレビューする・漏れを見る | [review/SKILL.md](/.claude/skills/test-cases/review/SKILL.md)(テストケースのレビュー。ケースを作る流れの中では、サブエージェント `test-cases-review` がこの手順で行う) |
| 作ったケースを行う・やり直す | `test-run` スキル |

変更の差分からテストケースを導き、作業フォルダに**下書き**(種別ごとの JSON)を書き、
エビデンスビューアが読む **`manifest.json`**(`result` の無い、未実施の項目)にまとめて渡すまでを行う。
専用の画面は作らない。HTML・CSS・JavaScript は書かない。

| 読むもの | 中身 |
|---|---|
| [reference/format.md](/.claude/skills/test-cases/reference/format.md) | 下書き・`order.json`・`00-cases.md` の形と、正本を作るコマンド(**書く前に必ず読む**) |
| [reference/writing.md](/.claude/skills/test-cases/reference/writing.md) | 項目の書き方(分からないことは聞く・3つの約束・読みやすく書く・優先度・コマンド・画面ベース・準備) |
| [reference/perspectives.md](/.claude/skills/test-cases/reference/perspectives.md) | 項目を導く観点(3つの見方・観点の出どころ・技法・狭い幅・変更前と比べる・重なり) |
| [reference/subagent.md](/.claude/skills/test-cases/reference/subagent.md) | サブエージェントの動く条件と共通の約束 |
| [templates/cases/](/.claude/skills/test-cases/templates/cases/) | ひな形(フォルダごと写して使う) |
| [agents/](/agents/)(dev-workbench の直下) | サブエージェント5つ(単体・結合・回帰・受け入れ・レビュー) |

## 一番大事な決まり

**「手で行うテスト」を行うのは人(ユーザー)であり、Claude ではない。** 親・サブエージェントともに必ず守る。

- Claude(親・サブエージェントとも)は、準備・テストの項目・後始末に書いた**コマンドを自分で実行しない**(コンテナの中のコマンド・データの作成/削除/更新を伴うコマンド・画面の操作など、`steps` に書く中身すべてが対象)。これらはユーザーがあとで自分の手で行って結果を確かめるためのもので、Claude が先回りして実行すると、ユーザーがまだ確かめていないのに環境の状態だけが変わってしまう(ほかの確かめの作業を巻き込んで壊す事故にもつながる)
- Claude がケースを作る時にしてよい確かめは、**コードを読む**(差分・実装・既存のテスト)、**形の整合を見る**(`check-cases.mjs`)、**期待する結果の根拠を、既存のコード・テストから拾う**ところまで。期待する結果は、実際に動かして確かめた数値ではない
- 実行してよいのは、`check-cases.mjs`・`build-manifest.mjs`(作業フォルダにだけ書く)と、`git diff` / `git log` / `gh issue view` / `grep` など、**対象のリポジトリにも環境にも書き込まない、読み取りだけの調べもの**だけ
- **項目に書くコマンドを試しに動かすのは、読み取りだけのもの(書き込みを外した版を含む)に限る。** 引用符・出力の形が動くことを、実際のデータで確かめるところまで。書き込むものは、試しでも動かさない
- 実装を読むだけでは言い切れない値(コマンドの出力の正確な文言など)は、**推測で埋めずユーザーに聞く**(`test-cases/reference/writing.md`「分からないことは聞く」)
- **本番や共有の環境のデータを書き換える操作はしない。** 本番の環境には、ユーザーが指示した時だけ、読み取りでつなぐ(画面を開く・一覧を取る・データベースを SELECT する、など)。保存・計算の実行・作成/更新/削除のリクエストは、試しでも行わない

## ゴール(ケースが満たすこと)

テストケースを作るゴールは、**ケースが次の5つを満たしていること**。ケースを書く・整理する・レビューする時の判断の基準にする。迷ったら、そのケース(や手順)が5つのどれに効くかで決め、どれにも効かないものは足さない。テストケースを作らない受入確認(`test-run/evidence/`)も、同じ5つで項目を作る。

| # | ゴール | 満たすための手立て |
|---|---|---|
| 1 | **イシューの要件を満たしていることを確かめられる** | 設計の `acceptance.md` があれば、その AC が要件になる(`test-cases/reference/format.md`「設計の受け入れ基準から作る」)。無ければ、要件を `plan.json` の `requirements` に書き出し、1つの要件に1つ以上の受け入れの項目を置く(2節)。すべての要件を指す、行う受け入れの項目が残っているかは `check-cases.mjs` が見る |
| 2 | **イシューに書かれていない仕様の動きを確かめられる** | 差分から見える分岐、共通の処理のほかの用途、実際のデータの形、副作用、変わらない側の今までどおりの動き、設計で決めたことを、単体・結合・回帰の観点として拾う(`test-cases/reference/perspectives.md`)。**受け入れの要件は、イシューと設計に書かれたものだけ**。要件に無い動きの期待する結果も、根拠(コード・既存の動き・仕様)を持つ |
| 3 | **自動のテストで確かめられていない動きを確かめられる** | 自動のテストを grep して**実際に読み**、その項目を確かめるテストがあるかで優先度を決める(`test-cases/reference/writing.md`「優先度」)。**確かめられていない動き(画面の流れ、実際のデータ、外のサービスとのつながり、画面にだけ出る文言)には、必ず項目を置き、優先度を高にする**。確かめられている動きも外さず、優先度を下げる。単体の `basis` に既存のテストの有無を残す |
| 4 | **実施する人が、操作や期待する結果の判定に迷わず進められる** | 画面の言葉だけで書く。手順は確かめる地点で区切り、期待する結果は具体的な値と画面に見えることにする。前提は状態で書く。`【要確認】` と「適切に」「正しく」のような判定できない言葉を残さない(`test-cases/reference/writing.md`) |
| 5 | **実施する人が、むだなく進められる**(品質を保ちつつ手間を抑える) | 重なりと、上位で賄える項目を行わない項目にする(5節)。実施の順に並べた正本を作る(7節)。準備は必要最小限にする(`test-cases/reference/writing.md`「準備は必要最小限にする」)。項目は、ゴール1〜3に効くものだけに絞る |

**ゴールの見直し(できあがる前に必ず行う)**: 6節のレビューと7-3の報告で、次の問いに答える。1つでも「いいえ」なら直す。

1. すべての要件に、行う受け入れの項目があるか(ゴール1)
2. 差分に含まれる分岐・共通の範囲・実際のデータの形・今までどおりの動き・設計で決めたことのうち、項目の無いものが無いか。イシューに書かれていない動きの期待する結果に、根拠があるか(ゴール2)
3. 自動のテストが確かめているだけの項目が、高い優先度で残っていないか。確かめられていない動きで、項目の無いものが無いか(ゴール3)
4. 項目を、初めて見る人が、聞き返さずに最後まで行って判定できるか(`【要確認】` が無い、画面の言葉、具体的な値)(ゴール4)
5. 準備・項目・実施の順に、省ける手順(同じ状態を作り直す、ログアウトの繰り返し、使わない準備)が残っていないか(ゴール5)

## 場所

| 場所 | 何に使う |
|---|---|
| **対象のリポジトリ**(cwd) | `git diff`・`gh`、コードの grep・調べもの。**何も書き込まない**(テストケースもコミットしない) |
| **作業フォルダ** | 設計(spec.md・acceptance.md・test.md)を読む。下書き(`cases/`)と正本(`evidence/<YYYY-MM-DD>-<内容>/manifest.json`)を書く |
| **dev-workbench**(`<dev-workbench>`) | このスキルのスクリプト・ひな形・サブエージェント、`.claude/skills/config.json`、`docs/` |

- 作業フォルダ・リポジトリ名と番号の決め方・環境変数・ビューアのURL: [docs/workspace.md](/docs/workspace.md)(`DEV_WORKBENCH_DOCS` が空なら止めて聞く)
- 以降のパスは、Read / Write / Agent に**絶対パスに展開して**渡す(環境変数は展開されない)。cwd の外に書き込むので、作業フォルダを書き込みの許可に入れておく(`additionalDirectories` か `--add-dir`)
- サブエージェントが見つからない時(dev-workbench をプラグインとして入れていない、など)は、そのファイルの中身をプロンプトに写して汎用のサブエージェントに渡す。入れ方は `<dev-workbench>/README.md` の「使い始める」

## 全体の流れ

1. 差分・イシュー・設計を読み、骨格を用意する
2. テストの観点を洗い出す(単体・結合・回帰・受け入れの4つの種別ごと)。イシューの要件も洗い出す
3. 観点ごとに節を作る(親が節の骨格と id まで決める)
4. **先に準備・後始末と事実のシートを決め(4-0)**、そのうえで種別ごとにサブエージェントを**並行に**起動し、項目を書かせる
5. 全ファイルを見て、重なった項目と、上位のテストで賄えている下位の項目を、行わない項目にする。**どこから拾ったかと項目の対応表(`cases/00-cases.md`)を埋める**(親が行う)
6. レビューのエージェントに漏れを見てもらい、指摘を直す(親が行う)
7. 行わない項目を除き、実施の順に並べ直した**正本(`manifest.json`)**を、作業フォルダの `evidence/<YYYY-MM-DD>-<内容>/` に作る(親が行う)
8. ビューアのURLを渡す

## 時間を抑える進め方(書き直しの往復をなくす)

作るのに時間がかかるわけは、**あとから前提・事実が変わって、全ファイルを書き直すこと**。次の3つを、項目を書かせる前に済ませる。

1. **使える既存のアカウント・データを、先に読み取りで調べる。** 準備でアカウントやデータを新しく作る前に、権限の中身(入れる画面)、機能の有効・無効の設定、使われていないデータを調べる。パスワードの有無はユーザーに聞く(準備には書かない)。調べずに準備を書くと、あとから作り直して、準備を前提にする全項目を直すことになる
2. **事実のシートを、実測で先に固める**(4-0)。外のサービスの名前、区分・方法などの値の定義、権限、画面の言葉は、コードや読み取りの調べもので確かめた値だけを渡す。推測のまま渡すと、4つのファイルすべてに誤りが広がり、一括で置き換えることになる。**準備や項目に書くコマンドは、実施する人が画面で使う環境(画面がつながるサーバー、同じデータベース)を指しているか**を、動いているプロセス・コンテナの一覧とデータの件数の読み取りで確かめてから書く(実例: 作業用に別に起動した環境を指していて、画面で作ったデータが「0件」になった)
3. **項目が少ない時(目安: 行う項目が30件前後以下、または変更が1〜2か所)は、種別ごとにサブエージェントを分けず、1人(または親)が全部書く。** 並行にすると、番号・準備の参照・事実の食い違いを合わせる手間のほうが重くなる

## 1. 差分・イシュー・設計を読み、骨格を用意する

**推測で書かない。** 必ず差分と実装を読んでから書く。

```bash
git diff --name-only <基点>...HEAD
git diff <基点>...HEAD
gh pr view <番号> --json title,body,baseRefName,headRefOid,url,closingIssuesReferences   # PR がある時。gh pr diff <番号> でも差分を取れる
gh issue view <イシュー番号> --comments
```

- 作業フォルダに設計(`spec.md` 最終仕様・`acceptance.md` 受け入れ基準・`test.md` テストの方針)があれば読む。決まった仕様は観点の出どころに、テストの方針(範囲・環境・確かめないこと)は2節以降の前提にする
- **設計の `acceptance.md` があれば、受け入れの項目は書かない。** スクリプトが表からそのまま作る(`test-cases/reference/format.md`「設計の受け入れ基準から作る」)。`plan.json` に `requirements` を書かず、`cases/acceptance.json` を作らず、受け入れのサブエージェントを呼ばない。`test.md` で手段を「自動」とした AC は項目にならない。単体・結合・回帰は、AC で確かめきれないもの(差分の分岐・境界、変えた共通の処理を使うほかの画面など)だけを書く
- 作業フォルダを作り直す(`<イシュー番号>_2`)時は、作り直しの範囲をユーザーに確かめ、再テストなら、対象のコミットの範囲と、要件をその変更で動きが変わる点に絞ったものを `plan.json` に書く。結果を残したまま一部の項目だけやり直すなら、作り直さず [やり直し(`test-run/retest/`)](/.claude/skills/test-run/retest/SKILL.md) を使う

[templates/cases/](/.claude/skills/test-cases/templates/cases/) を `<作業フォルダ>/cases/` に写す(すでにあれば上書きしない)。`plan.json` には `title`(イシュー番号と内容が分かる短い名前)と `source`(リポジトリ・PR・コミット・URL)を置き、`notes`(変更の概要と確かめる条件)・`requirements`・`excluded` は2節で埋める。`setup.json` / `cleanup.json` は親が書く。項目の無い種別のファイルは消す。設計の `acceptance.md` がある時は、`acceptance.json` を消し、`plan.json` の `requirements` も消す(1節の「設計の `acceptance.md` があれば」)。**この時点では観点ごとの節(TC-01 など)はまだ作らない。**

## 2. テストの観点を洗い出す

**節を作る前に、まず観点だけを箇条書きで並べる。** 先に節を作ると、思いついた順の切れ切れの観点しか出てこない。観点は `test-cases/reference/perspectives.md` の3つの見方と「観点の出どころ」を上から総なめにして拾い、差分を1行ずつ見直して、対応する観点が無い行が残っていないかを確かめる。

| 種別(`kind`) | 何を確かめるか | 導き方 |
|---|---|---|
| **単体(ホワイトボックス)** `unit` | 変更した関数・部品の中の分岐が意図どおりか | **コードを読んで**導く。分岐・途中で抜けるところ・繰り返しの 0件/1件/複数件・境界の値・例外を1つずつ拾い、各分岐を通す入力を画面の操作に落とす。期待する結果の根拠は path:line(`basis` に書く) |
| **結合(ブラックボックス)** `integration` | 画面の操作から最後の出力(画面・CSV・ファイル・ほかの画面)まで、仕様どおりにつながるか | **実装を見ずに**、仕様と使う人の操作から導く。入力と出力だけで判定する。期待する結果の根拠は仕様・既存の画面の実測 |
| **回帰(デグレ)** `regression` | 変更前から動いていたものが壊れていないか | 変更した所を**共有するほかの用途・ほかの画面・周りの機能**を洗い、変更前の動きと比べる |
| **受け入れ** `acceptance` | イシューの**要件**を満たしているか | 要件を1つずつ取り出し、**1つの要件に1つ以上の項目**。業務の言葉で、要件が実現されたかを判定する。各項目に `requirement` で要件の id を付ける |

- 同じ画面を見ていても、導き方が違えば別の観点。結合は「流れが正しいか」、受け入れは「頼まれたことが実現されたか」。1つの観点を種別をまたいで混ぜない
- 4つの種別とも考える。観点が1つも出ない種別はファイルを作らず、`plan.json` の `notes` に「単体: 該当なし(理由)」と1文残す。**確かめないこと(`excluded`)にはしない**
- 要件は、設計の `acceptance.md` が無い時だけ、`plan.json` の `requirements` に1件ずつ書き出す(`{ "id": "R1", "text": "…" }`)。確かめないことは `excluded` に理由つきで書く(差分に含まれていないものだけ)

## 3. 観点ごとに節を作る

**1つの観点=1つの節。** 複数の観点を1つの節にまとめない。1つの観点を複数の節に分けない。境界の場合は別の節にせず、同じ観点の中に置く。

- 準備・後始末は決まった骨組みで、この決まりの外
- それ以外は `tc01` から**種別をまたいで通し番号**で `id` を振り、`title` を `TC-01 …` で始める(例:「TC-01 主な症状の確認」)。`kind` は種別のファイルで決まる。並びは **準備 → 単体 → 結合 → 回帰 → 受け入れ → 後始末**
- 項目の `id` は節の `id` を頭にした `tc01-04` の形。**決めたあとは変えない**(エビデンスのファイル名と再テストの対応に使う)。足す時は末尾に足す
- 画面をまたぐ節(全画面の見出しの表示など)は、操作の順に依存しないなら**メニューの並びに揃える**。並びはメニューの定義を読んで取り、推測しない。複数の節で同じ画面の群を扱う時は、すべて同じ並びにする。操作の順に依存する時は操作の順を優先し、外したわけを1行添える
- 実施の必要度に差がある観点(時間が無ければ後回しでよい、など)は、節の `notes` に書く
- 動きを変えないことが目的の変更は、`test-cases/reference/perspectives.md`「動きを変えないことが目的の変更」の3つを別の節にする

### 3-1. 共有するデータの状態表を作る

複数の項目が**同じデータを書き換える**と、行う順によって、後ろの項目の前提が崩れる(実例: 同じ利用者の設定が項目ごとに書き換わり、あとから準備の直後に戻すコマンドを足して、前提を書き直した)。**項目を書く前に、状態表を作る。**

- 縦に共有するデータ(利用者・設定・申請など)、横に項目を並べ、各項目がそれを**どう変えるか**(読むだけ/書き換える/使い切る)と、**戻す手順**を書く
- 書き換える項目には、**項目の中で元に戻す手順**を入れるか、準備に**戻すためのコマンド**(何度行っても同じ状態に戻る)を置く。準備を書く時点で決める(4-0)
- 申請などを使い切る項目は、どの項目がどれを使い切るかの対応表を作り、取り合いが無いことを確かめる
- 状態表は、サブエージェントのプロンプトにも渡す。7節の実施の順を決める時の、制約の一覧にもなる。作業フォルダの `cases/` に Markdown で置いてよい(正本には添えない)

## 4. サブエージェントを並行に起動して項目を書かせる

### 4-0. 先に準備・後始末と事実のシートを決める

項目の担当は、準備が決まっていないと、画面の言葉・使う利用者・実際のデータを書けず、`【要確認】` を大量に残す(実例: 準備がひな形のまま4種を並行に書かせ、29件の `【要確認】` が出た。その大半は、準備とコードを読めば決まる中身だった)。**項目の担当を起動する前に、次の2つを済ませる。**

1. **準備・後始末を書く**(`setup.json` / `cleanup.json`。書き方は `test-cases/reference/writing.md`「準備・後始末」)。項目の `id`・`title`・用意する状態(どの利用者がどんなデータか)を**決めてから**項目の担当を起動する。項目の前提は「準備の〜を済ませている」の形で書かせる
2. **事実のシートを作る**(ファイルにしなくてよい。プロンプトに貼れる形で)。項目に書く**具体的な値**を、根拠つきでまとめる: 実際のデータ(コードと対応する名前、外のサービスの実測の値)/ 画面の言葉(メニュー名・タブ名・ボタン名・メッセージ)と出どころ(画面のコードの path:line)/ 使うアカウントと権限 / 準備が用意する利用者・データの ID と状態。**確かめていない値は、推測のまま渡さない。**「未確認」と書くか、先にユーザーに聞く(実例: 実測と違う名前を4つのファイルに書かせ、あとで一括で置き換えた)

単体・結合・回帰・受け入れの項目は互いに関わらないので、**1つのメッセージで種別ごとの Agent の呼び出しを同時に出して、並行に書かせる**(設計の `acceptance.md` がある時は、受け入れを除いた3つ)。書き込む先を種別ごとに分けてあるので、ぶつからない。**親が3節までと4-0を終えてから起動する**(番号が種別をまたぐので、書き始めてから節を増やしたり減らしたりするとぶつかる)。

| 種別 | サブエージェント | 書き込む先 |
|---|---|---|
| 単体 | `test-cases-unit` | `<作業フォルダ>/cases/unit.json` |
| 結合 | `test-cases-integration` | `<作業フォルダ>/cases/integration.json` |
| 回帰 | `test-cases-regression` | `<作業フォルダ>/cases/regression.json` |
| 受け入れ | `test-cases-acceptance`(設計の `acceptance.md` が無い時だけ) | `<作業フォルダ>/cases/acceptance.json` |

プラグインとして入れた時の名前(`dev-workbench:test-cases-unit` など)は `docs/workspace.md` の「dev-workbench の場所」。

### 親がプロンプトに入れるもの

サブエージェントが読む決まり(`test-cases/reference/` の `format.md`・`writing.md`・`subagent.md` など)は、各サブエージェントのファイルの「先に読む」に挙げてある。プロンプトには、決まりを写さず、次の中身を入れる。

- **作業フォルダ・対象のリポジトリ・`<dev-workbench>` の絶対パス**
- イシューの要件・変更の概要、差分の範囲。**結合にはコードのパスを渡さず**、仕様・画面の情報・メニューの並びだけを渡す
- 受け持つ節の一覧(`id` / `title` / `kind` / 節の説明)と、書き込む先のファイル
- 受け入れには**要件の一覧**(`plan.json` の `requirements`)
- **決まった `setup.json` のパスと、事実のシート**(4-0)と、共有するデータの状態表(3-1)
- コードの調べものを頼む時は、**対象の作業ツリー(`git -C <パス>`)とコミットの範囲**(手元のチェックアウトが別のブランチだと、`git diff main...HEAD` に目的の変更が含まれない)
- PR の本文・イシューのコメント・作業フォルダの設計など、サブエージェントが取れない外の文書は、**親が先に取って貼る**
- ユーザーが本番の環境への読み取りを指示していれば、そのこと

### 戻ってきたら

1. `check-cases.mjs <作業フォルダ>` を**親が必ず実行する**(サブエージェントは実行できないことがある。コマンドは `test-cases/reference/format.md`「正本と証跡を作る」)
2. `【要確認】` と確かめることを集め、**次の3段階で仕分けて**埋める(全部埋まるまで `check-cases.mjs` は通らない)。親が推測で埋めない
   - ① 一覧にする: `check-cases.mjs` が出す id と、報告にある質問をまとめ、項目ごとに質問を並べる
   - ② **「調べれば決まるもの」と「ユーザーの判断が要るもの」に分ける。** 前者は、コード・準備・外のサービスの読み取りの GET で決まるもの(画面の言葉、実際のコード、どの利用者を使うか、変更前の動き)。後者は、仕様の是非、対象に含めるか、再現できない手順をどう扱うか
   - ③ 前者は**調べものの担当(サブエージェント)にまとめて任せる**(読み取りだけ。埋めた中身を id ごとに報告させる)。後者だけを `AskUserQuestion` で**1回にまとめて**聞く(選択肢と推奨を添える)
3. 5節の重なりの整理

## 5. 重なった項目を、行わない項目にする

全ファイルの項目を見て、種別・節をまたいで同じ操作・同じ期待する結果の項目が無いかを見直す。**同じ画面を同じ操作で確かめる項目は、種別が違っても、1回行えば足りる。** 実施の手間と、同じ申請・同じデータを何度も使い切るぶつかりを減らすために、**下位のテストが上位のテストで賄えていれば、下位の項目を行わない項目にする**。

**消さずに、打ち消し線で残す。** 行う方(一番自然に説明できる方)はそのまま残し、もう一方に `"duplicateOf": "tc01-04"` を足す。照らし合わせ方は `test-cases/reference/perspectives.md`「重なりをまとめる」。

### 5-1. 上位のテストで賄えている下位の項目

**テストの階層(低い方から)**: 単体 → 結合 → 回帰・受け入れ。下位の項目の操作と期待する結果のすべてが、1つ、または複数の上位の項目で確かめられていれば、下位の項目を行わない項目にする(上位を残す)。

- 回帰と受け入れの間、同じ種別の中では、階層の上下は無い。同じ操作・同じ期待する結果なら、より自然に説明できる方を残す
- **受け入れの項目は、要件を確かめる唯一の拠り所になりうるので、軽々しく行わない項目にしない**(`check-cases.mjs` が、すべての要件を指す受け入れの項目が残っているかを見る)
- 上位の項目の `given`・`steps`・`expect` を**実際に読んで**決める(`title` や節の名前だけで決めない)。`duplicateOf` は1件しか指せない。複数の項目にまたがる時は、**一番よく含む上位の項目1件**を指す
- 足りないところが小さければ、上位の項目に書き足してから行わない項目にする。書き足しは、今の期待する結果を損なわない最小限にする。**受け入れの項目への書き足しは、要件の文の範囲に収まる時だけ**。収まらないなら、回帰・結合の項目に書き足して、そちらを指す
- **賄えていないものは、行わない項目にしない**。判断が割れる時も行う項目のままにして、わけを記録する。典型: 上位に無い状態・分岐(0件、境界の値、初めの状態、例外、入力の変わり種)/ 上位に無い画面の組み合わせ / 結合が画面をまたぐ**一連の流れ**として確かめているもの、狭い幅、画面の外の出力 / 単体だけが、画面から再現できない分岐を `basis` で確かめているもの
- 行わない側の `title`・`given`・`steps`・`expect`・`basis` は**残す**(証跡に打ち消し線で出る)。残す側は、**階層が同じか上の項目で、自身が `duplicateOf` を持たないこと**。単体どうし・結合どうしで指さない

**整合を取る**
- 行わない項目にした id を、準備や、ほかの項目の前提が**行う項目として参照していないか**を確かめ、参照を残す側の id に置き換える
- 上位の項目に書き足したら、準備の件数(申請の数・使う利用者・使い切る項目)と実施の順が成り立つかを確かめる。**申請などを使い切る項目を、新しく足さない**
- 進め方: ① 下位の行う項目を一覧にする ② 1件ずつ、上位の項目を読んで、賄えているかを決める ③ 書き足しが要るものは書き足す ④ `duplicateOf` を付ける ⑤ `check-cases.mjs` を通す ⑥ 準備と前提の参照を直す。項目が多い時は、種別ごとにサブエージェントに任せてよい(この節と `test-cases/reference/perspectives.md`「重なりをまとめる」を読ませる)
- 行わない項目にしたあとの件数(種別ごとの全件・行わない・行う)を数えて、報告に含める

### 5-2. 対応表(`00-cases.md`)を埋める

`cases/00-cases.md`(ひな形にある。`plan.json` の `attachments` で正本に添える)に、どこから拾ったか(要件・観点の出どころ・変えた処理・決めたこと)と項目の対応、行わない項目にしたもの(行わない側 → 残す側、残す側に書き足したこと)、確かめないことを書く。形は `test-cases/reference/format.md`「00-cases.md」。

## 6. レビューのエージェントで漏れを見る

重なりの整理まで終えたら、`test-cases-review` を起動する。項目の書き手とは別の文脈で、**差分と要件に対して項目に漏れが無いか**を見る(読み取りだけ。直さず、指摘だけを返す。見るものは [review/SKILL.md](/.claude/skills/test-cases/review/SKILL.md))。

- 渡すもの: `<作業フォルダ>/cases/` のパス、対象のリポジトリのパスと差分の範囲、要件、作業フォルダの設計(あれば)、事実のシート
- 打ち消し線の付いた全件をビューアで見たい時は、先に `build-manifest.mjs <作業フォルダ> --trail` で `cases/manifest.json` を作っておく
- 書き手のサブエージェントは使い回さず、レビュアーには**書き手の途中の考えを渡さない**(できあがったものだけを見て決めさせる)
- 返ってくるのは、P1〜P3 の指摘(重要度の意味は `test-cases/review/` の「出力」)と、ゴールの5つへの答え
- 親は P1・P2 を直す。足す時は**末尾に足す**(id は変えない)。足したら `check-cases.mjs` を通す
- 直したら、P1 があった時に限りもう一度レビューさせる(2回まで)。2回目でも P1 が残るなら、ユーザーに判断を仰ぐ

## 7. 実施する正本(manifest.json)を作る

6節までの下書き(種別ごとのファイル)は、「なぜこの項目が無いか」を追える**証跡**で、行わない項目が混ざり、種別ごとに並んでいるので、実施する人には見づらい。**行わない項目を除き、実施の順に並べ直したものを、1つの `manifest.json`(正本)にまとめる**(証跡のファイルは変えずに残す)。実施の順は `cases/order.json` に手で書く(形は `test-cases/reference/format.md`「実施の順」)。項目が少なく、種別の順のままで行えるなら、`order.json` は作らなくてよい。
`<YYYY-MM-DD>-<内容>` は作った日と、英小文字とハイフンの内容(例: `2026-11-22-pr45`)。

### 7-1. 並べ方の判断

- **グループの並び**は、準備の「実施の順」に沿わせる。目安: ① 見るだけ(使う人の画面)→ ② 見るだけ(管理する人の画面)→ ③ 宛先の登録・通知を確かめるための申請など、データを作る → ④ 前もって作っておいたデータを使い切る項目(承認・差し戻し・修正の依頼)→ ⑤ 作り直したあとに使い切る項目 → ⑥ 入力・保存・提出 → ⑦ 最後(後始末のあとに行うもの。`afterCleanup`)
- **グループ**は、同じアカウント・同じ画面を続けて見るようにまとめる(アカウントや環境の切り替えを減らす)。おおむね3〜8項目。`who` に使うアカウントを書く
- **同じ人が同じ画面を、別々の項目で開き直す/同じ流れの中で続けて確かめられる項目は、統合した項目にまとめる。** 元の項目の確かめを1つも落とさない。元の項目は証跡として変えない
- 項目は、1つの画面を1つの項目の小さな項目にする(操作→期待する結果を、項目ごとに完結させる)。前の項目から続く時は、手順を最初から書かず、`@key` で「@key の続き」と書く(ログイン・画面を開く手順の繰り返しを避ける)
- 各項目の `given` を読み、**前提となる状態(別の項目が作る・変える状態、申請などの使い切り)が、先に行う項目に含まれる順**にする。行わない項目が順の制約に出てくる時は、`duplicateOf` の先の行う項目に読み替える
- 各グループの `note` に、続けて行うわけ・始める前の注意(ログインするアカウント、このグループは申請を使い切る、など)を、画面の言葉で1〜3文書く
- 1つの項目に複数の時点の操作(申請 → 承認 など)が入っていて分けられない時は、そのまま1つのグループに置き、`note` で、どのアカウントがいつ何をするかを書く
- サブエージェントに任せてよい(準備と全項目と `test-cases/reference/format.md`「実施の順」を読ませ、`order.json` と、`check-cases.mjs` の結果を返させる)

### 7-2. 作って確かめる

`check-cases.mjs` → `build-manifest.mjs --trail --out <作業フォルダ>/evidence/<YYYY-MM-DD>-<内容>` → `check-manifest.mjs` の順に動かす(コマンドと、正本で何が変わるかは `test-cases/reference/format.md`「正本と証跡を作る」)。証跡の項目を直したら、正本を作り直してから `--manifest` で合っているかを確かめる。正本にすでに結果があれば、[やり直し(`test-run/retest/`)](/.claude/skills/test-run/retest/SKILL.md) の手順で新しいフォルダに作る。

### 7-3. 報告

正本の件数(グループの数・行う項目の数)、`order.json` の並べ方の根拠(順の制約をどう反映したか)、順がぶつかって直した点を、ユーザーに報告する。あわせて、**ゴールの見直し(5つ)の結果**を1行ずつ報告する(満たしていないものがあれば、直すか、ユーザーに判断を仰ぐ)。

## 8. 渡す

正本のフォルダ(`evidence/<YYYY-MM-DD>-<内容>/`)のビューアのURLを作る。作り方(Drive への置き方・フォルダ ID の取り方・`<site>evidence/?folder=<ID>`)は [docs/workspace.md](/docs/workspace.md) の「Driveへの置き方」「ビューアで開く」。
ユーザーに、そのURLと件数(グループ・行う項目・種別ごとの全件/行わない)を渡す。証跡を見たい人には、`cases/` のフォルダ ID で同じ形のURLを作る。

## ライト版の設計から作る

ライト版の設計(作業フォルダの `index.md` に `進め方: ライト版`)では、上の1〜8の流れを通さず、`acceptance.md` から正本を作る。サブエージェントは呼ばない。「一番大事な決まり」と「ゴール」はそのまま守る。

1. 差分・イシュー・設計を読む(1節のコマンド)
2. `cases/plan.json` を、ひな形の `plan.json` から `title`・`source`・`notes` だけで書く(`requirements` と `attachments` は書かない。`00-cases.md` と `order.json` は作らない)
3. 補う項目: `acceptance.md` の AC で確かめきれないもの(差分の分岐で画面から見えるもの・境界の値、変えた共通の処理を使うほかの画面)があれば、親が1人で、種別ごとの下書き(`unit.json`・`integration.json`・`regression.json`)に書く。書き方は `test-cases/reference/format.md`・`writing.md`、観点は `perspectives.md`。準備が要れば `setup.json`・`cleanup.json` を書く
4. `check-cases.mjs <作業フォルダ>` を通す
5. レビュー: 親が、テストケースのレビュー([review/SKILL.md](/.claude/skills/test-cases/review/SKILL.md))の観点とゴールの見直し(5つ)で見直し、直す
6. `build-manifest.mjs <作業フォルダ> --out <作業フォルダ>/evidence/<YYYY-MM-DD>-<内容>` で正本を作り、`check-manifest.mjs` を通す(コマンドは `test-cases/reference/format.md`「正本と証跡を作る」)。節は、準備 → 単体 → 結合 → 回帰 → 受け入れ → 後始末 の順に並ぶ
7. 8節のとおりに渡す。件数と、項目にしなかった自動の AC を報告する
