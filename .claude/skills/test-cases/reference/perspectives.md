# 項目を導く(観点の決まり)

変更から、確かめる項目を漏れなく導く決まり。テストケース(`test-cases`)でも、テストケースを作らない受入確認(`test-run/evidence/`)でも、これで項目を拾う。
仕様を決める時も、同じ見方を使う。「どう確かめるか」が言えない仕様は、まだあいまいなところが残っている。

項目が満たすゴール(5つ)は `test-cases/SKILL.md` の「ゴール」。足すか迷った項目は、どのゴールに効くかで決め、どれにも効かないものは足さない。
項目の書き方は [writing.md](/.claude/skills/test-cases/reference/writing.md)。

## 3つの見方

項目は、どれも次のどれか1つから拾う。

| 見方 | 何を確かめるか | どこから拾うか | テストケースの種別 |
|---|---|---|---|
| 要件 | イシューや設計に書かれた要件を満たしていること | イシューの本文、決めた仕様(spec.md・acceptance.md) | 受け入れ |
| 既存機能への影響 | 変更が、もとからある機能を壊していないこと。とくに共通の処理を変えた時 | 差分と、変えた処理(関数・型・設定・スタイル・保存のキーなど)を使っている場所 | 回帰 |
| 設計で追加した仕様 | 要件の文には無いが、設計や実装の途中で決めた動き | 相談して決めたこと、実装中に決めた細かいこと、レビューで足した直し | 単体・結合 |

「要件」に置くのは、イシューと設計に**書かれたこと**だけ。書かれていない動きは、ほかの2つに置く(要件を勝手に増やさない)。要件が無い・あいまいなら、ユーザーに確かめる。

### 要件

1. イシューと設計を、**1行に1つの要件**になるまで分ける。「AとBができる」は2つにする
2. 要件に番号(R1, R2, …)を振る
3. 要件ごとに1つ以上の項目を作る。**できないこと・失敗した時の振る舞いを先に**考える(後回しにすると漏れる)
4. 不具合を直すイシューは、**直す前に起きていたことが起きない**ことを必ず項目にする

### 既存機能への影響

1. 差分から、変えた処理(関数・定数・型・設定・スタイル・保存のキーなど)を書き出す
2. それを**使っている場所を検索で探す**。変えていない機能から使われていれば、そこが影響を受ける
3. 影響を受ける場所ごとに、いつもの操作が今までどおり動く項目を作る。共通の処理を変えた時は、**使っているすべての機能**で1つずつ
4. 動きを狙って変えた時は、変わった後の動きは「要件」か「設計で追加した仕様」で確かめ、ここでは**変わってはいけないところ**だけを確かめる
5. 保存するデータの形を変えた時は、前に保存したデータで開けることを項目にする

### 設計で追加した仕様

要件の文には出てこないので、意識して拾わないと漏れる。

- 相談して決めたこと(数値・置き場所・名前・操作のやり方・文言)
- 実装中に決めた細かいこと(押せない時の見せ方、最小の大きさ、範囲の外の値の扱い、エラーの出し方など)
- レビューで足した直し
- 空・上限を超えた入力・対象が無い時などに、どう振る舞うと決めたか

## 観点の出どころ

3つの見方で拾ったあと、次の表を**上から順に総なめ**にして、差分に当てはまるのに項目が無いものを足す。当てはまらない行は飛ばしてよい。

| 出どころ | 拾い方 | テストケースの種別 |
|---|---|---|
| 前提の条件 | 不具合が再現する条件・確かめるためのデータの作り方。**一番大事**。満たさないまま行うと、全項目が誤って合格になる | 準備 |
| 主な症状 | 変更で直るはずの動き。変更したファイルすべてを画面に結びつけて並べる | 結合 |
| 分岐 | 差分の `if` / `else` / `try` / `catch` / 途中の `return`。繰り返しは 0件・1件・複数件。1つの分岐に1つ以上 | 単体 |
| 入力の欄 | 入力の欄ごとに、必須か任意か・型・桁数・文字の種類・初めの値。境界の値(最小−1・最小・最大・最大+1)。空の入力の変わり種(空、前後の半角/全角の空白だけ、空白+値) | 単体・結合 |
| データの状態 | 重ねてはいけない値の有無・未登録・複数の所属・削除済みなど、**実際のデータにありうる形**(古い形のまま保存されたデータで壊れないか) | 単体・回帰 |
| 権限 | 使う人の役割・権限の組み合わせ | 単体・結合 |
| 状態の移り変わり | 新規・編集・削除・承認の前後などの状態と、移る前後。移れない組み合わせも書く | 単体・結合 |
| 新しく作る時/既存を読み込む時 | 同じ部品でも、新しく足す時と既存のデータを読み込む時で、作られる道筋が違うことがある。両方を実際に通す | 単体・結合 |
| 外とのやりとり | ほかの画面・ほかの定期的な処理・ほかのサービスなど、別に更新されうるものとの整合。失敗した時の振る舞い | 結合 |
| 画面・文言の変更 | 見た目や文言が変わったら、変更した画面ごとに狭い幅の項目を作る(下の「狭い幅の確認」) | 結合 |
| 条件で振る舞いが分かれる変更(対になる確かめ) | 利用者の種類・設定の有無・権限など、条件で表示や動きが変わる差分は、変わる側だけでなく、**変わらない側(今までどおり)の確かめも対にして置く**。変わる側の確かめを1つずつ並べ、**それぞれに対応する「今までどおり」の確かめが、どこかの項目にあるか**を突き合わせる(「変わらない」側を1つの節にまとめるだけでは、変わる側の確かめが抜け落ちる) | 結合・回帰 |
| 画面の外の入力・出力 | ファイルの取り込み・ダウンロード・通知・ログなど、画面の表示とは別の道を通るもの(必須/任意・対象の項目か、列が含まれるか・見出しが正しいか) | 結合 |
| 既存機能への影響 | 上の「既存機能への影響」 | 回帰 |
| 設計で決めたこと | 上の「設計で追加した仕様」。作業フォルダの spec.md と PR の議論から拾う | 単体・結合 |
| 要件 | 上の「要件」 | 受け入れ |
| 確かめないこと | **差分に含まれていない**ので確かめなくてよいもの。書いておかないと、不合格の誤報が出る | 確かめないこと |
| 後始末 | 確かめるために変えた環境・データを戻す手順 | 後始末 |

拾い終えたら、**差分を1行ずつ見直し、どの項目にも結びつかない行が残っていないか**を確かめる。残っていれば、観点が漏れている。

### 確かめないこと

**確かめないことは、差分に含まれていないものだけに使う。** 差分が触れているものは、確かめないことにしない。
自動のテストで確かめていても、確かめないことにしない。自動のテストの有無は、優先度でだけ加減する([writing.md](/.claude/skills/test-cases/reference/writing.md)「優先度」)。
根拠にする前に、そのテストのコードを実際に読み、どの操作を行っているかを確かめる(ファイル名や describe だけで「確かめられている」と決めない)。
(悪い例:「入力の画面は E2E のテストで確かめているので確かめない」→ 実際は表示と入力の検査しか見ておらず、ボタンは一度も押していなかった)

確かめないことは、理由つきで書く(テストケースは `plan.json` の `excluded`、受入確認は `notes` の「確かめないこと」)。

## 漏れを防ぐ技法

当てはまる時だけ使う。機械的に境界の場合を出す。

| 技法 | 使う時 | すること |
|---|---|---|
| 同値分割・境界値 | 値に範囲・上限・件数がある | 有効/無効のまとまりと境界(最小−1・最小・最大・最大+1、0件・1件・上限の件数)を出す |
| 組み合わせの表 | 条件が複数あり、組み合わせで結果が変わる | 条件×条件の表を作り、**全部の組み合わせを先に出してから**優先度で間引く。先に間引くと漏れる |
| 状態の移り変わり | 画面やデータが状態を持つ | 状態×操作を並べ、移れない組み合わせも書く |
| エラー推測 | 前の不具合やミスの形に心当たりがある | 似た不具合・起きやすい間違いを並べる |

## 狭い幅の確認

**画面の見た目や文言が変わる**(ラベル・メッセージ・列・ボタン・並べ方の追加や変更。文言が長くなる変更を含む)時は、変更した画面を**狭い幅(例: 375px)**で開いて表示が崩れないかを確かめる項目を、必ず作る。

- テストケースでは、**1つの観点=1つの節**(結合)にまとめ、**変更した画面ごとに1項目**。見た目の変更が無い差分(サーバーだけ・ロジックだけ)では作らない
- 操作の書き方: ブラウザの開発ツールの端末の表示などで幅を 375px にして、変更した画面を開く(コマンドは書かない)
- 期待する結果は崩れを具体的に書く: ページ全体が横に動かない/変更した文言・ラベルが欠けたり、ほかの部品と重ならない/ボタン・入力の欄が押せる・入れられる/表や長い文字は折り返す、または枠の中だけで横に動く。変更前の見え方より悪くなっていないことも添える
- **対象の画面が狭い幅で使われるか分からなければ、推測せず、ユーザーに聞く。** 使われないと答えられたら、項目を作らず、確かめないことに理由と合わせて書く
- 優先度は、変更した文言・並べ方が崩れやすいもの(長い文言・列が増える)を高にする

## 動きを変えないことが目的の変更(変更前と比べる)

共通化・ファイルの分け直しなど、「動きを一切変えないこと」が目的なら、次の3つを**混ぜずに**別の節(項目)にする。

1. **変更前の撮影**(テストケースでは `kind: regression`)— 変更前のコードで、見るべき画面や出力を撮るだけ。合否を判定しない
2. **変更後の確かめ** — 変更後のコードで、コードから導いた期待する結果を満たすかだけを確かめる。変更前とは比べない
3. **変更前/変更後の見比べ**(テストケースでは `kind: regression`)— 1と2で見えた同じ画面を1つずつ見比べ、意図しない違いが無いことを確かめる

混ぜないわけ: 期待する結果に照らすだけでは、共通化のついでに**直ってしまった既存の不具合**のような、コードを読んでも予見できない違いを見逃す。3で見つかった違いは、「意図した、ついでの直し」か「確かめていない壊れ」かを切り分けて記録に書く。

## 重なりをまとめる

同じ操作・同じ結果を確かめる項目が、節や種別をまたいで重なっていないかを見る。**消さずに、行わない項目として残す**(テストケースは `duplicateOf`。手順は `test-cases/SKILL.md` 5節)。

- まとめる前に、行わない側の期待する結果を**1つずつ**取り出し、残す側で確かめているかを照らし合わせる。題名や操作が似ているだけで決めない
- 残す側に足りない確かめがあれば、残す側に足してからまとめる。足せない(要件の範囲を超える、別の利用者・別の状態で行う確かめ)なら、まとめない
- 要件を確かめる項目は、同じ要件を確かめる別の項目が残る時だけまとめてよい
- 1つの要件・1つの影響先・1つの決めたことに結びつく項目が、まとめた結果ゼロにならないようにする
- 見落としやすい例: 行わない側が「保存されていないこと(開き直しても元のまま)」を確かめているのに、残す側は画面の上の取り消しで終わっている/行わない側は別の利用者(名前が空の行など)で確かめている
- まとめたことは、対応表(`00-cases.md`)に「行わない側 → 残す側(残す側に足したこと)」で残す
