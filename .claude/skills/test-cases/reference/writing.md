# 項目の書き方

実施する人が、聞き返さずに最後まで行って判定できる項目にするための書き方。親もサブエージェントも、項目を書く前に読む。
欄と形の決まり(どの欄に何を書けるか)は [format.md](format.md)、どんな項目を作るかは [perspectives.md](perspectives.md)。

## 分からないことは聞く

**推測で埋めない。** 仕様・要件・期待する結果・前提・画面の名前・メニューの並び・手順など、差分やイシューから読み取れない点は、**その都度ユーザーに聞く**。

- 親は `AskUserQuestion` で、選択肢と推奨を添えて聞く(1回に4問まで。同じ種類の疑問はまとめる)。聞いてから書く。想定の値や「たぶん〜」「実測して記録(想定: …)」で埋めて、あとで直す進め方にしない
- サブエージェントはユーザーに聞けない。読み取れない点は該当の欄に `【要確認】<質問>` と書き、終わりの報告で親に返す。**親がまとめてユーザーに聞き、答えで埋める**。`【要確認】` が残っていると `check-cases.mjs` が止める
- 実施する時にしか分からない値(採番される ID など)で、ユーザーが「実施する時に記録する」と答えたものだけ、想定の値なしで「実施する時に実測して記録する」と書く

## 書く時の3つの約束

破ると、実施する人が判定できない項目になる。

1. **期待する結果には根拠を持つ** — 期待する結果を1つ書いたら、その値を出しているコードの path:line か、既存のテストの assert を1つ挙げられること(単体は `basis` に書く。結合・受け入れは仕様・画面の実測)。期待する結果は、実装を読んで筋道で導く(例:「自分自身を除いた最大値+1になる」)か、既存のテストの assert をそのまま根拠にする。挙げられないなら**推測で書かず、聞く**。
   (悪い例:「更新で空欄にしない指定のほうが、1セル多い」→ 実装を読むと同じ数だった)
2. **前提が期待する結果を成り立たせるか、件数で確かめる** — 件数が絡む期待する結果(0件/1件/2件、○行目の直後 など)は、前提の件数と操作の行数を並べて数える。
   (悪い例: 既存2件 × ファイル2行 の前提で「削除行の並び位置」を確かめさせていた。全部が更新になり、削除行が出ない)
3. **画面に出ている言葉だけを使う(コードの言葉を書かない)** — `title`・`given`・`steps`・`expect` は実施する人が読む欄。ファイル名・行番号・関数名・変数名・モデル名・内部の ID・HTTP のステータス・SQL は書かない。造語も書かない。画面に出ている言葉と業務の言葉で書き、コードの根拠は単体の `basis` に分ける。エラーメッセージはコードから採った実物を書く。新しい言葉が要るなら、初めて出る所に「(以下〜)」で定義を置く。コマンドの `` `…` `` と、画面の文言の「…」は引用なので書いてよい。`check-cases.mjs` が、機械で判定できる範囲(ファイル名・`関数()`・snake_case・HTTP のステータス・HTML)を止める

## 1つの項目

1つの項目は **確認内容(`title`)→ 前提 → 操作 → 期待する結果 → 優先度** の5点の組(単体は、これに期待する結果の根拠 `basis` が付く)。

- **確認内容(`title`)は必須。**「何が正しいと言えれば合格か」を1文で書く。実施する人が手順を読む前に、この項目の目的が分かるようにする。操作や期待する結果の言い換えにしない(悪い例:「ボタンを押す」「CSV が出る」)。観点の節の名前より具体的に書く(良い例:「更新で空欄にしない指定をしても、新しい行は空欄のまま登録されること」)
- 行わない項目(`duplicateOf`)の `title` は、何と重なるかが分かる程度でよい

## 読みやすく書く

実施する人は、項目を**読みながら操作する**。読みにくい書き方は、操作の迷いと見落としになる。次の11の決まりで書き、書き終えたら各項目をこの11で見直す。

1. **手順は、「確かめる地点」で区切る。** 1つの手順は、次に何かを確かめるまでの操作のまとまり。同じ画面で続く入力や、保存のような決まった操作は、1つの手順にまとめてよい。確かめの無い操作は、次の手順に含める。画面やウィンドウ、タブを移る所は、手順を分ける
2. **期待する結果は、頭に「手順N:」を付けて、その手順を終えた直後に見るものを書く。** 1つの手順に確かめが複数あれば、同じ「手順N:」を繰り返す。確かめの無い手順には、期待する結果を付けない
3. **期待する結果は、1つの要素に1つの確かめ。** 画面に出る文言・数値・状態をそのまま書き、「〜になる」で終える。理由や補足の括弧は書かない(理由は `basis` または準備に置く)
4. **準備と本編を分ける。** 項目の中で準備が要る時は、項目の頭にまとめて「準備:」と明示して区切る。手順の途中に「ここからが本編」のような文を挟まない
5. **呼び名は、1人(1つ)に1つに揃える。** 画面に出る書き方で呼ぶ。社員番号などの番号は、行を探す最初の1回だけ書く。役割の名前(利用者A など)と氏名を混ぜない
6. **同じ動作は、同じ言葉で書く。**「保存する」のように繰り返す操作は、1つの決まった形を、節の `notes` に1回だけ書き、以降は短く書く
7. **「〜なら」の分かれ道を手順に書かない。** 分かれる時は、前提(`given`)で状態を決めるか、項目を分ける
8. **長いコマンドは、手順の文に混ぜない**(下の「コマンドの書き方」)
9. **前提(`given`)は2行以内。** 繰り返す説明(画面の言葉、状態の説明)は、節の `notes` に1回だけ書く
10. **id や中の呼び名(`tc02-01`・`setup-01`・`cleanup-01`)を、文の中に埋め込まない。** 要る時は、「前の項目で〜にした」のように状態で書く
11. **1つの項目に、確かめる地点は1つだけ。** 期待する結果の「手順N:」が2つ以上の手順に付くなら、「操作→結果」の1組ごとに項目を分ける。入力の値だけを変えて同じ操作を繰り返す変わり種(日数に「e」「-」「0」を順に入れる、など)も、状態を積み上げていく流れ(依頼→定期の処理→差し戻し→定期の処理、など)も対象。同じ確かめる地点に期待する結果が複数あるのはよい。
    逆に、**1つの操作で複数の観点を確かめられる時は、1つの項目にまとめ、期待する結果を並べる**(同じ操作や同じ画面の表示を、観点ごとに別の項目で繰り返さない。元の項目が別々なら、片方に `duplicateOf` を付けて外し、残す側に期待する結果と要件を足す。コマンドを含む項目は、正本の統合した項目にできない。実施を始めたあとは、項目をまとめない。エビデンスと合わなくなる)。2回目を行うこと自体が確かめになる操作(同じ日付での再実行など)は、別の項目のままにする。
    分けた2つ目以降の前提は「前の項目の続き(同じ画面・状態のまま)」とし、項目をまたぐ参照は「前の項目で出た〜」のように状態で書く(1つの項目に操作と期待する結果が複数並ぶと、実施の途中で操作と期待する結果の対応がずれる)

## 期待する結果は具体的な値で書く

「名前が出る」「正しく表示される」「適切に」では判定できない。画面に出る文言・数値・状態をそのまま書く。**直す前の動きと違う時は、直す前の動きも添える**(節の `notes` に `修正前の挙動: …`)。

```
○ アイデア帳_2026-11-03.csv
× 名前を含むファイル名
```

## 前提には、判定のしかたを添える

条件を満たしたかを実施する人が自分で確かめられるようにし、**合否の基準まで書く**。

```
前提: 所属が1件だけの利用者がいる
手順: 「利用者」の画面で、その利用者を開く
期待: 手順1: 「所属」の欄が1行だけ。2行以上なら、前提を満たしていない
```

## 優先度

| 優先度 | 基準 |
|---|---|
| 高(`high`) | 主な場合の確かめ、または自動のテストで確かめられていない項目 |
| 中(`mid`) | 主な場合から派生した、パターンを網羅するための項目 |
| 低(`low`) | 境界の場合 |

- **高と中の境**: 自動のテストを実際に grep して**読み**、その項目を確かめるテストがあるかを確かめる。無ければ高。「たぶんテストされているだろう」で中に落とさない
- **高と低の境**:「飛ばして本番で問題が起きた時、見逃しとして許せるか」で決める。許せないなら高
- 自動のテストで確かめていても、画面の表示・ファイル名・ほかの画面との整合など**手でしか確かめられない要素**が乗っていれば、高のまま残す
- そのような要素が無く、自動のテストと同じ中身を確かめるだけでも、**項目は残し、優先度を低にするだけに留める**。自動のテストの期待する結果そのものが間違っていることや、実施する人の目で見て初めて気づく違和感を拾えないため。省きたい項目は、確かめないこと(`excluded`)に理由つきで書く([perspectives.md](perspectives.md)「確かめないこと」)

```bash
# 例: この項目を確かめるテストが本当に無いかを確かめる
grep -rn "対象の関数名やキーワード" <テストのフォルダ>
```

## コマンドの書き方

`steps` の中で、実施する人がターミナルに貼るコマンドは、**手順の1つの要素に `` `…` `` だけで置く**(ビューアで等幅になる。写して貼るので、文に混ぜない)。

```
× "--field を付けずに docker compose exec -T app sh -lc \"…\" を実行する"
○ ["--field を付けずに、次のコマンドを実行する", "`docker compose exec -T app sh -lc \"…\"`"]
```

- **1つの手順に1コマンド。** 前置きの説明は前の要素に書く
- 枠の中は**そのまま貼って動く1行**にする。`cd` は `&&` でつなぎ、複数行にしない。`<イシュー番号>` のような仮の値を残さず、実際の値を入れる
- `-c "…"` のような引数に、実際の改行の入った複数行のスクリプトを書かない。コピー先で改行が保たれず、1行に潰れて動かなくなることがある(実例あり)。文をすべて `;` で1行につなぐ。繰り返しのあとに続けたい処理(件数の表示など)は、繰り返しの**前**に書く(言語によっては、後ろに書くと繰り返しの中に取り込まれる)
- 長いスクリプトや、`` ` `` を含むコマンドは、ファイルにして `plan.json` の `attachments` で添え、そのファイルを実行する手順にする
- 同じコマンドを何度も使うなら、準備(`setup.json`)に1回だけ書く
- 文の中で `` `…` `` を使うのは、画面の値・入れる文字の引用(`「名前」に `ひとつめ` を入れる`)。こちらはコマンドとは見なさない
- 書いたコマンドを試しに動かしてよいかは、`test-cases/SKILL.md` の「一番大事な決まり」に従う(読み取りだけのものは可、書き込むものは不可)

## 画面ベースの原則

**結合・回帰・受け入れは、原則として画面(実施する人が普段使う画面・出力ファイル)で確かめる。** コマンド・データベース・API・ログでの確かめは、**単体と準備・後始末に置く。**

- 操作は画面の操作(押す・入れる・選ぶ・ダウンロードする)、期待する結果は「画面がどう見えるか」「ダウンロードしたファイルの中身」で書く
- 確かめるためのデータも画面から作る(下の「確かめるためのデータは画面の操作で作る」)。コマンドが要るデータの準備は `setup.json` に寄せ、項目の前提には「準備の〜を済ませている」と状態で書く
- **例外**: 画面の無い変更(コマンドラインの道具・定期的な処理・ライブラリなど)や、画面に出ない値でしか判定できない時だけ、結合・回帰・受け入れの項目にコマンドを書いてよい。その時は `noScreen` に**画面で確かめられない理由**を1文で書く。理由が書けないなら、画面で確かめる形に直す
- `check-cases.mjs` が、結合・回帰・受け入れの手順にコマンドがあるのに `noScreen` が無いものを止める。単体には `noScreen` を付けない

## 準備・後始末

### 準備は必要最小限にする

準備は、実施する人の手間を一番食う(ゴール5)。**準備に置くのは、本当に要るものだけ**にする。書いたあとで「これは準備に要るか」を項目ごとに問い直す(実例: 画面から1回の保存で作れる状態を、専用の準備の項目にして13〜15手順に膨らませていた)。

- **画面だけでは作れない状態、またはコマンドが要る状態**だけを準備に置く(例: 不正な値が残った既存のデータ。仕様の上、画面からは作れない/外のサービスにつながらない状態)。**最初に使う項目の手順で、1回の画面の操作で作れる状態は、準備の項目にせず、その最初の項目の頭に畳む**。以降の項目の `given` は、「実施の順で最初に使う項目で変えてある」と書く
- **準備に置くのは、項目の全体が共有する準備(ログイン、複数の項目が共通で使うデータ)だけ。特定の項目でしか使わない準備は、その項目の手順に書く**(実例:「外のサービスにつながらない状態」は、つながらない時の項目2件だけで使うのに、準備に置くと最初に行って、ほかの項目を妨げる。使う項目の頭で作り、最後の項目で戻す。戻し忘れの保険として、後始末に戻す手順を残してよい)
- **データを直接書き換えるコマンドを準備・後始末に書く時**は、次を守る
  - 実行する先は、**実施する人が画面で使う環境**(画面がつながるサーバー、同じデータベース)にする。書く前に、その環境の件数を読み取りで確かめる(別に起動した環境は、データが空のことがある)
  - 履歴やキャッシュを持つデータは、アプリがふだん使う書き方(アプリのコマンド・保存の処理)で書き換える。表を直接書き換えると、画面に出ないことがある(実例: 履歴を持つデータを直接書き換えたら、画面には元の値のまま出た)。書き換えたあとの確かめも、画面と同じ読み方で読む
  - 書き換えるコマンドには、**元に戻すコマンド、または画面での戻し方**を必ず組にして書く(何度行っても同じ状態に戻る形)
- **アカウントとデータは、既存のものを使い回す。** 新しく作るのは、既存が条件に合わない時だけにする。権限は、その中身(画面を見る権限)まで確かめ、要る画面に入れることを確かめる(実例: 機能が無効になっている所や、承認の画面の権限が無いアカウントは使えない)。パスワードは書かず、「実施する人が控えているもの」とする。使ってよい既存のデータ(書き換えてよい利用者など)は、ユーザーに確かめ、書き換えるものには**元に戻す手順を組にして置く**
- **ログアウトとログインを繰り返す作りにしない。** 同じ人が複数のアカウントを使う時は、ブラウザのウィンドウ(通常とシークレットのウィンドウ)またはブラウザを分け、**最初に1回ログインして、そのまま使い続ける**。二段階の認証があるアカウントは、ログインし直すたびにコードが要るので、とくに避ける。アカウントの切り替えが避けられない項目は、実施の順で1か所にまとめる
- 準備の各項目の頭に「ログインする」を繰り返し書かない。最初の項目でログインし、以降は「ログインが続いていること」の確かめ1行にする
- 項目を削ったら、その `id` を参照している `given`・手順・実施の順の注意・後始末を全部直す(grep で確かめる)

### 確かめるためのデータは画面の操作で作る

データベースを直接書き換える手順は書かない(戻し忘れると、ほかの確かめを巻き込む)。**アプリの画面から専用の利用者・データを作る手順**を書き、後始末は「作ったものを画面から消す」だけで済むようにする。直接の書き換えしか手が無い時に限り、上の「データを直接書き換えるコマンド」の決まりで、戻すコマンドを後始末に必ず組にして置く。

### 準備は「上から順にやってチェックする手順書」にする

実施する人は、準備を**上から順に、1項目ずつ操作して確かめる**。参照用の表や、読むだけの注意に、準備の中身を散らさない。**この手順書は、画面を初めて見る人が、迷わず最後までできる細かさで書く。**

- **1項目=1人、または1つのデータの準備。** 人が6人いれば6項目にする。「同様に」「前と同じ」で省かず、項目ごとに全部の手順を書く(操作の途中で、ほかの項目へ戻らせない)
- 項目の欄: `title`(「〜を用意する」)/ `given`(この項目の前に済んでいる項目。無ければ省く)/ `steps`(操作)/ `expect`(できあがりの確かめ)
- **`steps` には操作だけを書く。** 1つの要素=1つの動作(開く・押す・入れる・選ぶ)。画面に出ている言葉(メニュー名・タブ名・ボタン名・入力の欄の名前・出るメッセージ)をそのまま使う。「適宜」「必要に応じて」と書かない
- **`expect` には、できあがりの確かめを、画面に見えることで書く**(1項目に1〜2行)。操作の言い換えや、理由・仕様の説明は書かない
- 実施する人が決める値(パスワード・受け取れるメールアドレス)は「自分で決める」と書く。値そのものや、実在するアドレスは書かない
- 表を作らない。氏名・ログイン ID・番号は、使う項目の中に書く
- 画面の言葉は、コードや実際の画面から拾う。推測で書かない(拾えなければ `【要確認】`)

```
× title「利用者Bの準備」/ steps「作ってログインできた」
○ title「利用者Bを作る」/ steps ["…でログインする", "…を押す", "…を入れて「追加」を押す"] / expect「招待メールのログイン ID で、自分の画面に入れる」
```

書き終えたら、次の4点を確かめる。

1. `steps` の各要素が、人の動作(開く・押す・入れる・選ぶ)で終わっているか
2. `expect` が、画面に見えることだけで、1項目に1〜2行か
3. 表を作っていないか(要る氏名・ID は、使う項目の中にあるか)
4. 項目を上から順にやるだけで、準備が終わるか(ほかの項目へ戻らずに済むか)
