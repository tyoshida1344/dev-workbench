# フェーズ7: 最終仕様のまとめ

作業フォルダ(`<作業フォルダ>`)の場所と共通の決まりは `design` スキルにある。

## 成果物
`<作業フォルダ>/spec.md`(最終仕様)。`<作業フォルダ>` の直下に置く(`spec/` の中には置かない)。実装の方針・計画(`impl.md`)は、フェーズ9で作る

## ひな形
最終仕様は [templates/spec.md](templates/spec.md) をひな形にして作る。ひな形の `> 書き方:` で始まる引用の説明に従って中身を埋め、関係しない節を消し、説明の引用は最後に消す。詳細仕様の小節は、ひな形の「話題の候補」から、変更に関係するものを選ぶ(機能の種類(画面・計算・通知・バッチ・権限など)に合わせて、足す・削る)。

## 構成
1. 基本仕様 — 概要、対象・条件の要点、設定と画面の要点、変更箇所の一覧(何を新しく作り、何を変え、何を変えないか)。ここだけ読めば全体が分かる細かさにする
2. 詳細仕様 — 基本仕様の中身を掘り下げる。話題ごとに小節(対象と条件、きっかけ、中身、設定と画面、初期設定、実行など)。異常系・心配な点・「未決の仮」も、ここの該当する行に書く。QA.md に残っている項目は、その行に「仮」と書いて載せ、冒頭にも一覧にする
3. スコープ外 — やらないこと・できないことを、理由つきの表にする
4. 適用した観点(design-02 で適用すると判定したものだけ)

冒頭に、状況(仮確定があるか)を書く。最終仕様は、ほかのファイルを参照せず、これ1つで完結させる。画面の変更が大きい時は、画面イメージ(SVG など)を `<作業フォルダ>/images/` に作り、`spec.md` に相対パスで画像として埋め込む(`![一覧の画面](images/list.svg)`)。本文は、動きと決めたことだけを書く。コードの識別子・実装の方法・根拠の `path:line` は書かない(根拠は `search/`、実装の方針は `impl.md` にある。`design` スキルの「文書ごとに、コードの内容をどこまで書くか」)。未確認のことは書かず、QA.md に起こす。

ビューアは HTML を出さない。`<!-- -->` のコメントやタグを書かない(書くと文字のまま出る)。

## 決まり
- 仮確定が1件でも残る間は、実装に入ってよいとしない(`spec.md` の冒頭に「仮確定あり: 実装に入る前に回答が必要」と書く)
- 最終仕様をイシューへコメントとして載せる時は、載せる前にユーザーに確かめる。載せる文面はユーザーに見せる
- 例外(仮確定が残ったまま進める必要がある、など)→ [reference/irregular.md](reference/irregular.md)。あてはまった時に読む

## 完了条件
- [ ] 確定と仮の区別がつく(仮には「仮」と書いてある)
- [ ] 仮が QA.md の未決と一致している
- [ ] 本文にコードの識別子・実装の方法・`path:line` が書かれていない
- [ ] 「未確認」が本文に混じっていない(未確認は QA.md にある)
- [ ] `review-design` で確かめた。見る・触るものの名前・置き場所・権限・既定値・リリース直後の状態が書いてある
- [ ] search/・spec/ の中身と矛盾が無い
- [ ] ひな形の説明(`> 書き方:`)が残っていない
- [ ] 仮が無ければ、QA.md が無い(または空)。最終仕様に QA.md への参照を書いていない
