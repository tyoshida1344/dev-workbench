# 受け入れ項目の作り方

エビデンスで何を確かめるかを決める決まり。撮る前にこの手順で項目を作り、自分で見直して漏れを無くしてから撮る。

仕様を決める時や、テストを書く時も、同じ3つの見方を使う。「どう確かめるか」が言えない仕様は、まだあいまいなところが残っている。

## 3つの見方

項目は、どれも次のどれか1つに入る。`manifest.json` の `sections` もこの3つに分ける(項目が無い節は作らない)。

| 節(`sections[].title`) | 何を確かめるか | どこから拾うか |
|---|---|---|
| 要件 | Issueや仕様に書かれた要件を満たしていること | Issueの本文、決めた仕様 |
| 既存機能への影響 | 変更が、もとからある機能を壊していないこと。特に共通の処理を変えた時 | 差分と、変えた処理(関数・型・設定・スタイル・保存のキーなど)を使っている場所 |
| 設計で追加した仕様 | 要件には無いが、設計や実装の途中で決めた動き | 相談して決めたこと、実装中に決めた細かいこと、レビューで足した直し |

### 要件

1. Issueと仕様を、**1行に1つの要件**になるまで分ける。「AとBができる」は2つにする
2. 要件に番号(R1, R2, …)を振る
3. 要件ごとに1つ以上の項目を作る。次のものは項目を分ける
   - 操作のやり方が複数ある(ボタンとショートカットなど)→ やり方ごと
   - 値に幅がある(上限・下限・空・長い入力など)→ よくある値と端の値
   - 初めの値が決まっている → 開いた直後の値
4. 不具合を直すIssueは、**直す前に起きていたことが起きない**ことを必ず項目にする

### 既存機能への影響

1. 差分から、変えた処理(関数・定数・型・設定・スタイル・保存のキーなど、プロジェクトにあるもの)を書き出す
2. それを**使っている場所を検索で探す**。変えていない機能から使われていれば、そこが影響を受ける
3. 影響を受ける場所ごとに、いつもの操作が今までどおり動く項目を作る。共通の処理を変えた時は、**使っているすべての機能**で1つずつ
4. 動きを狙って変えた時は、変わった後の動きは「要件」か「設計で追加した仕様」で確かめ、ここでは**変わってはいけないところ**だけを確かめる
5. 保存するデータの形を変えた時は、前に保存したデータで開けることを項目にする

### 設計で追加した仕様

要件の文には出てこないので、意識して拾わないと漏れる。

- 相談して決めたこと(数値・置き場所・名前・操作のやり方)
- 実装中に決めた細かいこと(押せない時の見せ方、最小の大きさ、範囲外の値の扱い、エラーの出し方など)
- レビューで足した直し
- 空・上限を超えた入力・対象が無い時などに、どう振る舞うと決めたか

## 項目の書き方

- **1つの項目では1つだけ確かめる。** `title` は「〜すると〜になる」と、期待することまで書く
- **値で確かめる。** 見た目だけで決めず、画面の状態・出力・戻り値・保存された値・ログなどを読んで `checks` に書く。画像や動画は、それを見せるためのもの
- 確かめられなかった項目も消さずに `partial` にし、`note` にわけを書く

## 対応表

項目を作ったら、どこから拾ったかと項目の対応を `00-cases.md` に書き、フォルダに入れて `attachments` に載せる。
ビューアで「何をもとに、何を確かめたか」を追えるようにするため。

```markdown
# 項目の一覧(PR #22)

| 見方 | どこから | 項目 |
|---|---|---|
| 要件 | R1 最終行で Enter を押すと行が足される | 1 |
| 既存機能への影響 | list.js(一覧と検索の両方で使う) | 5, 6 |
| 設計で追加した仕様 | 空白だけの入力は足さない(相談して決めた) | 8 |

## 確かめていないこと
- スマートフォンの画面(手元で動かせないため。項目 7 は partial)
```

## 撮る前の見直し

項目を作り終えたら、次を1つずつ確かめる。満たしていなければ、項目を足すか直してから撮る。

- [ ] すべての要件(R1, R2, …)に、項目が1つ以上ある
- [ ] 操作のやり方・値の幅・初めの値で、項目を分けている
- [ ] 変えた処理を使っている場所をすべて探し、影響を受ける場所ごとに項目がある
- [ ] 共通の処理を変えた時は、使っているすべての機能に項目がある
- [ ] 相談して決めたこと、実装中に決めた細かいこと、レビューで足した直しのすべてに項目がある
- [ ] 空・上限を超えた入力・対象が無い時を、要件ごとに考えた
- [ ] すべての項目で、`checks` に書く値が決まっている
- [ ] 1つの項目で2つ以上を確かめていない。同じことを確かめる項目が重なっていない
- [ ] 確かめられないものは「確かめていないこと」にわけを書いた
