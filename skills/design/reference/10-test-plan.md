# フェーズ10: テストの方針・計画

作業フォルダ(`<作業フォルダ>`)の場所と共通の決まりは [SKILL.md](../SKILL.md)にある。

## 前提
- `acceptance.md` と、`impl.md` の実装方針がある(無ければ、ユーザーに伝える)

## 手順
1. テストの層ごとに、何を確かめるかの方針を、下書きとして `test/NN_<slug>.md` に書く
   - 層の例: 単体(判定・計算の部品)、結合(API・バッチ・画面を通した一連)、手動(実機・画面)、回帰(変えないものが変わっていないか)
   - 各層で、対象・観点・自動か手動か・データの準備・環境
2. 受け入れ基準(AC)を1つずつ、**層・手段(自動 / 手動)・担当・データの準備**に割り当てる(対応表)
3. 変えないものの確認(AC の「変わらないこと」)を、今あるテストで足りるか、新しく要るかを決める
4. **特殊な環境の準備**を決める(ひな形の 1.2)。いつもの環境のままでは、安全に、または同じ形で繰り返して確かめられないものを洗い出す
   - 外に出るもの: メール、チャットへの通知、外部の API、ファイルの出力。既定は、外に出さない。出先が本番と同じ(宛先の上書きが無い、決まった BCC がある、通知先がすべての環境で同じなど)かを、コードで確かめる。遮断を外してよい操作は、限る
   - 日付・時刻: 実際の日を待たずに、どう動かすか。動かせないもの(画面など)は、どう代えるか
   - 検証用のアドレス・アカウント・設定の初めの状態
   - それぞれに、方法・有効にする時期・準備できたことの確かめ方・戻し方を決める
5. テストデータを決める。既存データの実際にありうる状態(未登録・複数・消したものなど)を、どう作るか。本番のデータには触らない
6. **性能を確かめる AC があれば、計る前に指標を立てて、ユーザーと合わせる**(あてはまらなければ「該当なし」)
   - **指標**: 時間を左右する軸(例: 行数・列数・追加か変更か)と、その組み合わせ。目安の時間と、その根拠(例: 打ち切りの 900秒から、通信や実行ごとのばらつきの余裕として 120秒を引いた 780秒)
   - **比べ方**: 修正の前と後で、同じファイル・同じ環境で計る組み合わせ。修正前が打ち切られる見込みなら、それも結果として扱う
   - **実際の運用を想定した限界の動き**: 本番の最大の規模(人数・項目数など)と、軸を両端まで振った組み合わせ(例: 多い行×少ない列、少ない行×多い列、多い行×多い列)。どこまで通るかの目安(「行数から何列まで」「列数から何行まで」)を出すなら、計る点と式(切片が何を表すか)を先に決める
   - 載せ方: PR・イシューに載せる表の形(行・列の見出し)を先に決め、計った値をそのまま埋められるようにする
7. 実機でしか確かめられず、設計の判断に影響するものは、`test.md` に書かず、QA.md に起こす(推奨案つき)。判断に影響しない確認は、手動のテストとして、AC の対応表に載せる
8. 下書きから、決まったことだけを `test.md`(テストの方針・計画)にまとめる(ひな形: [templates/test.md](../templates/test.md))
9. 書き終えたら、設計のレビュー(`design/review/`) で確かめる

## 成果物
- `<作業フォルダ>/test/NN_<slug>.md`(話題ごとに1ファイル。NN は作った順の連番、欠番は使い直さない。slug は英小文字とハイフン)
- `<作業フォルダ>/test.md`(テストの方針・計画)

テストケース(手動のテストの1件ずつの手順と期待する結果)は、`test.md` をもとに `test-cases` スキルで作る(置き場は `<作業フォルダ>/cases/`)。

## 決まり
- 決まったことだけを `test.md` に書く。未確認のことは QA.md に起こす
- 受け入れ基準に無いテストを足さない。足したくなったら QA.md に起こし、`acceptance.md`・`spec.md` を直してから計画に書く
- テストコードを書かない(設計では実装しない)。テスト対象の名前(エンドポイント、画面、バッチ)は書いてよい
- 外に出るもの(メール・チャットへの通知・外部の API など)は、既定で遮断する前提で計画する。遮断を外す操作は、1.2 に書き出したものだけにする。外したら、すぐ戻す手順を計画に入れる
- データを書き換える操作(登録・更新・削除のAPI、計算やバッチの実行、マイグレーションなど)は、設計の間は実行しない(本番・開発のDBには触らない)
- 自動で確かめるものと、手動で確かめるものを、理由つきで分ける

## 完了条件
- [ ] すべての AC が、対応表で、層・手段・担当・データの準備に割り当てられている
- [ ] 「変わらないこと」の確かめ方が決まっている
- [ ] 特殊な環境の準備(外に出るもの、日付、検証用データ)が、方法・時期・確かめ方・戻し方つきで書いてある(あてはまらなければ「該当なし」)
- [ ] 遮断を外してよい操作が、限って書き出されている
- [ ] AC が、動かせない日付・外に出る動きに関わる時、2.1 の対応表に、使う準備が書いてある
- [ ] テストデータ(既存データの実際にありうる状態の作り方)が書いてある
- [ ] 性能の AC がある時、指標(軸・目安とその根拠)、修正前との比べ方、実際の運用を想定した限界の動きの組み合わせと載せ方が書いてあり、ユーザーと合わせてある(あてはまらなければ「該当なし」)
- [ ] `test.md` に、未確認のことが書かれていない(未確認は QA.md)
- [ ] 自動と手動の分け方に理由がある
- [ ] `test.md` にまとめた(ひな形の説明 `> 書き方:` が残っていない)
