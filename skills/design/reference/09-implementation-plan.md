# フェーズ9: 実装の方針・計画

作業フォルダ(`<作業フォルダ>`)の場所と共通の決まりは [SKILL.md](../SKILL.md)にある。

## 前提
- `spec.md` に仮が無く、`acceptance.md` がある(無ければ、ユーザーに伝える)

## 手順
1. 最終仕様を実現するために**手を加える対象**を、関係するリポジトリ(スキルを呼び出したリポジトリと関連リポジトリ。画面・API・インフラなど)のコードを読んで洗い出す(読むだけ)
2. 次の話題ごとに、下書きを `impl/NN_<slug>.md` に書く(変更に関係するものだけ)。**調べたこと・コードの根拠(`repo名:path:line`)・検討の過程は、下書きに書く**
   - **データ構造の変更**: テーブル間の関係(図、1対1 / 1対多、紐づかないもの、ほかから取る列、作る順序)。新しいテーブルは、すべての列(型・長さ・NULL・既定・制約。型は先に決める)と、各列の役割・理由、持たせなかった列とその理由。既存のテーブルは、足す・変える列、制約、今ある行の扱い、なぜ既存に足すのか。値の持ち方・定数の置き場所・将来の広げ方。参照(外部キー)の先が、消された・無効・不正の時の動き。初期データ・マスタの追加(マイグレーション)
   - **手を加える機能**: 修正する対象を、コードの**入口**(ファイルのパスと、クラス・関数・ルート・設定の名前。行番号は書かない)まで特定する。API のエンドポイント(メソッド・パス・入力・出力・権限)、バッチ・定期実行、管理コマンド、画面・部品、管理画面。新しく作るものは、ファイルのパスと、倣う先の既存のものを書く
   - **データの流れ**: どのきっかけで、どのデータを読み、何を通って、どこへ書く・送るか。正常系と失敗した時(表や図にする)
   - **画面の文言**: タブ名・ボタン名・項目名・ラベル・エラーメッセージ・確認・注意書きを先に決める。「既存と同じ」と書くものは、既存の画面・テンプレートを実際に読んで一致を確かめ、読んだ場所を `impl/` に残す(既存の文言を推し量って書かない)。決まっていないものは QA.md に起こす
   - **実装計画**: 作業の分け方のみ(上から順に進められるように並べる)。PRの分け方・リリースの手順・戻し方は、リポジトリの決まりに従い、ここには書かない
3. 手を加える既存の機能(API・処理・画面・管理画面)を、すべて洗い出し、「変更 / 変更なし」に分ける(既存機能への影響)。**洗い出しは、コードを検索して行う**
   - 変える列・制約・モデルは、名前で検索して、参照している箇所をすべて挙げる(API の入出力の定義・ルート・管理画面・管理コマンド・バッチ・ほかの機能・テスト)。検索の結果を `impl/` に残し、1件ずつ「変更 / 変更なし(理由)」を決める
   - 制約・型・既定を変える時は、それに頼っている仕組みの動きが変わらないかを確かめる(例: フレームワークが制約から自動で付ける検証、管理画面の一覧、API の入出力の定義が自動で作る項目)
   - 修正対象の入口に挙げるファイルは、中身を読んで、変更が要るかを決める。名前から推し量って挙げない
   - 本文・設定を順に探すもの(個別 → 全体共通 → 初期値など)は、各段を使うか使わないかを、はっきり書く
4. 下書きから、**決まったことだけ**を、`impl.md` の「実装方針」「実装計画」にまとめる(ひな形: [templates/impl.md](../templates/impl.md))。未確認のことは `impl.md` に書かず、QA.md に起こす(推奨案つき)
5. 書き終えたら、設計のレビュー(`design/review/`) で確かめる

## 成果物
- `<作業フォルダ>/impl/NN_<slug>.md`(話題ごとに1ファイル。NN は作った順の連番、欠番は使い直さない。slug は英小文字とハイフン)
- `<作業フォルダ>/impl.md`(決まったことだけをまとめた、実装の方針・計画。`spec.md` と同じく、ほかのファイルを参照せず1ファイルで完結させる。根拠・未確認は書かない)

## 決まり
- 下書き(`impl/`)には、コードの名前・場所・根拠(クラス、関数、エンドポイント、テーブル、カラム、`path:line`)を書いてよい。`impl.md` には、コードの名前(クラス、関数、エンドポイント、テーブル、カラム)は書いてよいが、根拠の `path:line` は書かない。どちらも、**実装しない**。コードの断片は書かない
- 決めたことと、実装者に任せること(内部の関数名、細かい処理の分け方など)を分けて書く
- 最終仕様に無い動きを足さない。足したくなったら QA.md に起こし、`spec.md` を直してから方針に書く
- 記号(①②③ など)だけで指さず、名前で書く。同じものは、`spec.md` と同じ名前で書く
- 今の仕組み(似た機能の作り)に揃える。揃えない時は理由を書く
- データを書き換える操作(登録・更新・削除のAPI、計算やバッチの実行、マイグレーションなど)は実行しない

## 完了条件
- [ ] データ構造の変更、手を加える機能(入口つき)、データの流れ、既存機能への影響、実装計画(作業の分け方)が書いてある(変更に関係しないものは「該当なし(理由)」)
- [ ] テーブル間の関係(どちらから見て1対いくつか、もう一方から取る列)が読み取れる
- [ ] 新しいテーブルのすべての列と、各列の理由が読み取れる。既存のテーブルの追加・変更と、その理由が読み取れる
- [ ] 参照(外部キー)の先が、消された・無効・不正の時の動きが書いてある
- [ ] 既存機能への影響が、コードの検索で洗い出してある(変更 / 変更なし)。変える列・制約・モデルの参照箇所が、すべて挙がっている。順に探すものは、各段を使うかが書いてある
- [ ] 「既存と同じ」と書いた画面の文言・作りが、既存を読んで確かめてある(根拠は `impl/`)
- [ ] 手を加える機能のすべてに、入口(ファイルのパスと名前)がある。最終仕様のすべての項目が、どれかの変更に結びついている(漏れが無い)
- [ ] 画面の文言が決まっている(決まっていないものは QA.md にある)
- [ ] 実装者に任せること(「実装で決める」)が、決めたことと区別できる
- [ ] `impl.md` には決まったことだけがあり、根拠・未確認が混じっていない(未確認は QA.md、根拠は `impl/`)
- [ ] `impl.md` にまとめた(ひな形の説明 `> 書き方:` が残っていない)
