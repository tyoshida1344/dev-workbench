# 設計の統括(フェーズ1〜10)

このスキルは、設計の進め方と、全フェーズに共通する決まりを持つ。各フェーズのスキル(`design-0N-*`)には、そのフェーズに固有の手順・成果物・完了条件だけを書いている。

## 1. 置き場と読むもの

### 成果物の置き場(作業フォルダ)

成果物は、**開発しているリポジトリにも、dev-workbench にもコミットしない。** 次の作業フォルダに、手元のファイルとして書く。

```
$DEV_WORKBENCH_DOCS/<リポジトリ名>/<イシュー番号>/
```

- `DEV_WORKBENCH_DOCS` は、Google ドライブ パソコン版の同期フォルダの中を指す環境変数。同期がDriveへ上げる。**未設定ならユーザーに聞く**(推し量って作らない)
- `<リポジトリ名>` はイシューのあるリポジトリの名前(`owner/` は付けない)。番号の無いテーマは、英小文字とハイフンの名前を `<イシュー番号>` の代わりにする
- 同じイシューを作り直す時は、元を残して `<イシュー番号>_2` を作る
- DriveのコネクタやAPIでファイルの中身を送らない(大きなファイルで多くのトークンを使う)
- 以下では、このフォルダを `<作業フォルダ>` と書く

### 読むもの

- イシュー: `gh issue view <番号> --comments`。リポジトリは、スキルを呼び出したリポジトリ(cwd)の git remote から決める。分からない時、別のリポジトリのイシューの時は `-R <owner>/<repo>` を付ける。どのリポジトリか分からなければ、ユーザーに聞く
- コード: スキルを呼び出したリポジトリ(cwd)と、そのイシューやPRに出てくる関連リポジトリ。関連リポジトリが手元のどこにあるか分からなければ、ユーザーに聞く
- 既存の仕様の根拠にするのは、各リポジトリの既定のブランチ(`origin/<既定のブランチ>`)。cwd 以外のリポジトリのブランチは切り替えず、`git show` で読む。課題ごとの worktree や作業中のブランチは、まだマージされていない変更を含むので、既存の仕様の根拠にしない
- 各リポジトリの `CLAUDE.md` や `docs/` に、既存の仕様の背景や、守る決まり(実行してはいけない操作など)がある。既存の仕様を書く前に、関係するところを読む

## 2. 進め方

1. イシュー番号と、どのリポジトリかを確かめる。イシューを読む(上の「読むもの」)
2. `<作業フォルダ>` の**ファイルの状況を読んで**、どのフェーズまで進んでいるかを推し量る。決まった判定の方法は無い。次の手がかりを合わせて判断する
   - どのファイルがあるか(`index.md`、`search/`、`spec/`、`QA.md`、`spec.md`、`impl.md`、`impl/`、`images/`、`acceptance.md`、`test.md`、`test/`)
   - 各ファイルの中身が、そのフェーズの完了条件を満たしているか(各スキルの「完了条件」を見る)
   - `QA.md` に未決が残っているか
3. 推し量った結果と根拠を伝え、**「フェーズ X から進めてよいですか」とユーザーに確かめる**。ユーザーが別のフェーズを指定したら、そちらに従う
4. 確かめられたら、そのフェーズのスキルを使って進める。各段の結果は、1つの最終仕様(`spec.md`)にまとめていく
5. フェーズの完了条件をすべて満たすまで、次のフェーズへ進まない。満たしたら、結果を短く伝え、次へ進んでよいか確かめる
6. 設計を見せる時は、ビューアのURLを渡す(下の「3. ビューアで見せる」)
7. 最後のフェーズ(テストの方針・計画 `test.md`)まで終わったら、イシューへの反映をどうするかを、ユーザーに確かめる。テストケースは `test-cases` スキルで作る
8. 会話が圧縮された時は、成果物のファイルを読み直して、今のフェーズを推し量り直す(2〜3 をもう一度行う)

## 3. ビューアで見せる

設計は、dev-workbench の設計のビューアで見る。

```
<サイト>design/?folder=<作業フォルダのDriveのID>
```

- `<サイト>` は `$DEV_WORKBENCH_HOME/skills/config.json` の `site` を読む(URLを決め打ちしない)。`DEV_WORKBENCH_HOME` は dev-workbench を手元に置いた場所。未設定で読めなければ、ユーザーに聞く
- `<作業フォルダのDriveのID>` は、DriveのフォルダのURL `https://drive.google.com/drive/folders/<ID>` の `<ID>`。Driveのコネクタがあれば、それでフォルダを探して調べる(中身は送らない。名前と親フォルダで探し、`<リポジトリ名>/<イシュー番号>` のフォルダであることを確かめる)。コネクタが無い時、見つからない時は、ユーザーにフォルダのURLを聞く
- 同期がDriveへ上げ終わるまで、フォルダや新しいファイルが見えないことがある
- 見せる相手は、`$DEV_WORKBENCH_DOCS` かリポジトリのフォルダの共有設定で決まる。作業フォルダごとに「リンクを知っている全員」の共有を足さない

## 5. フォルダの構成

成果物は `<作業フォルダ>` に置く。

```
<作業フォルダ>/
  index.md        イシューの概要とリンク
  QA.md           今の未決だけ(未決がある間だけ置く。解決したら項目を消し、なくなったらファイルごと消す)
  spec.md         最終仕様(確定した仕様。これ1つで完結させる)
  acceptance.md   受け入れ基準
  impl.md         実装の方針・計画(決まったことだけ。根拠・未確認は書かない)
  test.md         テストの方針・計画(決まったことだけ。未確認は書かない)
  search/         調査(NN_<slug>.md)
  spec/           変更仕様(NN_<slug>.md。最終仕様の下書き)
  impl/           実装の調査・検討の下書き(NN_<slug>.md。コードの根拠を書く。決まったことを impl.md にまとめる)
  test/           テストの検討の下書き(NN_<slug>.md。決まったことを test.md にまとめる)
  images/         画面イメージ(SVG など。spec.md に画像として埋め込む)
  cases/          テストケース(test-cases スキルが作る)
  evidence/       エビデンス(evidence-pack スキルが作る)
```

- 最終仕様 `spec.md`、実装の方針・計画 `impl.md`、テストの方針・計画 `test.md` は、`<作業フォルダ>` の直下に置く(`spec/`・`impl/`・`test/` の中には置かない)。`spec/`・`impl/`・`test/` は、`search/` と同じく話題ごとの下書きを置き、書き終えたら直下のファイルにまとめる
- 連番 NN は作った順。欠番は使い直さない
- slug は英小文字とハイフン

### ビューアで読める書き方

ビューアが読む Markdown の決まりは、dev-workbench の `docs/design-folder.md`(`$DEV_WORKBENCH_HOME/docs/design-folder.md`)。設計を書く時は次を守る。

- **HTMLは書けない**(`<!-- -->` のコメントも、そのまま文字として出る)
- ほかの `.md` へのリンクと画像は、相対パスで書く(`[最終仕様](spec.md)`、`![一覧の画面](images/list.svg)`)。画像は `.png` `.jpg` `.jpeg` `.webp` `.gif` `.svg`
- 使える記法は、見出し(`#`〜`####`)・段落・箇条書き(入れ子も)・番号付き・表・コードブロック・引用・水平線と、行内の強調・斜体・コード・リンク・画像

## 6. 全フェーズ共通の決まり

### 書き方
- 既存の仕様は、実装を読んで確かめた事実だけを書く。コードで確かめられないものは「未確認」と書き、推し量って埋めない。未確認で QA の対象になるものは、QA.md に起こす
- 根拠は `repo名:path:line`(リポジトリの直下からの相対パス)で残す。根拠は、調査・検討の下書き(`search/`・`impl/`)に書く。確定した文書(`spec.md`・`impl.md`・`test.md`・`acceptance.md`)には書かない。根拠には既定のブランチのコードを使う(worktree や作業中のブランチは、マージされていない変更を含むので使わない。例外は各フェーズの reference)
- 「できないこと」「正常系以外の動き」を書き漏らさない(正常系だけの仕様は現場で事故になる)。`search/`・`spec/NN_*.md`・`acceptance.md` では先に書く。最終仕様 `spec.md` は、基本仕様 → 詳細仕様(異常系を含む) → スコープ外 → 適用した観点 の順に書く
- 未確認のことは、確定した文書(`spec.md`・`impl.md`・`test.md`・`acceptance.md`)に書かず、QA.md に起こす(推奨案つき)
- 未決を確定として書かない。推奨案は「仮」と書いて載せ、QA.md に残す。仮が残る間は、実装に入ってよいとしない
- すでに確定したデータや、利用者がすでに受け取った結果(締めたデータ、送った通知、出した帳票など)は変えない。変える場合は、明示的な合意を QA.md に起こす
- 参照は QA.md → search/・spec/ の一方通行。search/・spec/・最終仕様の側から、QA の ID や QA.md を参照しない

### 名前で書く
- 確定した文書(`spec.md`・`impl.md`・`test.md`・`acceptance.md`)では、①②③・A/B などの記号だけで指さず、名前(例: 「差し戻し」「変更手続きの依頼」)で書く。記号や略称(N・Y など)を使う時は、初めに意味を書く
- 同じものは、文書をまたいで同じ名前で書く(画面の名前・機能の名前・用語)

### 文書ごとに、コードの内容をどこまで書くか

| 文書 | コードの名前・場所 | 書く内容 |
|------|--------------------|----------|
| `search/`(既存の仕様の整理) | 書く(根拠として `repo名:path:line`) | 今のコードを読んで分かった、今の動き |
| `spec/NN_*.md`(変更仕様。下書き) | どの機能の話か分かる最小限だけ | 変更後の動き |
| `spec.md`(最終仕様) | 書かない(`impl.md` に書く) | 変更後の動きと、決めたこと |
| `impl/`(実装の調査・検討の下書き) | 書く(根拠の `path:line` も。実装しない。コードの断片は書かない) | 調べたこと、コードの根拠、検討の過程 |
| `impl.md`(実装の方針・計画) | コードの名前(クラス、関数、エンドポイント、テーブル、カラム)と、修正対象の入口(ファイルのパスと、クラス・関数・ルートの名前)は書く。行番号の根拠(`path:line`)は書かない。コードの断片は書かない | 決まったことだけ: データ構造の変更、手を加える機能、データの流れ、画面の文言、作業の分割。実装者が決めることは「実装で決める」と書く |
| `test/`(テストの検討の下書き) | テスト対象の名前は書く。テストコードは書かない | 検討の過程 |
| `test.md`(テストの方針・計画) | テスト対象の名前(エンドポイント、画面、バッチ)は書く。テストコードは書かない | 決まったことだけ: 層・手段・担当・データの準備、受け入れ基準との対応 |
| `acceptance.md`(実装後の確認の条件) | 書かない | 画面・メール・データで確かめられること |

- 「動き」とは、誰に・いつ・何が起きるか、画面・メールで見えること
- コードの名前・場所にあたるもの: クラス名・関数名・カラム名・テーブル名、一意制約・トランザクション・例外処理などの実装の方法、`path:line`
- 例外: 画面・メールに出る言葉や、仕様の用語になっているもの(例: 種類を表す値、メール本文の差し込み `{form_kind}`)は、`spec.md` に書いてよい
- `impl.md` は、項目ごとの表(項目・根拠・部品)にする。実装者が決めること(テーブル名、カラムの形、API の名前など)は「実装で決める」と書き、仕様で固定しない

### 実行してよいこと・いけないこと
- 実装しない。コードとDBは読むだけ
- データを書き換える操作は実行しない(登録・更新・削除のAPI、計算やバッチの実行、マイグレーション、外へ送る処理など)。調べるのは、読み取りの操作とコードを読むことまで。各リポジトリの `CLAUDE.md` に、実行してはいけない操作が書いてあれば従う
- 成果物を開発しているリポジトリにコミットしない。イシューへのコメント・本文の更新は、外への公開にあたるので、ユーザーに確かめてから行う

### 質問の進め方
- 質問(未決の確認)は、1つずつ聞く。選択肢・具体例・推奨案を添えて、詳しく聞く
- ユーザーの提案を、勝手に確定として扱わない。確定してよいかを確かめる
- 決まったことは、先に成果物へ反映してから、QA.md の項目を消す

### 詰め漏れをなくす
- 変更で、利用者・運用者が見る・触る・待つもの(画面、メニュー、設定項目、メール、バッチ、管理画面など)は、すべて書き出し、1つずつ、名前・置き場所・権限・既定値・空の時・OFF の時・失敗した時・やり直した時・リリース直後の状態を、仕様に書く
- 「実装で決める」にしてよいのは、利用者・運用者に見えないもの(テーブル名、カラムの形、内部の関数名など)だけ。名前・置き場所・既定値・文言の方針は、仕様で決める
- フェーズ5とフェーズ7を書き終えたら、`review-design` スキルで、詰め漏れ・成果物どうしの食い違い・書き方の決まりを確かめる。指摘はユーザーに伝え、決める必要のあるものは QA.md に起こす

### 実装からの反映
実装の担当から、実装中に決めた・変えたことの報告を受けたら、次のように分けて成果物に反映する。反映したら、確定した文書(`spec.md`・`impl.md`・`test.md`・`acceptance.md`)に矛盾が残らないようにする。

| 報告の種類 | 反映先 |
|------------|--------|
| 仕様の記述を変えたもの(動きが変わる) | `spec.md`(詳細仕様の該当する行)、`acceptance.md`(該当する条件の直し・追加)。ユーザーに、変えてよいか確かめる |
| 仕様に書かれていなかったことを決めたもの(画面・動き) | `spec.md`(該当する行に追加)、`acceptance.md`(条件を追加) |
| 実装で決めたもの(URL、API、テーブル、判定の細部など。仕様が「実装で決める」とした部分) | `impl.md`(方針)。根拠・調べたことは `impl/` |
| 不具合の修正で、仕様の解釈をはっきりさせたもの | 仕様の文言が変わらなければ `impl.md` に。解釈が要るなら `spec.md` に |
| 確かめて、仕様どおりと分かったもの | `impl/`(確かめた記録)。確定した文書には書かない |
| 未確認のまま残るもの | `QA.md`(推奨案つき) |

- 報告は、写す前に、実装のコード(実装のブランチや worktree。読むだけ)で、報告のとおりかを確かめる。文言は、実装にある文字列を検索して確かめる。確かめられないものは、「未確認」として QA.md に起こす
- 報告にある、決めたことの理由・解釈(例: 「既存に揃える」という方針からの解釈)は、ユーザーに確かめてから仕様に書く
- 同じ内容の報告が重ねて届くことがある。差分だけを反映する

### 各フェーズのスキルの共通の約束
- 各フェーズの「完了条件」は、すべて満たすまで次へ進まない
- 例外のケースは、各スキルの `reference/` に書いてある。読む時機は SKILL.md が示す
