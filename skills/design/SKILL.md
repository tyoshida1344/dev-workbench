# 設計の統括(フェーズ1〜10)

## 振り分け

頼まれたことで、読む手順を選ぶ。

| 頼まれたこと | 読む手順 |
|---|---|
| 設計を進める・続きから・フェーズXをやる | このファイルの「進め方」と、そのフェーズの手順 `design/reference/NN-*.md` |
| 設計をレビューする・詰め漏れを見る | 設計のレビュー([review/SKILL.md](review/SKILL.md))。レビューの共通の進め方と出力の形は `review/SKILL.md` |
| 実装の担当から、実装中に決めた・変えたことの報告を受けた | 実装からの反映([reference/11-feedback-from-impl.md](reference/11-feedback-from-impl.md)) |

このファイルは、設計の進め方と、全フェーズに共通する決まりを持つ。各フェーズの手順(`design/reference/NN-*.md`)には、そのフェーズに固有の手順・調べ方・完了条件・例外のケースだけを書く。何をどの節に書くかは、ひな形(`design/templates/`)の `> 書き方:` が正本。フェーズに入る時に、その手順を読む。

## 1. 作業フォルダと読むもの

作業フォルダとビューアのURLは `docs/workspace.md`(`$DEV_WORKBENCH_HOME/docs/workspace.md`)のとおり。以下この作業フォルダを `<作業フォルダ>` と書く。設計に固有のことは次のとおり。

- 直下の文書は確定したものを置く: `index.md`(イシューの概要とリンク)、`QA.md`(今の未決だけ。未決がある間だけ置き、解決したら項目を消し、なくなったらファイルごと消す)、`spec.md`(最終仕様)、`acceptance.md`(受け入れ基準)、`impl.md`(実装の方針・計画)、`test.md`(テストの方針・計画)
- `search/`(調査)・`spec/`(変更仕様)・`impl/`(実装の調査・検討)・`test/`(テストの検討)は、話題ごとの下書き。書き終えたら、決まったことを直下の文書にまとめる。`spec.md`・`impl.md`・`test.md` は直下に置き、下書きのフォルダの中には置かない
- 設計を見せる時は、設計のビューア(`design/`)で作業フォルダを開くURLを渡す
- 設計の Markdown は `docs/design-folder.md`(`$DEV_WORKBENCH_HOME/docs/design-folder.md`)を守る

### 読むもの
- イシュー: フェーズ1([01-issue-review.md](reference/01-issue-review.md))の読み方で読む
- コード: スキルを呼び出したリポジトリ(cwd)と、そのイシューやPRに出てくる関連リポジトリ。関連リポジトリが手元のどこにあるか分からなければ、ユーザーに聞く
- 既存の仕様の根拠にするのは、各リポジトリの既定のブランチ(`origin/<既定のブランチ>`)。cwd 以外のリポジトリのブランチは切り替えず、`git show` で読む。課題ごとの worktree や作業中のブランチは、まだマージされていない変更を含むので、根拠にしない(あてはまった時はフェーズ4の「例外のケース」)
- 各リポジトリの `CLAUDE.md` や `docs/` に、既存の仕様の背景や、守る決まり(実行してはいけない操作など)がある。既存の仕様を書く前に、関係するところを読む

## 2. 進め方

1. イシュー番号と、どのリポジトリかを確かめる。イシューを読む(上の「読むもの」)
2. `<作業フォルダ>` の**ファイルの状況を読んで**、どのフェーズまで進んでいるかを推し量る。決まった判定の方法は無い。次の手がかりを合わせて判断する
   - どのファイルがあるか(`index.md`、`search/`、`spec/`、`QA.md`、`spec.md`、`impl.md`、`impl/`、`images/`、`acceptance.md`、`test.md`、`test/`)
   - 各ファイルの中身が、そのフェーズの完了条件を満たしているか(各フェーズの手順の「完了条件」を見る)
   - `QA.md` に未決が残っているか
3. 推し量った結果と根拠を伝え、**「フェーズ X から進めてよいですか」とユーザーに確かめる**。ユーザーが別のフェーズを指定したら、そちらに従う
4. 確かめられたら、そのフェーズの手順を読んで進める。各段の結果は、1つの最終仕様(`spec.md`)にまとめていく
5. フェーズの完了条件をすべて満たすまで、次のフェーズへ進まない。満たしたら、結果を短く伝え、次へ進んでよいか確かめる
6. 設計を見せる時は、ビューアのURLを渡す(上の「作業フォルダと読むもの」)
7. 最後のフェーズ(テストの方針・計画 `test.md`)まで終わったら、イシューへの反映をどうするかを、ユーザーに確かめる。テストケースは `test-cases` で作る
   - `issue-handler` から来た時は、どのフェーズまで行うか・イシューへのコメントは `issue-handler/SKILL.md` に従う
8. 会話が圧縮された時は、成果物のファイルを読み直して、今のフェーズを推し量り直す(2〜3 をもう一度行う)

## 4. 全フェーズ共通の決まり

### 書き方
- 既存の仕様は、実装を読んで確かめた事実だけを書く。コードで確かめられないものは「未確認」と書き、推し量って埋めない
- 未確認のことは、確定した文書(`spec.md`・`impl.md`・`test.md`・`acceptance.md`)に書かず、QA.md に起こす(推奨案つき)
- 未決を確定として書かない。推奨案は「仮」と書いて該当する行に載せ、QA.md に残す。仮が残る間は、実装に入ってよいとしない
- 「できないこと」「正常系以外の動き」を書き漏らさない(正常系だけの仕様は現場で事故になる)。`search/`・`spec/`・`acceptance.md` では先に書く
- すでに確定したデータや、利用者がすでに受け取った結果は変えない。扱いは [viewpoints/existing-data.md](reference/viewpoints/existing-data.md)
- `spec.md`・`impl.md`・`test.md` は、ほかの成果物(`search/`・`spec/`・`impl/`・`test/`・`QA.md`)を参照せず、1ファイルで完結させる。参照は QA.md → 下書きの一方通行で、下書きや確定した文書から QA の ID や QA.md を参照しない
- 下書きのファイル名は `NN_<slug>.md`。NN はそのフォルダの中で作った順の連番、slug は英小文字とハイフン。連番(NN・QA の Q01・受け入れ基準の AC01)の欠番は使い直さない
- 画面の変更が大きい時は、画面イメージ(SVG など)を `images/` に作り、`spec.md` に相対パスで埋め込む(`![一覧の画面](images/list.svg)`)

### 名前で書く
- 確定した文書では、①②③・A/B などの記号だけで指さず、名前(例: 「差し戻し」「変更手続きの依頼」)で書く。記号や略称(N・Y など)を使う時は、初めに意味を書く
- 同じものは、文書をまたいで同じ名前で書く(画面の名前・機能の名前・用語)

### 文書ごとに、コードの内容をどこまで書くか

根拠は `repo名:path:line`(リポジトリの直下からの相対パス)で、下の表で「書く」とした所にだけ残す。

| 文書 | 根拠の `path:line` | コードの名前・場所 | 書く内容 |
|------|----|--------------------|----------|
| `search/`(既存の仕様の整理) | 書く | 書く | 今のコードを読んで分かった、今の動き |
| `spec/`(変更仕様。下書き) | 書かない(`search/` にある) | どの機能の話か分かる最小限だけ | 変更後の動き |
| `impl/`(実装の調査・検討の下書き) | 書く | 書く(コードの断片は書かない) | 調べたこと、コードの根拠、検討の過程 |
| `test/`(テストの検討の下書き) | 書く(出先などをコードで確かめた所) | テスト対象の名前は書く。テストコードは書かない | 検討の過程 |
| `QA.md` | 背景に書く | 背景に書いてよい | 質問・選択肢・推奨案 |
| `spec.md`(最終仕様) | 書かない | 書かない(`impl.md` に書く) | 変更後の動きと、決めたこと |
| `impl.md`(実装の方針・計画) | 書かない | コードの名前(クラス、関数、エンドポイント、テーブル、カラム)と、修正対象の入口(ファイルのパスと、クラス・関数・ルートの名前)は書く。コードの断片は書かない | 決まったことだけ。実装者が決めることは「実装で決める」と書く |
| `test.md`(テストの方針・計画) | 書かない | テスト対象の名前(エンドポイント、画面、バッチ)は書く。テストコードは書かない | 決まったことだけ |
| `acceptance.md`(実装後の確認の条件) | 書かない | 書かない | 画面・メール・データで確かめられること |

- 「動き」とは、誰に・いつ・何が起きるか、画面・メールで見えること
- コードの名前・場所にあたるもの: クラス名・関数名・カラム名・テーブル名、一意制約・トランザクション・例外処理などの実装の方法、`path:line`
- 例外: 画面・メールに出る言葉や、仕様の用語になっているもの(例: 種類を表す値、メール本文の差し込み `{form_kind}`)は、`spec.md` に書いてよい

### 実行してよいこと・いけないこと
- 実装しない。コードとDBは読むだけ
- データを書き換える操作は実行しない(登録・更新・削除のAPI、計算やバッチの実行、マイグレーション、外へ送る処理など)。調べるのは、読み取りの操作とコードを読むことまで。各リポジトリの `CLAUDE.md` に、実行してはいけない操作が書いてあれば従う
- イシューへのコメント・本文の更新は、外への公開にあたるので、ユーザーに確かめてから行う

### 質問の進め方
- 質問(未決の確認)は、1つずつ聞く。選択肢・具体例・推奨案を添えて、詳しく聞く
- ユーザーの提案を、勝手に確定として扱わない。確定してよいかを確かめる
- 決まったことは、先に成果物へ反映してから、QA.md の項目を消す

### 詰め漏れをなくす
- 書く時も、詰め漏れの観点([viewpoints/completeness.md](reference/viewpoints/completeness.md))で確かめる

### 各フェーズの共通の約束
- 例外のケースは、各フェーズの手順の末尾の「例外のケース」に書いてある。あてはまった時に読む
- 考慮すべき観点の読み物は `design/reference/viewpoints/`、ひな形は `design/templates/` にある
