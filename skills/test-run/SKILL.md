# テストケースを実施してエビデンスを残す

テストケースは、原則として人が行う(test-cases の一番大事な決まり)。このスキルは、**ユーザーがはっきり「実施して」と頼んだグループ・項目だけ**を、Claude が代わりに行う時の手順。頼まれていない項目は行わない。

- 実施する正本: `<作業フォルダ>/evidence/<YYYY-MM-DD>-<内容>/manifest.json`(作業フォルダは `$DEV_WORKBENCH_DOCS/<リポジトリ名>/<イシュー番号>/`。項目の id は `tc02-01` など、グループは節の見出しの `G05` など)
- 記録の形: `$DEV_WORKBENCH_HOME/docs/evidence-manifest.md`(**書く前に読む**)。結果は、正本の**同じ項目**に `result`・`checks`・`video` か `image`・`note` を足す。ファイルは同じフォルダに平らに置く
- 撮り方のこつ: `$DEV_WORKBENCH_HOME/skills/evidence-pack/reference/capture.md`(**撮る前に読む**)
- 結果のある正本は、開発しているリポジトリにコミットしない(作業フォルダは Drive の同期フォルダの中にあり、同期で上がる)
- `DEV_WORKBENCH_DOCS` / `DEV_WORKBENCH_HOME` が空なら、止めてユーザーに場所を聞く

## 守ること

- **本番や共有の環境では行わない。** 行うのは、ユーザーが指定した手元や確かめ用の環境だけ。データを書き換える手順は、項目に書かれたものだけを、その環境で行う。手順に無い書き換え・設定の変更はしない
- **ケースを勝手に直さない。** 正本の `title`・`given`・`steps`・`expect` は変えない(下の「ケースの不備を見つけたら」)
- **結果をよく見せない。** 期待どおりでなかった項目(`ng` / `partial`)も、撮ったものも消さない。`checks` には実際に画面に出た値を書く

## 行えない項目(未実施のまま、ユーザーに任せる)

次は Claude が行わない。その項目は `result` を付けず(未実施のまま)、`note` に「実施できない: <わけ>。<ユーザーにしてほしいこと>」と書く。

- パスワードを入れてログインする(どのアカウントでも)。ログインは、Claude が開いたブラウザのウィンドウで、ユーザーにしてもらう
- 別のアカウントでの確かめのために、今のブラウザのログインを切り替える必要がある(例: 権限の無いアカウントで管理の画面を開く)
- ユーザーの受信箱を読む(テストで送ったメールの中身の確かめなど)。送るまでは行い、受け取った中身の確かめだけを任せる
- 実機・チャットの本番のチャンネル・外のサービスの画面など、手元のブラウザとターミナルで再現できないもの
- ユーザーに飛ばすよう言われた項目は、`note` に「飛ばした: <わけ>」と書く(未実施のまま)

## 始める前に

1. **対象を決める**: どのグループ・項目かを、正本から一覧にする(`title`・`given`・`steps`・`expect`)。飛ばす項目がユーザーから指示されていれば、上の「飛ばした」にする。正本が今の下書きと合っているかを `node "$DEV_WORKBENCH_HOME/skills/test-cases/scripts/check-cases.mjs" <作業フォルダ> --manifest <正本のフォルダ>` で確かめる
2. **前提を確かめる**(読み取りだけ):
   - グループの前提(`given`・全体の `notes` にあるグループの注意)が、今のデータ・画面の状態で成り立つか。設定の値・データの状態は、画面か読み取りのコマンドで確かめる
   - 前提と食い違っていたら、**直す前にユーザーに伝えて指示を仰ぐ**(実例: 設定の日数が 14 のはずが 5 だった)。勝手にデータや設定を変えない
   - 確かめる日付で結果が変わるグループなら、ケースが前提にしている日付と今日がずれていないかを見て、ずれていれば伝える
   - 確かめるコミットを控える(`git rev-parse --short HEAD`。環境に出ているものが違えば、そちら)
3. **画面を操作する手立てを用意する**: プロジェクトにあるもの(Playwright の MCP、ブラウザを操作するツール、プロジェクトの E2E の仕組みなど)を使う。どれを使うかプロジェクトで決まっていなければ、ユーザーに聞く。ユーザーのふだんのブラウザ(ログイン済みのもの)は、ユーザーが指示した時だけ使う
   - ログインの画面になったら、そのウィンドウでのログインをユーザーに頼んで待つ(`AskUserQuestion` で「ログインした」を待つ)。アカウントを切り替える時は、Claude がログアウトまで行ってから頼む
   - ログインはふつう**オリジン(ホスト名とポート)ごと**に保たれる(例: 修正前 `localhost:8080` と修正後 `localhost:8083` は別々にログインできる)。同じオリジンでは1つのアカウントだけなので、利用者と管理者を行き来する項目は、切り替えが少なくなるよう、結果に影響しない範囲で順をまとめる(まとめたことを全体の `notes` に書く)
4. **画面の大きさを揃える**: 撮る前に、capture.md の決まりで画面の大きさと倍率を揃える(例: 1280×720)

## 行う

項目ごとに、`steps` の手順どおりに操作し、`expect` と照らす。

- **操作**: 押す・入れるは、画面の部品を名前や役割(アクセシビリティのツリー・参照の番号)で特定してから行う(座標で押さない)。入力は、画面の仕組みが反応する入力の出来事が出る手立てで行う
- **確認のダイアログ・アラート**: 出たら、手立ての機能で閉じる。文言は結果に出るので、そのまま期待する結果と照らす(ページの `alert` / `confirm` を書き換えない)。閉じられない時は、次の「画面が止まった時」に従う
- **画面が止まった時**: ログインのほかに、ダイアログの操作も Claude ではできないことがある。次の時は、同じ操作を繰り返さず、そこで止めてユーザーに確かめを頼む
  - 止まったとみなす時: 操作が時間切れ・エラーで返る、ダイアログを閉じられない、操作のあと画面が変わらない
  - 頼み方: `AskUserQuestion` で、どの項目の・どの操作で止まったか、今ウィンドウに何が出ているか(分かる範囲で)、ユーザーにしてほしいこと(例:「確認のダイアログの OK を押してください」)を伝え、「操作した」「この項目は実施できないにする」を選んでもらう。ダイアログの文言が期待する結果に関わるなら、文言も教えてもらう
  - 続ける: 「操作した」なら画面を確かめてから続ける。ユーザーが操作したこと(と教えてもらった文言)を、その項目の `note` に書く
- **判定**: 期待する結果の文言・数値を、画面の要素・出力・保存された値から**機械的に取り出して**照らす(見た目の印象で決めない)。照らした具体的な値を `checks` に書く
- **詳しい画面の開き方**: 一覧から行を探して開くのが手順どおり。アドレスを直接開いた時は、`note` に書く
- **ブラウザの「戻る」**: 自動の操作では効かないことがある。同じ画面のアドレスを開き直して代える。代えたことを全体の `notes` に書く
- **ターミナルの手順**: 手順のコマンドをそのまま、1つずつ実行する(開いたままの対話の画面は使わない)。出力は `<id>-<内容>.txt` に保存し、`attachments` に `{ "title": "<id> <何の出力か>", "file": "<id>-<内容>.txt" }` で載せる(添付の `title` は項目の id で始める。再テストで、やり直す項目の添付を見分けるため)
- **項目の後始末**: 手順にある後始末(名前を戻す、作ったものを消す、など)は必ず行う。テストの送信など、外に出る操作は、手順にあるものだけ

## 期待する結果の外の問題を洗い出す

判定のほかに、行っている途中で気づいた問題を洗い出して、記録する。
記録する先は、作業フォルダの `QA.md`(未決)、またはプロジェクトで決まった所。
判定が `ok` の項目にも、表示の崩れ・文言の揃っていないところ・承認する側に出ない欄などが隠れていることがある(実例: 総合テストで、ok の項目から 10 件以上を記録し、うち 8 件が直すことに決まった)。

- **期待する結果の外も見る**: 項目の判定とは別に、同じ画面のほかの欄、幅を変えた時の見え方、エラーの出方を見る。
  幅は 375・800・1280px などに変えて確かめる。
  見た目の問題は、位置・幅を測って数値で書く。
- **周りに広げる**: 同じ部品・同じ共通の文言・同じ条件を使うほかの画面やタブでも起きるかを見る。
  そこまでを影響の範囲として添える。
- **前からあるかを確かめる**: 本番に出ているコード(本番のブランチやタグ)か、本番の画面(読み取りだけ)で、同じことが起きるかを確かめる。
  - 画面で確かめたのか、コードだけで確かめたのかを分けて書く。
  - 確かめていない範囲も書く。
  - コードだけで「前からある」と言い切らない(実例: コードを読んで前からあると書いたが、前からではなかった)。
- **記録の書き方**: 次の節で書く。
  - 【事象】【条件】【原因(コード)】【前からあるか】【相談したいこと】【エビデンス】
  - 期待する結果を満たしているかどうかも書く。
  - 満たしていても、優先度が低くても、記録する。
- **エビデンス**: 項目のエビデンスとは別に、`obs-<内容>.png` として撮り、`attachments` に `{ "title": "QA: <内容>", "file": "obs-<内容>.png" }` で載せる。
  本番での見え方を撮ったものは、ファイル名に `-prod` を付ける。
- **結論は書かない**: 直すかどうかは、ユーザーが決める。
  判断の材料(影響・前からあるか・直す時に広がる範囲)だけを書く。

## エビデンスを撮る

- **1つの項目に、画像か動画のどちらか1つ**(`manifest.json` の決まり)。期待する結果を確かめた画面を撮る。1つの項目で複数の画面を開く時は、動画で通して撮るか、期待する結果を判定した最後の画面を項目の `image` にし、途中の画面を `attachments` に `{ "title": "<id> <何の画面か>" }` で添える
- **ファイル名**は `<id>-<内容>.<拡張子>`(例: `tc02-01-saved.png`、`tc05-03-approve.webm`)。英小文字・数字・ハイフンにし、フォルダは平らにする(サブフォルダを作らない)
- **画像と動画を使い分ける**(evidence-pack の決まりと同じ)
  - **一連の動作を確かめる項目は、動画で撮る**。画面の操作から結果まで(条件を選んでダウンロードし、中身を見る/申請して承認する、など)。画像を並べるだけでは、何をしてその結果になったかが伝わらない
  - **準備・データの状態の証跡は、画像(またはコマンドの出力のテキスト)でよい**。登録した設定、計算した値、データの状態など。1つの画面の表示だけで判定できる項目も画像にする
- **動画の撮り方**: capture.md に従う。何の確かめかが分かる印(画面の隅に項目の id と `title`、どの値を期待する結果と照らすか)を残し、読み終わるまで出しておく
  - ログインの間は撮らない(パスワードが映らないよう、ログインを済ませてから始める)
  - 画面が切り替わるのを待つ時間は長めにとる(実例: 読み込みの途中で絞り込みを入れて効かず、撮り直した)。印を出す前に、見せたい状態になっているかを確かめる
  - 撮ったあとは場面ごとにコマを見て、印・値が写っているかを確かめる
- **ダウンロードしたファイルの中身**は、ファイルそのものを `attachments` に添える(テキストとして開ける形式なら)。画面で見せる必要があれば、中身を表にしたページを手元のサーバー(`http://127.0.0.1:<ポート>`)で開いて撮る(`file:` を開けない手立てがある)。撮っている間に落としたファイルが、添えたファイルと同じ中身であることを確かめる
- **保存する先**: 手立てによっては、決まった場所(出力用のフォルダなど)にしか保存できない。その時は、その場所に保存してから正本のフォルダに写す
- **落ち着いてから撮る**: ダイアログの開け閉め・画面の読み込みのあとは、結果が出たことを待ってから撮る(実例: 開く途中の半透明のダイアログが撮れた)
- **同じ中身は1つのファイル**: 同じ画面を複数の項目で使う時は、1つのファイルを複数の項目に書く。同じ中身を別の名前で写さない
- 撮れない・撮らない項目(コマンドの確かめだけ、など)は、出力のテキストを `attachments` に添え、項目の `checks` に出力の要点を書く

## 記録する

正本の `manifest.json` に、`docs/evidence-manifest.md` の形で書き足す。項目の中身(`title`・`given`・`steps`・`expect`・`basis` など)は変えない。

- 項目ごとに:

  | 結果 | 書くこと |
  |---|---|
  | 期待する結果をすべて満たした | `"result": "ok"`、`checks` に照らした値(`○ 一覧の1行目: ひとつめ`)、`image` か `video` |
  | 1つでも満たさない | `"result": "ng"`、`checks` の該当の行を `×` にして実際の値を書く、`note` に、どの期待する結果がどう違ったか |
  | 一部だけ確かめられた | `"result": "partial"`、確かめられなかった行を `△` にし、`note` にわけを書く |
  | 行えない・飛ばした | `result` を書かない。`note` に「実施できない: …」「飛ばした: …」 |

- 全体に:
  - `recordedAt` に行った日(`YYYY-MM-DD`)、`source.commit` に確かめたコミット
  - `notes` に、行った回のことを1行で足す: `実施 <日付>(<誰が: Claude(手立て)>、<環境: 手元 localhost:3000 など>、<アカウント>、<グループ>): <補足>`。日を分けて行った時は、回ごとに1行。グループごとにコミットが違えば、どの項目をどのコミットで確かめたかも書く
  - `summary` を、`result` を書いた項目だけで数え直す(`ok` / `partial` / `ng`。未実施は数えない)
- **確かめた力が弱い合格は、`note` に書いて報告する**(実例:「初めの設定に戻す」の前と後で名前が同じだったため、戻ったかどうかを見分けられない)。直し方(手順を足すなど)を提案し、ユーザーが了承したら、[test-retest](../test-retest/SKILL.md) で直してから行い直す
- 書いたら確かめる:

```
node "$DEV_WORKBENCH_HOME/skills/evidence-pack/scripts/check-manifest.mjs" <正本のフォルダ>
node "$DEV_WORKBENCH_HOME/skills/test-cases/scripts/check-cases.mjs" <作業フォルダ> --manifest <正本のフォルダ>
```

1つ目はファイル名の綴り・拡張子・`summary` の数・使っていないファイル、2つ目は項目の中身を変えていないかを見る。エラーが出たら直す。

## ケースの不備を見つけたら

- 行っている途中で、手順・期待する結果・前提の誤りに気づいたら、**ケースは勝手に直さず**、伝えて直し方を提案する。その項目は `partial` か未実施にし、`note` に不備を書く
- 直す時は [test-retest](../test-retest/SKILL.md) の手順で行う(下書きを直し、新しい日付のフォルダに、結果を引き継いで作り直す)。項目の id は変えない。足す項目は、下書きの節の末尾に新しい番号で足す
- 項目をまとめる(行わない項目にする)時も、ユーザーに伝えてから行う

## 終わったら

1. 開いたタブ・ウィンドウを閉じる
2. ユーザーに報告する: 項目ごとの結果の表(ok・partial・ng・実施できない・飛ばした)、記録した QA(前からあるか)、ユーザーにしてほしいこと(実施できない項目)、確かめた力が弱い項目、ケースの不備、戻した・変えたデータ
3. ビューアのURLを渡す。`$DEV_WORKBENCH_HOME/skills/config.json` の `site` を読み、`<site>evidence/?folder=<正本のフォルダの Drive の ID>` を作る。ID は、Drive のコネクタがあればフォルダの名前で探して取り(中身は読まない)、無ければユーザーにフォルダのURLを聞く。件数を1行で添える(`全24項目(✓20 / !2 / ✕0 / 未実施 2)`)
