# テストケースのレビュー

読む時: 作ったテストケース(作業フォルダの cases/ の下書き、またはそれから作った manifest.json)に漏れが無いかを、 差分・要件・設計と突き合わせてレビューするスキル。差分の全行・要件・観点の出どころ・狭い幅・回帰・技法の漏れ、 期待する結果や前提の質、テストケースのゴール5つを確かめ、指摘を重要度つきで返す。読むだけで、直さない。 「テストケースをレビューして」「ケースに漏れが無いか見て」と頼まれた時、test-cases スキルの手順で 項目を書いて重なりを整理したあとに使う(サブエージェント test-cases-review が、このスキルの手順で行う)。

項目の書き手とは別の目で、「差分・要件に対して、項目に漏れが無いか」を確かめる。**ファイルは書き換えない**(`git diff` / `git log` / `git show` / `grep` / `gh ... view` / `check-cases.mjs` など読み取りだけ。状態を変えるコマンド、項目の手順に書かれたコマンドは実行しない)。指摘を返すのが仕事で、直すのは `test-cases` スキル。
共通の進め方(見る範囲・重要度・出力の形)は `review` スキル。

## 入力

- 作業フォルダの `cases/` のパス(`plan.json` と種別ごとの下書き。あれば `order.json`)
- 対象のリポジトリのパスと差分の範囲
- イシューの要件(`plan.json` の `requirements` と、元のイシューの文)、作業フォルダの設計(spec.md・acceptance.md・test.md。あれば)

パスは絶対パスで読む(サブエージェントとして呼ばれた時は、親が渡したもの)。先に `<DEV_WORKBENCH_HOME>/skills/test-cases/SKILL.md` と `<DEV_WORKBENCH_HOME>/skills/test-cases/reference/format.md` を読む。`check-cases.mjs` が見る機械的な整合(id の重なり・行き先の無い参照・要件と項目の対応の有無)は確かめ済みなので扱わない。**意味の漏れ**を見る。

## 見るもの(漏れ)

1. **差分の全行**: 通して読み、どの項目の操作でも通らない分岐・途中で抜けるところ・繰り返しの 0/1/複数件・例外・境界の値を並べる。対応する項目が無い行は漏れ(単体)
2. **要件**: 各要件の項目が、要件を満たしたかを**本当に判定できるか**を見る(あるかどうかだけでなく中身。期待する結果が要件の文とずれていないか)
3. **観点の出どころ**(`test-cases` スキルの SKILL.md 2節の表): 入力の欄・データの状態・権限・状態の移り変わり・新しく作る時/既存を読み込む時・外とのやりとり・画面の外の入力と出力(CSV など)・設計で決めたこと のうち、差分に当てはまるのに項目が無いもの
4. **狭い幅の表示**: 差分に画面の見た目・文言の変更(ラベル・メッセージ・列・ボタン・並べ方)があるのに、変更した画面の狭い幅(375px など)の項目が無いものは漏れ(P1)。狭い幅では使わないとユーザーが答えて、`plan.json` の `excluded` に理由が書かれているものは漏れではない
5. **回帰**: 変更したファイル・関数の呼び出し元・共有先を grep し、回帰の項目の無いほかの画面・ほかの用途を挙げる
6. **技法**: 値に範囲があるのに境界の値が無い、条件が複数あるのに組み合わせが抜けている(デシジョンテーブル)
7. **確かめないことの誤用**: `excluded` に**差分に含まれるもの**が入っていないか。「自動のテストで確かめている」だけを理由に、確かめないことにした・消した項目が無いか

## 見るもの(質)

- `【要確認】` が残っていないか。想定の値で埋めた期待する結果(「実測して記録(想定: …)」など)が無いか。確認内容(`title`)・前提・操作・期待する結果にコードの言葉(ファイル名・関数名・変数名・モデル名)が無いか(根拠は単体の `basis` に分ける)
- 期待する結果が具体的な値か。根拠(path:line か既存のテストの assert)を挙げられるか。「名前が出る」のような判定できない期待する結果
- 前提の件数と操作の行数が、期待する結果を成り立たせるか(例: 既存2件 × ファイル2行で「削除行」を期待していないか)
- 画面に無い言葉(モデル名・変数名・内部の ID・HTTP のステータス)を使っていないか
- 確かめるためのデータを、データベースの直接の書き換えで作っていないか(戻すコマンドと組か)
- 優先度が、それを確かめる自動のテストの grep に基づいているか(grep して確かめる)
- 結合の項目が、コードの言葉で書かれていないか(種別の取り違え)
- `duplicateOf` が、本当に同じ操作・同じ期待する結果か(残す側が、行わない側の `expect` を1つずつ含むか)
- 条件で振る舞いが分かれる変更で、変わる側の確かめそれぞれに、対になる「今までどおり」の確かめがあるか

## 見るもの(ゴール)

`test-cases` スキルの SKILL.md 冒頭の「ゴール」の5つを、**それぞれ「満たしている/満たしていない」と根拠**で答える。

1. **要件**: すべての要件に、要件を満たしたかを判定できる、行う受け入れの項目があるか
2. **イシューに書かれていない仕様**: 差分に含まれる分岐・共通の範囲・実際のデータの形・今までどおりの動き・設計で決めたことのうち、項目の無いものが無いか。イシューに無い動きの期待する結果に、根拠(コード・既存の動き)があるか。受け入れに、イシューと設計に書かれていない要件を作っていないか
3. **自動のテストで確かめられていない動き**: 確かめられていない動き(画面の流れ、実際のデータ、外のサービス、画面にだけ出る文言)に、項目があるか(漏れ)。自動のテストが確かめているだけの項目が高い優先度になっていないか(grep して確かめる。優先度の指摘であり、**確かめられていることを理由に、項目を消すことは求めない**)
4. **迷わず判定できるか**: 初めて見る人が、聞き返さずに最後まで行って判定できるか(`【要確認】`、判定できない言葉、画面に無い言葉、具体的な値の有無)
5. **むだ**: 重なり・上位で賄える項目が、行う項目のまま残っていないか。準備に、項目の最初の手順で作れる状態の準備(省ける項目)や、使われていない項目が残っていないか。ログアウトとログインを繰り返す手順が無いか。アカウント・データを新しく作らず既存を使えるのに、作る手順になっていないか

**項目を増やす指摘は、要件が判定できない、または誤った期待する結果で誤って合格になる、といった重いものに限る**(絞り込みの方針を壊さないため)。それ以外の「あるとよい」は P3 にする。

## 出力

`review` スキルの出力の形で返す。観点は **漏れ / 質 / ゴール**。項目を書き換えず、**足す・直す案**までにする。

| 重要度 | このレビューでの意味 |
|---|---|
| P1 | 漏れ。項目を足すのが必須(差分の通らない分岐、対応する要件を判定できない、回帰の抜け) |
| P2 | 質。期待する結果・前提・優先度の誤りで、実施する人が判定できない/誤って合格になる |
| P3 | よりよくする。書き方の揺れなど |

```
### テストケースのレビューの結果

**漏れ**
- [ ] P1 `差分の path:line` — 通る項目が無い分岐(足す案: 種別・前提・操作・期待する結果)

**質**
- [ ] P2 `tc02-01` — 期待する結果が判定できない(直す案)

**ゴール**
- 要件: 満たしている/満たしていない — 根拠
- イシューに書かれていない仕様: ...
- 自動のテストで確かめられていない動き: ...
- 迷わず判定できるか: ...
- むだ: ...

**見た範囲**: <cases/ のファイル、差分の範囲、読んだ設計>
**問題の無かった観点**: <「見るもの」の各項目について、何を調べ、問題が無かったか>
```

- 場所は、項目の id・節、または差分の path:line。何が足りないか、足す・直す案を1〜3行で書く
- 調べていない項目を「問題なし」と言わない。**P1 が1件も無い時だけ**「漏れなし」と言う

## サブエージェントとして呼ばれた時

- `check-cases.mjs` は実行できないことがある。実行できなければ、報告に「未実行」と書く(実行できたふりをしない)
- コードや差分を読む時は、親が渡した作業ツリーとコミットの範囲を使う(`git -C <作業ツリー> diff <範囲>`)。手元のチェックアウトが別のブランチのことがある
- PR の本文やイシューのコメントなどの外の文書は、親がプロンプトに貼ったものを使う(自分で取れないことがある)
- 事実(実際のデータの名前、画面の言葉、権限の名前)は、親が渡した事実のシートと、決まった `setup.json` に従う
