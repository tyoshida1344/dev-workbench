# テストケースの形(下書きと manifest.json)

テストケースは、エビデンスビューアが読む `manifest.json` に、`result` の無い(未実施の)項目として書く。
`manifest.json` の形そのものは dev-workbench の `docs/evidence-manifest.md`(`$DEV_WORKBENCH_HOME/docs/evidence-manifest.md`)が正本。
ここには、テストケースを作る時の下書きの形と、書く時の決まりを書く。

## 置き場

作業フォルダ(`$DEV_WORKBENCH_DOCS/<リポジトリ名>/<イシュー番号>/`)の中に置く。開発しているリポジトリにはコミットしない。

```
<作業フォルダ>/
  cases/                          下書き(証跡)。種別ごとに並行して書くので、ファイルを分ける
    plan.json                     見出し・出どころ・要件・全体の注意・確かめないこと・添付(親が書く)
    setup.json                    準備(kind: setup)
    unit.json                     単体(kind: unit)
    integration.json              結合(kind: integration)
    regression.json               回帰(kind: regression)
    acceptance.json               受け入れ(kind: acceptance)
    cleanup.json                  後始末(kind: cleanup)
    order.json                    実施の順(手で書く。無ければ種別の順に並ぶ)
    00-cases.md                   どこから拾ったかと項目の対応表(plan.json の attachments で正本に添える)
    manifest.json                 証跡を見るための生成物(build-manifest.mjs --trail)
  evidence/
    <YYYY-MM-DD>-<内容>/          1回のテスト
      manifest.json               正本(build-manifest.mjs --out)。テストを行うと結果と動画・画像が足される
```

- 種別のファイルは、項目の無い種別なら作らない(`plan.json` の `notes` に「単体: 該当なし(理由)」と残す)
- 雛形は [../templates/cases/](../templates/cases/)。フォルダごと写して使う
- `cases/` の中の下書きは、「なぜこの項目が無いか」を追える**証跡**。正本を作ったあとも消さない

## plan.json

| 項目 | 必須 | 中身 |
|---|---|---|
| `title` | ○ | ビューアの見出し。短い名詞句(例: `#123 一覧の並び替え`) |
| `source` | | `repository` / `pullRequest` / `commit` / `url`(`docs/evidence-manifest.md` と同じ)。イシューだけの時は `url` にイシューのURLを書く |
| `notes` | | 全体にかかる注意(配列)。変更の概要と確かめる条件を1〜2文、項目が無い種別の理由など。正本の `notes` の先頭に出る |
| `requirements` | 受け入れがあれば○ | 要件(`{ "id": "R1", "text": "…" }` の配列)。イシューと設計(spec.md・acceptance.md)に書かれたものだけ |
| `excluded` | | 確かめないこと(`{ "title", "reason" }` の配列)。**差分に含まれていないものだけ**。正本の `notes` に「確かめないこと: …」として出る |
| `attachments` | | 正本に添えるファイル(`{ "title", "file" }`)。`file` は `cases/` に置き、正本を作る時に evidence のフォルダへ写される |

## 種別ごとの下書き(`cases/<kind>.json`)

```json
{
  "sections": [
    {
      "id": "tc02",
      "title": "TC-02 主な症状の確認",
      "kind": "integration",
      "notes": ["何を見れば合否を判定できるか", "修正前の挙動: ○○になる"],
      "items": [
        {
          "id": "tc02-01",
          "title": "保存した名前が一覧に出ること",
          "priority": "high",
          "given": "一覧に1件ある",
          "steps": ["1行目の「名前」に `ひとつめ` を入れる", "「保存」を押す"],
          "expect": ["手順2: 一覧の1行目: `ひとつめ`", "手順2: トースト: `保存しました`"]
        }
      ]
    }
  ]
}
```

### 節(`sections[]`)

| 項目 | 必須 | 中身 |
|---|---|---|
| `id` | ○ | 英数字とハイフン(`tc02`、`setup`)。項目の `id` の頭になる。**ファイルをまたいで重ねない** |
| `title` | ○ | 観点が一目で分かる名前。テストの節は `TC-02 主な症状の確認` のように番号を頭に付ける |
| `kind` | ○ | ファイル名と同じ(`setup` / `unit` / `integration` / `regression` / `acceptance` / `cleanup`) |
| `notes` | | 節の説明(配列)。何を見れば合否を判定できるか、修正前の挙動(`修正前の挙動: …` と書く)など。正本では全体の `notes` に「節の title: …」として出る |
| `items` | ○ | 項目 |

### 項目(`items[]`)

| 項目 | 中身 |
|---|---|
| `id` | 節の `id` を頭にした番号(`tc02-01`、`setup-01`)。**ファイルをまたいで重ねない。決めたあとは変えない**(エビデンスのファイル名・再テストの対応に使う)。足す時は末尾に足す |
| `title` | **何を確かめる項目か**(確認内容)。1文。「何が正しいと言えれば合格か」を業務の言葉で書く(例:「休日の時間が、法定休日と所定休日で分かれて集計されること」)。操作や期待する結果の言い換えにしない。準備・後始末では「〜を用意する」「〜を元に戻した」 |
| `given` | 前提。満たしていないと結果が変わる状態。文字列で2行まで |
| `steps` | 操作の手順(文字列の配列。ビューアが番号を振る)。1つなら文字列でもよい |
| `expect` | 期待する結果(文字列の配列。確認することごとに分ける)。操作すれば必ずこうなる値。手順の後に見るものは頭に `手順N:` を付ける。準備・後始末では、できあがりの確認を1〜2行 |
| `basis` | 期待する結果の根拠(単体は必須、単体だけに付ける)。コードの `path:line` か、既存のテストの assert。**コードの言葉はここにだけ書ける** |
| `priority` | `high` / `mid` / `low`(テストの項目は必須) |
| `requirement` | 満たす要件の `id`(`R1`、または `["R1", "R2"]`)。**受け入れは必須、ほかの種別には付けない** |
| `noScreen` | 画面で確かめられない理由(結合・回帰・受け入れだけ)。手順にコマンドを置くなら必須(下の「画面ベースの原則」)。正本では `note` に「画面で確かめられない理由: …」として出る |
| `duplicateOf` | ほかの項目で確かめられるので行わない時、その項目の `id`。証跡では打ち消し線で出て、正本には入らない。行う側は、**階層が同じか上で、自身が `duplicateOf` を持たない項目**(SKILL.md 5節) |

- 下書きには `result`・`checks`・`video`・`image` を書かない(結果は正本に書く)
- HTML は書けない(ビューアは文字としてそのまま出す)。強調や改行が要るなら、文や配列の要素に分ける
- 表を作りたくなったら、項目ごとに書くか、`notes` の1行ずつに分ける(参照用の表に準備の中身を散らさない)

## 書く時の3つの約束

破ると、実施する人が判定できない項目になる。

1. **期待する結果には根拠を持つ** — 期待する結果を1つ書いたら、その値を出しているコードの path:line か、既存のテストの assert を1つ挙げられること(単体は `basis` に書く。結合・受け入れは仕様・画面の実測)。挙げられないなら**推測で書かず、ユーザーに聞く**(下の「分からないことは聞く」)。
   (悪い例:「更新で空欄にしない指定のほうが、1セル多い」→ 実装を読むと同じ数だった)
2. **前提が期待する結果を成り立たせるか、件数で確かめる** — 件数が絡む期待する結果(0件/1件/2件、○行目の直後 など)は、前提の件数と操作の行数を並べて数える。
   (悪い例: 既存2件 × ファイル2行 の前提で「削除行の並び位置」を確かめさせていた。全部が更新になり、削除行が出ない)
3. **画面に出ている言葉だけを使う(コードの言葉を書かない)** — `title`・`given`・`steps`・`expect` に、ファイル名・行番号・関数名・変数名・モデル名・内部の ID・HTTP のステータス・SQL は書かない。造語も書かない。コードの根拠は `basis` に分ける。エラーメッセージはコードから採った実物を書く。期待する結果は「画面がどう見えるか」で書く。新しい言葉が要るなら、初めて出る所に「(以下〜)」で定義を置く。

## 分からないことは聞く

**推測で埋めない。** 仕様・期待する結果・前提・画面の名前・手順など、読み取れない点があれば、ユーザーに**その都度聞く**(`AskUserQuestion`。選択肢と推奨があれば添える)。「実測して記録(想定: …)」のように、想定の値で埋めて先へ進めない。

- 実施する時にしか分からない値(採番される ID など)で、ユーザーが「実施する時に記録する」と答えたものだけ、想定の値なしで「実施する時に実測して記録する」と書く
- サブエージェントはユーザーに聞けない。分からないことは該当の欄に `【要確認】<質問>` と書いて、終わりの報告で親に返す。**親が聞いて埋める。** `【要確認】` が残っていると `check-cases.mjs` が止める

## コマンドの書き方

`steps` の中で、実施する人がターミナルに貼るコマンドは、**手順の1つの要素に `` `…` `` だけで置く**(ビューアで等幅になる)。

- **1つの手順に1コマンド。** 前置きの説明は前の要素に書く(`["次のコマンドを実行する", "`…`"]`)
- 枠の中は**そのまま貼って動く1行**にする。`cd` は `&&` でつなぎ、複数行にしない。プレースホルダ(`<イシュー番号>` など)を残さず、実際の値を入れる
- `-c "…"` のような引数に、複数行のスクリプトを埋め込まない。コピー先で改行が保たれず、1行に潰れて動かなくなることがある(実例あり)。文を `;` で1行につなぐか、スクリプトのファイルにして `attachments` に添え、そのファイルを実行する手順にする
- 同じコマンドを何度も使うなら、準備(`setup.json`)に1回だけ書く
- `` ` `` を含むコマンドは `` `…` `` で囲めない。ファイルにして添える
- 文の中で `` `…` `` を使うのは、画面の値・入れる文字の引用(`「名前」に `ひとつめ` を入れる`)。こちらはコマンドとは見なさない

## 画面ベースの原則

**結合・回帰・受け入れは、原則として画面(実施する人が普段使う画面・出力ファイル)で確かめる。** コマンド・データベース・API・ログでの確かめは、**単体と準備・後始末に置く。**

- 操作は画面の操作(押す・入れる・選ぶ・ダウンロードする)、期待する結果は「画面がどう見えるか」「ダウンロードしたファイルの中身」で書く
- 確かめるためのデータも画面から作る(SKILL.md 4節「確かめるためのデータは画面の操作で作る」)。コマンドが要るデータの準備は `setup.json` に寄せ、項目の前提には「準備の手順N を済ませている」と書く
- **例外**: 画面の無い変更(コマンドラインの道具・定期的な処理・ライブラリなど)や、画面に出ない値でしか判定できない時だけ、結合・回帰・受け入れの項目にコマンドを書いてよい。その時は `noScreen` に**画面で確かめられない理由**を1文で書く。理由が書けないなら、画面で確かめる形に直す
- `check-cases.mjs` が、結合・回帰・受け入れの手順にコマンドがあるのに `noScreen` が無いものを止める。単体には `noScreen` を付けない

## 実施の順(`cases/order.json`)

行う項目(`duplicateOf` を持たないもの)を、グループに分けて実施の順に並べる。準備と後始末は書かない(正本の最初と最後に自動で並ぶ)。

```json
{
  "groups": [
    {
      "id": "g01",
      "title": "一覧を見るだけの確かめ",
      "who": "閲覧だけのアカウント",
      "note": "続けて行う理由・始める前の注意を、画面の言葉で1〜3文",
      "cases": [
        "tc03-01",
        {
          "merge": ["tc02-01", "tc04-01"],
          "key": "save-name",
          "title": "保存した名前が一覧に出て、R1 を満たすこと",
          "given": "一覧に1件ある",
          "steps": ["1行目の「名前」に `ひとつめ` を入れる", "「保存」を押す"],
          "expect": ["手順2: 一覧の1行目: `ひとつめ`", "手順2: トースト: `保存しました`"]
        }
      ]
    },
    {
      "id": "g09",
      "title": "後始末のあとに確かめること",
      "afterCleanup": true,
      "cases": ["tc05-01"]
    }
  ]
}
```

| 項目 | 必須 | 中身 |
|---|---|---|
| `groups[].id` | ○ | 英数字とハイフン(`g01`)。正本の節の見出しの頭に大文字で出る(`G01 …`) |
| `groups[].title` | ○ | グループの名前 |
| `groups[].who` | | 使うアカウント・環境。見出しの後ろに `(…)` で出る |
| `groups[].note` | | 連続して行う理由・実施前の注意。正本では全体の `notes` に「見出し: …」として出る |
| `groups[].afterCleanup` | | `true` なら後始末のあとに並ぶ。`order.json` でも、ふつうのグループより後ろに置く |
| `groups[].cases[]` | ○ | 項目の `id` の文字列か、統合した項目 |

統合した項目(同じ人が同じ画面を続けて確かめられる項目を1つにまとめたもの):

| 項目 | 必須 | 中身 |
|---|---|---|
| `merge` | ○ | まとめる元の項目の `id`(1つ以上) |
| `title`・`steps`・`expect` | ○ | 書き方は下書きと同じ。**元の項目の確かめ(`expect`)を1つも落とさない** |
| `given`・`priority` | | `priority` を省くと、元の項目のうち一番高いもの |
| `id` | | 正本での `id`。省くと元の `id` を `+` でつないだもの(`tc02-01+tc04-01`) |
| `key` | | 英数字とハイフン。`order.json` の中で重ねない。後ろの統合した項目の本文から `@key` で指すと、その項目の `id` に置き換わる(「@save-name の続き」→「tc02-01+tc04-01 の続き」)。自分自身や後ろの項目は指せない |

- 行う項目は、**文字列か、1つ以上の統合した項目のどちらかに**入れる。文字列で2回書く・文字列と統合の両方に書く・1つの `merge` の中で重ねる・行わない項目を入れる、のはどれも止まる
- 元の項目が複数のアカウントにまたがる時は、アカウントごとの統合した項目に分け、同じ元の項目を複数の `merge` に入れてよい。元の確かめは、どれか1つの統合した項目に必ず書く
- 統合した項目の `requirement` は元の項目の和、`basis` は `元のid: 根拠` を並べたもの、`note` は「まとめた項目: …」になる

## 正本と証跡を作る

```
node "$DEV_WORKBENCH_HOME/skills/test-cases/scripts/check-cases.mjs" <作業フォルダ>
node "$DEV_WORKBENCH_HOME/skills/test-cases/scripts/build-manifest.mjs" <作業フォルダ> --trail --out <作業フォルダ>/evidence/<YYYY-MM-DD>-<内容>
node "$DEV_WORKBENCH_HOME/skills/test-run/scripts/check-manifest.mjs" <作業フォルダ>/evidence/<YYYY-MM-DD>-<内容>
```

| 作るもの | 中身 |
|---|---|
| 正本(`--out <フォルダ>`) | 準備 → `order.json` のグループの順(無ければ 単体 → 結合 → 回帰 → 受け入れ の節の順)→ 後始末 → `afterCleanup` のグループ。`duplicateOf` の付いた項目は入らない。項目の `id` は下書きのまま(統合した項目だけ新しい `id`)。本文の中の、行わない項目・統合した項目の `id` は、行う項目の `id` に書き換わる |
| 証跡(`--trail`) | 下書きの全件を種別の順に並べ、`duplicateOf` の付いた項目も打ち消し線で残したもの。`cases/manifest.json` に書く。ビューアで `cases/` のフォルダを開くと見られる(重なりの判断をレビューする時に使う) |

- 正本のフォルダに結果のある `manifest.json` があると、上書きしない(テストの結果を消さないため)。やり直しは [やり直し(`test-run/retest/`)](../../test-run/retest/SKILL.md) の手順で、新しいフォルダに作る
- 下書きを直したら、正本を作り直す(結果がまだ無い時)。`check-cases.mjs <作業フォルダ> --manifest <正本のフォルダ>` が、正本が今の下書きと合っているかを見る
- 種別ごとに並行して書いている間は、`check-cases.mjs <作業フォルダ> --file <cases/unit.json のパス>` で自分のファイルだけを見る(`--file` にはファイルの**パス**を渡す)

`check-cases.mjs` が見るもの: 形(`sections`・`kind` とファイル名・id の頭)・必須の欄・`priority` の値・コードの言葉と HTML・`【要確認】`・単体の `basis`・画面ベースの原則(`noScreen`)・要件ごとに受け入れの項目があるか・id の重なり・`duplicateOf` の先があり、行う項目で、階層が同じか上か・`order.json` の漏れと重なり・統合した項目の書き方と `@key`・正本が組み立てられ、要件をすべて確かめているか。
`manifest.json` の形そのもの(ファイル名・`summary` の数など)は `check-manifest.mjs` が見る。
