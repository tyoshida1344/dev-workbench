# テストケースを作る

## 振り分け

頼まれたことで、読む手順を選ぶ。

| 頼まれたこと | 読む手順 |
|---|---|
| テストケースを作る・作り直す・観点を洗い出す | このファイル |
| 作ったテストケースをレビューする・漏れを見る | [review/SKILL.md](review/SKILL.md)(テストケースのレビュー。ケースを作る流れの中では、サブエージェント `test-cases-review` がこの手順で行う) |
| 作ったケースを行う・やり直す | `test-run` スキル |

手順の場所は、このスキルのフォルダ(`$DEV_WORKBENCH_HOME/skills/<スキル>/`)からの相対。ほかのスキルの手順は `$DEV_WORKBENCH_HOME/skills/` からの相対(`review/impl/` など)で書く。

変更の差分からテストケースを導き、作業フォルダに**下書き**(種別ごとの JSON)を書き、
エビデンスビューアが読む **`manifest.json`**(`result` の無い、未実施の項目)にまとめて渡すまでを行う。
形は [reference/format.md](reference/format.md)(**書く前に必ず読む**)。`manifest.json` の正本は `$DEV_WORKBENCH_HOME/docs/evidence-manifest.md`。
専用の画面は作らない。HTML・CSS・JavaScript は書かない。

**「手で行うテスト」を行うのは人(ユーザー)であり、Claude ではない。** これは一番大事な決まりで、親・サブエージェントともに必ず守る。

- Claude(親・サブエージェントとも)は、準備・テストの項目・後始末に書いた**コマンドを自分で実行しない**(コンテナの中のコマンド・データの作成/削除/更新を伴うコマンド・画面の操作など、`steps` に書く中身すべてが対象)。これらはユーザーがあとで自分の手で行って結果を確かめるためのもので、Claude が先回りして実行すると、ユーザーがまだ確かめていないのに環境の状態だけが変わってしまう(ほかの確かめの作業を巻き込んで壊す事故にもつながる)
- Claude がケースを作る時にしてよい確かめは、**コードを読む**(差分・実装・既存のテスト)、**形の整合を見る**(`check-cases.mjs`)、**期待する結果の根拠を、既存のコード・テストから拾う**ところまで。「このコマンドが本当に動くか手元で試す」という理由での実行はしない
- 期待する結果は、実装を読んで筋道で導く(例:「自分自身を除いた最大値+1になる」)か、既存の自動のテストの assert をそのまま根拠にする。実際に動かして確かめた数値ではない
- 実装を読むだけでは言い切れない値(コマンドの出力の正確な文言など)は、**推測で埋めずユーザーに聞く**(下の「分からないことは聞く」)。実施する時にしか分からない値だとユーザーが答えたものだけ、想定の値なしで「実施する時に実測して記録する」と書く
- 実行してよいのは、`check-cases.mjs`・`build-manifest.mjs`(作業フォルダにだけ書く)と、`git diff` / `git log` / `gh issue view` / `grep` など、**対象のリポジトリにも環境にも書き込まない、読み取りだけの調べもの**だけ
- **本番や共有の環境のデータを書き換える操作はしない。** 調べるのは読み取りだけ(画面を開く・一覧を取る・データベースを SELECT する、など)。保存・計算の実行・作成/更新/削除のリクエストは、試しでも行わない。本番の環境には、ユーザーが指示した時だけ、読み取りでつなぐ

- 雛形: [templates/cases/](templates/cases/)(フォルダごと写して使う)
- 形と書き方: [reference/format.md](reference/format.md)
- サブエージェント: `$DEV_WORKBENCH_HOME/skills/test-cases/agents/test-cases-{unit,integration,regression,acceptance,review}.md`
- 受け入れ項目の作り方(3つの見方・観点の出どころ・撮る前の見直し): `$DEV_WORKBENCH_HOME/skills/test-cases/reference/acceptance-items.md`。このスキルは、その考え方を、人が行うテストの4つの種別に広げたもの

## ゴール(ケースが満たすこと)

テストケースを作るゴールは、**ケースが次の5つを満たしていること**。ケースを書く・整理する・レビューする時の判断の基準にする。迷ったら、そのケース(や手順)が5つのどれに効くかで決め、どれにも効かないものは足さない。

| # | ゴール | 満たすための手立て(該当する節) |
|---|---|---|
| 1 | **イシューの要件を満たしていることを確かめられる** | 要件を `plan.json` の `requirements` に書き出し、1つの要件に1つ以上の受け入れの項目を置く(2節)。すべての要件を指す、行う受け入れの項目が残っているかは `check-cases.mjs` が見る |
| 2 | **イシューに書かれていない仕様の動きを確かめられる** | イシューに書かれていない動き(差分から見える分岐、共通の処理のほかの用途、実際のデータの形、副作用、変わらない側の今までどおりの動き、設計で決めたこと)を、単体・結合・回帰の観点として拾う(2節「観点の出どころ」「観点の漏れを防ぐ」)。**受け入れの要件は、イシューと設計に書かれたものだけ**で、書かれていない動きは受け入れではなく単体・結合・回帰に置く。要件に無い動きの期待する結果も、根拠(コード・既存の動き・仕様)を持つ |
| 3 | **自動のテストで確かめられていない動きを確かめられる** | 自動のテストを grep して**実際に読み**、その項目を確かめるテストがあるかで優先度を決める(4節「優先度をつける」)。**確かめられていない動き(画面の流れ、実際のデータ、外のサービスとのつながり、画面にだけ出る文言)には、必ず項目を置き、優先度を高にする**。確かめられている動きも外さず、項目は残して優先度を下げる(自動のテストと両方で確かめる)。単体の `basis` に既存のテストの有無を残す |
| 4 | **実施する人が、操作や期待する結果の判定に迷わず進められる** | 画面の言葉だけで書く(「テストの言葉で書く」)。手順は確かめる地点で区切り、期待する結果は具体的な値と画面に見えることにする。前提は状態で書く。`【要確認】` と「適切に」「正しく」のような判定できない言葉を残さない。実施する時にしか決まらない値だけ「実施する時に実測して記録する」と書く |
| 5 | **実施する人が、むだなく進められる**(品質を保ちつつ手間を抑える) | 重なりと、上位で賄える項目を行わない項目にする(5節)。実施の順に並べた正本を作る(7節)。準備は必要最小限にする(4-0「準備は必要最小限に」)。項目は、ゴール1〜3に効くものだけに絞る。既存のアカウント・データを使い回し、ログアウトとログインの繰り返しを避ける |

**ゴールの見直し(できあがる前に必ず行う)**: 6節のレビューと7-4の報告で、次の問いに答える。1つでも「いいえ」なら直す。

1. すべての要件に、行う受け入れの項目があるか(ゴール1)
2. 差分に含まれる分岐・共通の範囲・実際のデータの形・今までどおりの動き・設計で決めたことのうち、項目の無いものが無いか。イシューに書かれていない動きの期待する結果に、根拠があるか(ゴール2)
3. 自動のテストが確かめているだけの項目が、高い優先度で残っていないか。確かめられていない動きで、項目の無いものが無いか(ゴール3)
4. 項目を、初めて見る人が、聞き返さずに最後まで行って判定できるか(`【要確認】` が無い、画面の言葉、具体的な値)(ゴール4)
5. 準備・項目・実施の順に、省ける手順(同じ状態を作り直す、ログアウトの繰り返し、使わない準備)が残っていないか(ゴール5)

## 分からないことは聞く

**推測で埋めない。** 仕様・要件・期待する結果・前提・画面の名前・メニューの並び・イシュー番号など、差分やイシューから読み取れない点は、**その都度ユーザーに聞く**。`AskUserQuestion` で、選択肢と推奨を添えて聞く(1回に4問まで。同じ種類の疑問はまとめる)。

- 聞いてから書く。想定の値や「たぶん〜」で埋めて、あとで直す進め方にしない
- サブエージェントはユーザーに聞けない。読み取れない点は該当の欄に `【要確認】<質問>` と書き、終わりの報告で親に返させる。**親がまとめてユーザーに聞き、答えで埋める**
- `【要確認】` が残っていると `check-cases.mjs` が止まる

## テストの言葉で書く(コードの言葉を書かない)

`title`(確認内容)・`given`(前提)・`steps`(操作)・`expect`(期待する結果)は、**テストを行う人が読む欄**。ファイル名・行番号・関数名・変数名・モデル名・内部の ID・HTTP のステータス・SQL を書かない。画面に出ている言葉と業務の言葉で書く([reference/format.md](reference/format.md)「書く時の3つの約束」)。コードの根拠(path:line・既存のテストの assert)は、単体の項目の **`basis`** に分けて書く。コマンドの `` `…` `` と、画面の文言の「…」は引用なので書いてよい。`check-cases.mjs` が機械で判定できる範囲(ファイル名・`関数()`・snake_case・HTTP のステータス・HTML)を止める。

## 場所(どのリポジトリから呼んでも動かすために)

3つの場所を分ける。

| 場所 | 何に使う |
|---|---|
| **対象のリポジトリ**(cwd) | `git diff`・`gh`、コードの grep・調べもの。**何も書き込まない**(テストケースもコミットしない) |
| **作業フォルダ**(`$DEV_WORKBENCH_DOCS/<リポジトリ名>/<イシュー番号>/`) | 設計(spec.md・acceptance.md・test.md)を読む。下書き(`cases/`)と正本(`evidence/<YYYY-MM-DD>-<内容>/manifest.json`)を書く |
| **dev-workbench**(`$DEV_WORKBENCH_HOME`) | このスキルのスクリプト・雛形・サブエージェント、`skills/config.json`(サイトのURL)、`docs/evidence-manifest.md` |

- **最初に** `echo "$DEV_WORKBENCH_DOCS"` と `echo "$DEV_WORKBENCH_HOME"` で絶対パスを取る。どちらかが空なら**止めて**、ユーザーに場所を聞く(推測で別の場所に書かない)。作業フォルダの決まりは `$DEV_WORKBENCH_HOME/docs/workspace.md`
- `<リポジトリ名>` は `gh repo view --json name -q .name`(使えなければ `git rev-parse --show-toplevel` のフォルダ名)
- 以降のパスは、Read / Write / Agent に**絶対パスに展開して**渡す(環境変数は展開されない)
- cwd の外に書き込むので、作業フォルダを書き込みの許可に入れておく(`additionalDirectories` か `--add-dir`)
- サブエージェントは `~/.claude/agents/` に `$DEV_WORKBENCH_HOME/skills/test-cases/agents/test-cases-*.md` を置いて(リンクして)使う。見つからなければ、そのファイルの中身をプロンプトに写して汎用のサブエージェントに渡す

## 全体の流れ

1. 差分・イシュー・設計を読み、骨格を用意する
2. テストの観点を洗い出す(単体・結合・回帰・受け入れの4つの種別ごと)。イシューの要件も洗い出す
3. 観点ごとに節を作る(親が節の骨格と id まで決める)
4. **先に準備・後始末と事実のシートを決め(4-0)**、そのうえで種別ごとにサブエージェントを**並行に**起動し、項目を書かせる
5. 全ファイルを見て、重なった項目を行わない項目にする。**上位のテスト(結合・回帰・受け入れ)で賄えている下位のテスト(単体・結合)も、同じく行わない項目にする**(親が行う)
6. レビューのエージェントに漏れを見てもらい、指摘を直す(親が行う)
7. 行わない項目を除き、実施の順に並べ直した**正本(`manifest.json`)**を、作業フォルダの `evidence/<YYYY-MM-DD>-<内容>/` に作る(親が行う)
8. ビューアのURLを渡す

## 時間を抑える進め方(書き直しの往復をなくす)

作るのに時間がかかるわけは、**あとから前提・事実が変わって、全ファイルを書き直すこと**。次の3つを、項目を書かせる前に済ませる。

1. **使える既存のアカウント・データを、先に読み取りで調べる。** 準備でアカウントやデータを新しく作る前に、権限の中身(入れる画面)、機能の有効・無効の設定、使われていないデータを調べる。パスワードの有無はユーザーに聞く(準備には書かない)。調べずに準備を書くと、あとから作り直して、準備を前提にする全項目を直すことになる
2. **事実のシートを、実測で先に固める**(4-0)。外のサービスの名前、区分・方法などの値の定義、権限、画面の言葉は、コードや読み取りの調べもので確かめた値だけを渡す。推測のまま渡すと、4つのファイルすべてに誤りが広がり、一括で置き換えることになる。**準備や項目に書くコマンドは、実施する人が画面で使う環境(画面がつながるサーバー、同じデータベース)を指しているか**を、動いているプロセス・コンテナの一覧とデータの件数の読み取りで確かめてから書く(実例: 作業用に別に起動した環境を指していて、画面で作ったデータが「0件」になった)
3. **項目が少ない時(目安: 行う項目が30件前後以下、または変更が1〜2か所)は、種別ごとにサブエージェントを分けず、1人(または親)が全部書く。** 並行にすると、番号・準備の参照・事実の食い違いを合わせる手間のほうが重くなる

## 1. 差分・イシュー・設計を読み、骨格を用意する

**推測で書かない。** 必ず差分と実装を読んでから書く。

```bash
git diff --name-only <基点>...HEAD
git diff <基点>...HEAD
gh pr view <番号> --json title,body,baseRefName,headRefOid,url   # PR がある時。gh pr diff <番号> でも差分を取れる
gh issue view <イシュー番号> --comments
```

- 作業フォルダに設計(`spec.md` 最終仕様・`acceptance.md` 受け入れ基準・`test.md` テストの方針)があれば読む。決まった仕様と受け入れ基準は要件の出どころに、テストの方針(範囲・環境・確かめないこと)は2節以降の前提にする
- **イシュー番号**は、ユーザーの指示・ブランチ名・PR(`gh pr view --json closingIssuesReferences`)・イシューのURLから取る。**分からなければ推測せず、ユーザーに聞く**
- 作業フォルダは `$DEV_WORKBENCH_DOCS/<リポジトリ名>/<イシュー番号>/`。**同じイシューのケースを作り直す時(再テストに絞る・仕様が変わって作り直す、など)だけ**、元を残したまま `<イシュー番号>_<連番>`(例: `123_2`)を作る(元は書き換えない)。作り直しの範囲(イシュー全体か、特定の変更だけの再テストか)は、推測せずユーザーに確かめ、再テストなら、対象のコミットの範囲と、要件をその変更で動きが変わる点に絞ったものを `plan.json` に書く。結果を残したまま一部の項目だけやり直すなら、作り直さず [やり直し(`test-run/retest/`)](../test-run/retest/SKILL.md) を使う

[templates/cases/](templates/cases/) を `<作業フォルダ>/cases/` に写す(すでにあれば上書きしない)。`plan.json` には次を仮に置く。

- `title`(イシュー番号と内容が分かる短い名前)/ `source`(リポジトリ・PR・コミット・URL)
- `notes`(変更の概要と確かめる条件。2節で埋める)
- `requirements`(イシューの要件。2節で埋める)
- `excluded`(確かめないこと。中身は2節で埋める)

`setup.json` / `cleanup.json` は親が書く。項目の無い種別のファイルは消す。**この時点では観点ごとの節(TC-01 など)はまだ作らない。**

## 2. テストの観点を洗い出す

**節を作る前に、まず観点だけを箇条書きで並べる。** 先に節を作ると、思いついた順の切れ切れの観点しか出てこない。

### テストの種別

| 種別(`kind`) | 何を確かめるか | 導き方 |
|---|---|---|
| **単体(ホワイトボックス)** `unit` | 変更した関数・部品の中の分岐が意図どおりか | **コードを読んで**導く。分岐・途中で抜けるところ・繰り返しの 0件/1件/複数件・境界の値・例外を1つずつ拾い、各分岐を通す入力を画面の操作に落とす。期待する結果の根拠は path:line(`basis` に書く) |
| **結合(ブラックボックス)** `integration` | 画面の操作から最後の出力(画面・CSV・ファイル・ほかの画面)まで、仕様どおりにつながるか | **実装を見ずに**、仕様と使う人の操作から導く。入力と出力だけで判定する。期待する結果の根拠は仕様・既存の画面の実測 |
| **回帰(デグレ)** `regression` | 変更前から動いていたものが壊れていないか | 変更した所を**共有するほかの用途・ほかの画面・周りの機能**を洗い、変更前の動きと比べる |
| **受け入れ** `acceptance` | イシューの**要件**を満たしているか | 要件を1つずつ取り出し、**1つの要件に1つ以上の項目**。業務の言葉で、要件が実現されたかを判定する。各項目に `requirement` で要件の id を付ける |

- 同じ画面を見ていても、導き方が違えば別の観点。結合は「流れが正しいか」、受け入れは「頼まれたことが実現されたか」。1つの観点を種別をまたいで混ぜない
- 4つの種別とも考える。観点が1つも出ない種別はファイルを作らず、`plan.json` の `notes` に「単体: 該当なし(理由)」と1文残す。**確かめないこと(`excluded`)にはしない**
- 受け入れ項目の作り方(reference/acceptance-items.md) の3つの見方との対応: 「要件」は受け入れ、「既存機能への影響」は回帰、「設計で追加した仕様」は単体・結合で拾う

### 観点の出どころ

| 観点 | 導き方 | 種別 |
|---|---|---|
| **前提の条件** | 不具合が再現する条件・確かめるためのデータの作り方。**一番大事**。満たさないまま行うと、全項目が誤って合格になる | 準備(`setup`) |
| **主な症状** | 変更で直るはずの動き。変更したファイルすべてを画面に結びつけて並べる | 結合 |
| **狭い幅の表示** | 差分で**画面の見た目・文言(ラベル・メッセージ・列・ボタンなど)が変わる**時。変更した画面を**狭い幅(スマートフォンの幅。例: 375px)**で開き、表示が崩れないか。下の「狭い幅の確認」 | 結合 |
| **境界・分岐** | 値が引けない・0件・権限が無い時の代わりの動き。差分の各分岐 | 単体 |
| **既存機能への影響** | 変更した所がほかの用途にも使われていた時、その用途が壊れていないか | 回帰 |
| **設計で決めたこと** | 要件の文には無いが、設計や実装の途中で決めた動き(相談して決めた数値・文言、押せない時の見せ方、範囲の外の値の扱い、レビューで足した直し)。作業フォルダの spec.md と PR の議論から拾う | 単体・結合 |
| **要件** | イシューと設計(spec.md・acceptance.md)に書かれた要件・受け入れ基準を1件ずつ `requirements` に書き出す(`{ "id": "R1", "text": "…" }`)。**書かれていない要件を作らない。** 要件が無い・あいまいなら、ユーザーに確かめる | 受け入れ |
| **確かめないこと** | **差分に含まれていない**ので確かめなくてよいもの。**書いておかないと、不合格の誤報が出る** | `excluded` |
| **後始末** | 確かめるために変えた環境・データを戻す手順 | 後始末(`cleanup`) |

**「確かめないこと」は、差分に含まれていないものだけに使う。** 自動のテストで確かめられていても、確かめないことにしない。差分に含まれる限り観点として残し、自動のテストの有無は4節の優先度でだけ加減する。根拠にする前に、そのテストのコードを実際に読み、画面のどの操作を行っているかを確かめる(ファイル名や describe だけで「確かめられている」と決めない)。
(悪い例:「入力の画面は E2E のテストで確かめているので確かめない」→ 実際は表示と入力の検査しか見ておらず、ボタンは一度も押していなかった)

### 観点の漏れを防ぐ

次の出どころを、上から順に総なめにする。

| 出どころ | 拾い方 |
|---|---|
| 分岐 | 差分の中の `if` / `else` / `try` / `catch` / 途中の `return`、繰り返しの 0件・1件・複数件。1つの分岐に1つ以上の観点 |
| 入力の欄 | 画面の入力の欄ごとに、必須か任意か・型・桁数・文字の種類・初めの値、境界の値(最小−1/最小/最大/最大+1)、空の入力の変わり種(空、前後の半角/全角の空白だけ、空白+値) |
| データの状態 | 重ねてはいけない値の有無・未登録・複数の所属など、**実際のデータにありうる形**(古い形のまま保存されたデータで壊れないか) |
| 権限 | 役割・権限の組み合わせ |
| 状態の移り変わり | 新規・編集・削除・承認の前後などの状態と、移る前後 |
| 新しく作る時/既存を読み込む時 | 同じ画面の部品でも、「新しく足す」時と「既存のデータを読み込む」時で、作られる道筋が違うことがある。両方を実際に通す |
| 外とのやりとり | ほかの画面・ほかの定期的な処理・API など、別に更新されうるものとの整合 |
| 画面・文言の変更 | 画面の見た目や文言が変わる差分があれば、変更した画面ごとに狭い幅の項目を作る(上の表の「狭い幅の表示」) |
| 条件で振る舞いが分かれる変更(対になる確かめ) | 利用者の種類・設定の有無・権限など、**条件によって表示や動きが変わる**差分は、変わる側だけでなく、**変わらない側(今までどおり)の確かめも、同じ観点の中に置く**。変わる側の確かめ(見出し・ボタン・件数が増えた時の表示・承認の画面など)を1つずつ並べ、**それぞれに対応する「今までどおり」の確かめが、どこかの項目にあるか**を突き合わせる(「変わらない」側を1つの節にまとめるだけでは、変わる側の確かめが抜け落ちる) |
| 画面の外の入力・出力 | 画面の表示とは別の道を通る、ファイルの取り込み・ダウンロード・通知などを別の観点にする(必須/任意・対象の項目か、列が含まれるか・見出しが正しいか) |

洗い出したら、**差分を1行ずつ見直し、対応する観点が無い行が残っていないか確かめる。** 残っていたら観点が漏れている。

### 狭い幅の確認

イシューの対応で**画面の見た目や文言が変わる**(ラベル・メッセージ・列・ボタン・並べ方の追加や変更。文言が長くなる変更を含む)時は、変更した画面を**狭い幅(例: 375px)**で開いて表示が崩れないかを確かめる項目を、必ず作る。

- **1つの観点=1つの節**(結合)にまとめ、**変更した画面ごとに1項目**。見た目の変更が無い差分(サーバーだけ・ロジックだけ)では作らない
- 操作の書き方: ブラウザの開発ツールの端末の表示などで幅を 375px にして、変更した画面を開く(画面ベースの原則どおり、コマンドは書かない)
- 期待する結果は崩れを具体的に書く: ページ全体が横に動かない/変更した文言・ラベルが欠けたり、ほかの部品と重ならない/ボタン・入力の欄が押せる・入れられる/表や長い文字は折り返す、または枠の中だけで横に動く。変更前の見え方より悪くなっていないことも添える
- **対象の画面が狭い幅で使われるか分からなければ、推測せず、ユーザーに聞く**(「分からないことは聞く」)。使われないと答えられたら、その節を作らず、`excluded` に理由と合わせて書く
- 優先度は、変更した文言・並べ方が崩れやすいもの(長い文言・列が増える)を高にする

## 3. 観点ごとに節を作る

**1つの観点=1つの節。** 複数の観点を1つの節にまとめない。1つの観点を複数の節に分けない。境界の場合は別の節にせず、同じ観点の中に置く。

- 準備・後始末は決まった骨組みで、この決まりの外
- それ以外は `tc01` から**種別をまたいで通し番号**で `id` を振り、`title` を `TC-01 …` で始める。`kind` は種別のファイルで決まる
- 並びは **準備 → 単体 → 結合 → 回帰 → 受け入れ → 後始末**(ファイルの並び。正本では7節の順に並べ直す)
- 見出しは観点が一目で分かる名前にする(例:「TC-01 主な症状の確認」)
- 項目の `id` は節の `id` を頭にした `tc01-04` の形。**決めたあとは変えない**(エビデンスのファイル名と再テストの対応に使う)。足す時は末尾に足す
- 画面をまたぐ節(全画面の見出しの表示など)は、操作の順に依存しないなら**メニューの並びに揃える**。並びはメニューの定義を読んで取り、推測しない。複数の節で同じ画面の群を扱う時は、すべて同じ並びにする。操作の順に依存する時は操作の順を優先し、外したわけを1行添える
- 実施の必要度に差がある観点(時間が無ければ後回しでよい、など)は、節の `notes` に書く

### 3-1. 共有するデータの状態表を作る

複数の項目が**同じデータを書き換える**と、行う順によって、後ろの項目の前提が崩れる(実例: 同じ利用者の設定が項目ごとに書き換わり、あとから準備の直後に戻すコマンドを足して、前提を書き直した。実施の順を決める段階で、金額の前提が成り立たない項目も見つかった)。**項目を書く前に、状態表を作る。**

- 縦に共有するデータ(利用者・設定・申請など)、横に項目を並べ、各項目がそれを**どう変えるか**(読むだけ/書き換える/使い切る)と、**戻す手順**を書く
- 書き換える項目には、**項目の中で元に戻す手順**を入れるか、準備に**戻すためのコマンド**(何度行っても同じ状態に戻る)を置く。あとから足すのではなく、準備を書く時点で決める(4-0)
- 申請などを使い切る項目は、どの項目がどれを使い切るかの対応表を作り、取り合いが無いことを確かめる(5-1と同じ)
- 状態表は、サブエージェントのプロンプトにも渡す(前提の書き方を揃えるため)。7節の実施の順を決める時の、制約の一覧にもなる
- 状態表は作業フォルダの `cases/` に Markdown で置いてよい(正本には添えない)

### 動きを変えないことが目的の変更(リファクタリング)

「動きを一切変えないこと」が目的(共通化・ファイルの分け直しなど)なら、次の3つを**混ぜずに**別の節にする。

1. **変更前のブランチでの画面の撮影**(`kind: regression`)— 変更後に切り替える**前**に画面を撮るだけ。合否を判定しない
2. **TC-01〜TC-0N** — 変更後のブランチで、コードから導いた期待する結果を満たすかだけを確かめる。変更前とは比べない
3. **変更前/変更後の画面の見比べ**(`kind: regression`)— 1と2で見えた同じ画面を1つずつ見比べ、意図しない見た目の違いが無いことを確かめる

混ぜないわけ: 期待する結果に照らすだけでは、共通化のついでに**直ってしまった既存の不具合**のような、コードを読んでも予見できない違いを見逃す。3で見つかった違いは、「意図した、ついでの直し」か「確かめていない壊れ」かを切り分けて記録に書く。

## 4. サブエージェントを並行に起動して項目を書かせる

### 4-0. 先に準備・後始末と事実のシートを決める

項目の担当は、準備が決まっていないと、画面の言葉・使う利用者・実際のデータを書けず、`【要確認】` を大量に残す(実例: 準備が雛形のまま4種を並行に書かせ、29件の `【要確認】` が出た。その大半は、準備とコードを読めば決まる中身だった)。**項目の担当を起動する前に、次の2つを済ませる。**

1. **準備・後始末を書く**(`setup.json` / `cleanup.json`。親が書くか、担当に任せる)。項目の `id`・`title`・用意する状態(どの利用者がどんなデータか)を**決めてから**項目の担当を起動する。担当には決まった `setup.json` のパスを渡し、項目の前提は「準備の setup-0N を済ませている」の形で書かせる
2. **事実のシートを作る**(ファイルにしなくてよい。プロンプトに貼れる形で)。項目に書く**具体的な値**を、根拠つきでまとめる:
   - 実際のデータ(例: コードと対応する名前。外のサービスの実測の値)
   - 画面の言葉(メニュー名・タブ名・ボタン名・メッセージ)と、その出どころ(画面のコードの path:line)
   - 使うアカウントと権限
   - 準備が用意する利用者・データの ID と状態
   - **確かめていない値は、推測のまま渡さない。**「未確認」と書くか、先にユーザーに聞く。親がプロンプトに書く事実も、根拠(コミット・実測)を添える。親の思い込みを渡すと、4つのファイルすべてに誤りが広がる(実例: 実測と違う名前を4つのファイルに書かせ、あとで一括で置き換えた)

#### 準備は必要最小限にする(ゴール5)

準備は、実施する人の手間を一番食う。**準備に置くのは、本当に要るものだけ**にする。書いたあとで「これは準備に要るか」を項目ごとに問い直す(実例: 画面から1回の保存で作れる状態を、専用の準備の項目にして13〜15手順に膨らませていた)。

- **画面だけでは作れない状態、またはコマンドが要る状態**だけを準備に置く(例: 不正な値が残った既存のデータ。仕様の上、画面からは作れない/外のサービスにつながらない状態)。**最初に使う項目の手順で、1回の画面の操作で作れる状態は、準備の項目にせず、その最初の項目の頭に畳む**。以降の項目の `given` は、「実施の順で最初に使う項目で変えてある」と書く
- **準備に置くのは、項目の全体が共有する準備(ログイン、複数の項目が共通で使うデータ)だけ。特定の項目でしか使わない準備は、準備ではなく、その項目の手順に書く**(実例:「外のサービスにつながらない状態」は、つながらない時の項目2件だけで使うのに、準備に置くと最初に行って、ほかの項目を妨げる。使う項目の頭で作り、最後の項目で戻す。戻し忘れの保険として、後始末に戻す手順を残してよい)
- **データを直接書き換えるコマンドを準備・後始末に書く時**は、次を守る
  - 実行する先は、**実施する人が画面で使う環境**(画面がつながるサーバー、同じデータベース)にする。書く前に、その環境の件数を読み取りで確かめる(別に起動した環境は、データが空のことがある)
  - 履歴やキャッシュを持つデータは、アプリがふだん使う書き方(アプリのコマンド・保存の処理)で書き換える。表を直接書き換えると、画面に出ないことがある(実例: 履歴を持つデータを直接書き換えたら、画面には元の値のまま出た)。書き換えたあとの確かめも、画面と同じ読み方で読む
  - 書き換えるコマンドには、**元に戻すコマンド、または画面での戻し方**を必ず組にして書く(何度行っても同じ状態に戻る形)
  - Claude は書き込みを実行しない。書き込みを外した版(読み取りだけ)を実際のデータで動かし、引用符・出力の形が動くことを確かめるところまでにする
- **アカウントとデータは、既存のものを使い回す。** 新しく作るのは、既存が条件に合わない時だけにする。状態を変えない読み取りの調べもので、使える既存のアカウント・データを調べる。権限は、その中身(画面を見る権限)まで確かめ、要る画面に入れることを確かめる(実例: 機能が無効になっている所や、承認の画面の権限が無いアカウントは使えない)。パスワードは書かず、「実施する人が控えているもの」とする。使ってよい既存のデータ(書き換えてよい利用者など)は、ユーザーに確かめ、書き換えるものには**元に戻す手順を組にして置く**
- **ログアウトとログインを繰り返す作りにしない。** 同じ人が複数のアカウントを使う時は、ブラウザのウィンドウ(通常とシークレットのウィンドウ)またはブラウザを分け、**最初に1回ログインして、そのまま使い続ける**。二段階の認証があるアカウントは、ログインし直すたびにコードが要るので、とくに避ける。アカウントの切り替えが避けられない項目は、実施の順で1か所にまとめる
- 準備の各項目の頭に「ログインする」を繰り返し書かない。最初の項目でログインし、以降は「ログインが続いていること」の確かめ1行にする
- 項目を削ったら、その `id` を参照している `given`・手順・実施の順の注意・後始末を全部直す(grep で確かめる)

単体・結合・回帰・受け入れの項目は互いに関わらないので、**1つのメッセージで4つの Agent の呼び出しを同時に出して、並行に書かせる**。書き込む先を種別ごとに分けてあるので、ぶつからない。

| 種別 | サブエージェント | 書き込む先 |
|---|---|---|
| 単体 | `test-cases-unit` | `<作業フォルダ>/cases/unit.json` |
| 結合 | `test-cases-integration` | `<作業フォルダ>/cases/integration.json` |
| 回帰 | `test-cases-regression` | `<作業フォルダ>/cases/regression.json` |
| 受け入れ | `test-cases-acceptance` | `<作業フォルダ>/cases/acceptance.json` |

**親が3節までと、4-0(準備・後始末と事実のシート)を終えてから起動する。** 番号が種別をまたぐので、書き始めてから節を増やしたり減らしたりするとぶつかる。

### 親がプロンプトに入れるもの

- **作業フォルダ・対象のリポジトリ・`$DEV_WORKBENCH_HOME` の絶対パス**(書き込む先は作業フォルダ、コードの調べものは対象のリポジトリ、形の決まりとスクリプトは `$DEV_WORKBENCH_HOME`)
- イシューの要件・変更の概要、差分の範囲。**結合にはコードのパスを渡さず**、仕様・画面の情報・メニューの並びだけを渡す
- 受け持つ節の一覧(`id` / `title` / `kind` / 節の説明)
- 受け入れには**要件の一覧**(`plan.json` の `requirements`)。項目は1つの要件に1件以上、`requirement` に要件の id を書かせる
- 書き込む先のファイル
- **決まった `setup.json` のパスと、事実のシート**(4-0)と、共有するデータの状態表(3-1)
- コードの調べものを頼む時は、**対象の作業ツリー(`git -C <パス>`)とコミットの範囲**を明示する(手元のチェックアウトが別のブランチだと、`git diff main...HEAD` に目的の変更が含まれない)
- PR の本文・イシューのコメント・作業フォルダの設計など、サブエージェントが取れない外の文書は、**親が先に取ってプロンプトに貼る**

### サブエージェントが動く条件

サブエージェントは、権限の設定で、**`check-cases.mjs` を実行できないことがある**(実例: 5つのうち4つが実行できなかった)。次を前提にする。

- `check-cases.mjs` は**親が必ず実行する**。担当には「実行できなければ、報告に『未実行』と書く」よう指示する
- 1つのファイルだけを確かめる時は `--file` に**パス**を渡す(`node "$DEV_WORKBENCH_HOME/skills/test-cases/scripts/check-cases.mjs" <作業フォルダ> --file <ファイルのパス>`。`--file unit` のような名前だけでは動かない)
- コードを読む担当は、読み取りだけのコマンドを使う。外のサービスの読み取りだけの GET(状態を変えない。実際のコードの名前の実測など)は、API のキーを出力・ファイルに書かないことを条件に使ってよい

### サブエージェントに共通の約束

- 書き込むのは書き込む先の1つのファイルだけ。`plan.json`・ほかの種別のファイル・対象のリポジトリは触らない(フックでは止めないので、各自が守る。単体・回帰・レビューの Bash は読み取りだけのコマンドに限る。結合・受け入れは作業フォルダの外のコードを読まない)
- 出力は `{ "sections": [...] }` だけを持つ JSON。渡された節の中身(`notes` と `items`)だけを書き、節を増やしたり減らしたりしない。項目の `id` は渡された節の `id` を頭にする(`tc02-01`)
- 書く前に `$DEV_WORKBENCH_HOME/skills/test-cases/reference/format.md`(形と「書く時の3つの約束」)と、この SKILL.md の4節以降を読む
- **結合・回帰・受け入れは、原則として画面ベースで書く。** 操作は画面の操作、期待する結果は画面の見え方・出力ファイルの中身にする。コマンド・データベース・API・ログでの確かめは、単体と準備・後始末に置く。画面の無い変更などで例外にする時だけ、`noScreen` に理由を書く(format.md「画面ベースの原則」。`check-cases.mjs` が止める)
- `duplicateOf` は付けない(種別をまたぐ重なりは、親が5節で付ける)
- **分からないことは推測で埋めない。** 該当の欄に `【要確認】<質問>` と書き、終わりの報告に質問を一覧で返す(親がユーザーに聞く)
- `title`・`given`・`steps`・`expect` にコードの言葉を書かない。単体の根拠は `basis` に書く

### 戻ってきたら

1. `node "$DEV_WORKBENCH_HOME/skills/test-cases/scripts/check-cases.mjs" <作業フォルダ>` を**親が必ず実行する**(`kind` とファイル名の食い違い・id と節の id の重なり・`duplicateOf` の行き先・**どの項目にも結びつかない要件**などを見つける)
2. `【要確認】` と確かめることを集め、**次の3段階で仕分けて**埋める(全部埋まるまで `check-cases.mjs` は通らない)。親が推測で埋めない
   - ① 一覧にする: `check-cases.mjs` が出す id と、報告にある質問をまとめ、項目ごとに質問を並べる
   - ② **「調べれば決まるもの」と「ユーザーの判断が要るもの」に分ける。** 前者は、コード・準備・外のサービスの読み取りの GET で決まるもの(画面の言葉、実際のコード、どの利用者を使うか、変更前の動き)。後者は、仕様の是非、対象に含めるか、再現できない手順をどう扱うか
   - ③ 前者は**調べものの担当(サブエージェント)にまとめて任せる**(読み取りだけ・GET だけ。画面の操作・状態を変えるコマンドはしない。埋めた中身を id ごとに報告させる)。後者だけを `AskUserQuestion` で**1回にまとめて**聞く(選択肢と推奨を添える)
3. 5節の重なりの整理

### 項目の書き方

1つの項目は **確認内容(`title`)→ 前提 → 操作 → 期待する結果 → 優先度** の5点の組(単体は、これに期待する結果の根拠 `basis` が付く)。

- **確認内容(`title`)は必須。**「何を確かめる項目か」を1文で書く。実施する人が手順を読む前に、この項目の目的が分かるようにする。操作や期待する結果の言い換えにしない(悪い例:「ボタンを押す」「CSV が出る」)。観点の節の名前より具体的に書く(良い例:「更新で空欄にしない指定をしても、新しい行は空欄のまま登録されること」)。画面に出ている言葉だけを使う
- 行わない項目(`duplicateOf`)の `title` は、何と重なるかが分かる程度でよい

#### 読みやすく書く(実施する人が迷わず、速く読める書き方)

実施する人は、項目を**読みながら操作する**。読みにくい書き方は、操作の迷いと見落としになる。次の11の決まりで書く。

1. **手順は、「確かめる地点」で区切る。** 1つの手順は、次に何かを確かめるまでの操作のまとまり。同じ画面で続く入力や、保存のような決まった操作は、1つの手順にまとめてよい。確かめの無い操作は、次の手順に含める。画面やウィンドウ、タブを移る所は、手順を分ける(実施する人が「どこまで操作したか」を迷わないようにする)
2. **期待する結果は、頭に「手順N:」を付けて、その手順を終えた直後に見るものを書く。** 1つの手順に確かめが複数あれば、同じ「手順N:」を繰り返す。確かめの無い手順には、期待する結果を付けない(実施する人が「どの期待する結果と照らすか」を迷わないようにする)
3. **期待する結果は、1つの要素に1つの確かめ。** 画面に出る文言・数値・状態をそのまま書き、「〜になる」で終える。理由や補足の括弧は書かない(理由は `basis` または準備に置く)
4. **準備と本編を分ける。** 準備の手順は、項目の頭にまとめて「準備:」と明示して区切る。手順の途中に「ここからが本編」のような文を挟まない
5. **呼び名は、1人(1つ)に1つに揃える。** 画面に出る書き方で呼ぶ。社員番号などの番号は、行を探す最初の1回だけ書く。役割の名前(利用者A など)と氏名を混ぜない
6. **同じ動作は、同じ言葉で書く。**「保存する」のように繰り返す操作は、1つの決まった形を、節の `notes` に1回だけ書き、以降は短く書く
7. **「〜なら」の分かれ道を手順に書かない。** 分かれる時は、前提(`given`)で状態を決めるか、項目を分ける
8. **長いコマンドは、手順の文に混ぜない。** 手順は「次のコマンドを実行する」の1つの要素にし、コマンドは次の要素に `` `…` `` だけで置く
9. **前提(`given`)は2行以内。** 繰り返す説明(画面の言葉、状態の説明)は、節の `notes` に1回だけ書く
10. **id や中の呼び名(`tc02-01`・`setup-01`・`cleanup-01`)を、文の中に埋め込まない。** 要る時は、「前の項目で〜にした」のように状態で書く(項目の id は参照の手立てであって、実施する人が読む情報ではない)
11. **1つの項目に、確かめる地点は1つだけ。** 期待する結果の「手順N:」が2つ以上の手順に付くなら、「操作→結果」の1組ごとに項目を分ける。入力の値だけを変えて同じ操作を繰り返す変わり種(日数に「e」「-」「0」を順に入れる、など)も、状態を積み上げていく流れ(依頼→定期の処理→差し戻し→定期の処理、など)も対象。同じ確かめる地点に期待する結果が複数あるのはよい。逆に、**1つの操作で複数の観点を確かめられる時は、1つの項目にまとめ、期待する結果を並べる**(同じ操作や同じ画面の表示を、観点ごとに別の項目で繰り返さない。元の項目が別々なら、片方に `duplicateOf` を付けて外し、残す側に期待する結果と要件を足す。コマンドを含む項目は、正本の統合した項目にできない。実施を始めたあとは、項目をまとめない。エビデンスと合わなくなる)。2回目を行うこと自体が確かめになる操作(同じ日付での再実行など)は、別の項目のままにする。分けた2つ目以降の前提は「前の項目の続き(同じ画面・状態のまま)」とし、項目をまたぐ参照は「前の項目で出た〜」のように状態で書く(1つの項目に操作と期待する結果が複数並ぶと、実施の途中で操作と期待する結果の対応がずれる)

書き終えたら、各項目を上の11の決まりで見直す。

#### 優先度をつける

| 優先度 | 基準 |
|---|---|
| 高(`high`) | 主な場合の確かめ、または自動のテストで確かめられていない項目 |
| 中(`mid`) | 主な場合から派生した、パターンを網羅するための項目 |
| 低(`low`) | 境界の場合 |

- **高と中の境**: 自動のテストを実際に grep して、その項目を確かめるテストがあるかを確かめる。無ければ高。「たぶんテストされているだろう」で中に落とさない
- **高と低の境**:「飛ばして本番で問題が起きた時、見逃しとして許せるか」で決める。許せないなら高
- 自動のテストで確かめていても、画面の表示・ファイル名・ほかの画面との整合など**手でしか確かめられない要素**が乗っていれば、高のまま残す
- そのような要素が無く、自動のテストと同じ中身を確かめるだけでも、**項目は残し、優先度を低にするだけに留める。低いことを理由に確かめないことへ落とさない**。自動のテストの期待する結果そのものが間違っていることや、実施する人の目で見て初めて気づく違和感を拾えないため
- 省きたい項目は、確かめないこと(`excluded`)に理由つきで書く

```bash
# 例: この項目を確かめるテストが本当に無いかを確かめる
grep -rn "対象の関数名やキーワード" <テストのフォルダ>
```

#### パターンの漏れを防ぐ(テストの技法)

技法ごとに、機械的に境界の場合を出す。当てはまらない技法は使わない。

| 技法 | 使う時 | すること |
|---|---|---|
| 同値分割・境界値分析 | 値に範囲・上限・件数がある | 有効/無効のまとまりと境界(最小−1・最小・最大・最大+1、0件・1件・上限の件数)を洗う |
| デシジョンテーブル | 条件が複数あり、組み合わせで結果が変わる | 条件×条件の表を作り、**全部の組み合わせを先に出してから**優先度で間引く。先に間引くと漏れる |
| 状態遷移 | 画面やデータが状態を持つ | 状態×操作を洗い、移れない組み合わせも書く |
| エラー推測 | 前の不具合やミスの形に心当たりがある | 似た不具合・勘所のあるミスを並べる |

#### 期待する結果は具体的な値で書く

「名前が出る」では判定できない。実測して具体的な値を書く。**修正前の動きも添える。**

```
○ アイデア帳_2026-11-03.csv
× 名前を含むファイル名
```

#### 確かめるためのデータは画面の操作で作る

データベースを直接書き換える手順は書かない(戻し忘れると、ほかの確かめを巻き込む)。**アプリの画面から専用の利用者・データを作る手順**を書き、後始末は「作ったものを画面から消す」だけで済むようにする。直接の書き換えしか手が無い時に限り、戻すコマンドを後始末に必ず組にして置く(4-0)。

#### コマンドは `` `…` `` で囲み、1つの手順に1つにする

実施する人がコマンドを写して貼るので、**文に混ぜない**。書き方は [reference/format.md](reference/format.md)「コマンドの書き方」。

```
× "--field を付けずに docker compose exec -T app sh -lc \"…\" を実行する"
○ ["--field を付けずに、次のコマンドを実行する", "`docker compose exec -T app sh -lc \"…\"`"]
```

- 枠の中は、そのまま貼って動く1行にする。実際の値を入れ、`<…>` の仮の値を残さない
- 長いスクリプトはファイルにして `plan.json` の `attachments` で添える。同じコマンドの繰り返しは準備に1回だけ書く
- `-c "…"` のような引数の中に、実際の改行の入った複数行のスクリプトを書かない。コピー先で改行が保たれない環境があり、貼った時に全部の行が1行に潰れて動かなくなる(実例あり)。文をすべて `;` で1行につなげる。繰り返しのあとに続けたい処理(件数の表示など)は、繰り返しの**前**に書く(言語によっては、後ろに書くと繰り返しの中に取り込まれる)

#### 前提には、判定のしかたを添える

条件を満たしたかを実施する人が自分で確かめられるようにし、**合否の基準まで書く**。

```
前提: 所属が1件だけの利用者がいる
手順: 「利用者」の画面で、その利用者を開く
期待: 手順1: 「所属」の欄が1行だけ。2行以上なら、前提を満たしていない
```

#### 準備は「上から順にやってチェックする手順書」にする

実施する人は、準備を**上から順に、1項目ずつ操作して確かめる**。参照用の表や、読むだけの注意に、準備の中身を散らさない。**この手順書は、画面を初めて見る人が、迷わず最後までできる細かさで書く。**

- **1項目=1人、または1つのデータの準備。** 人が6人いれば6項目にする。「同様に」「前と同じ」で省かず、項目ごとに全部の手順を書く(操作の途中で、ほかの項目へ戻らせない)
- 項目の欄: `title`(「〜を用意する」)/ `given`(この項目の前に済んでいる項目。無ければ省く)/ `steps`(操作)/ `expect`(できあがりの確かめ)
- **`steps` には操作だけを書く。** 1つの要素=1つの動作(開く・押す・入れる・選ぶ)。画面に出ている言葉(メニュー名・タブ名・ボタン名・入力の欄の名前・出るメッセージ)をそのまま使う。「適宜」「必要に応じて」と書かない
- **`expect` には、できあがりの確かめを、画面に見えることで書く**(1項目に1〜2行)。操作の言い換えや、理由・仕様の説明は書かない
- 実施する人が決める値(パスワード・受け取れるメールアドレス)は「自分で決める」と書く。値そのものや、実在するアドレスは書かない
- 表を作らない。氏名・ログイン ID・番号は、使う項目の中に書く
- 画面の言葉は、コードや実際の画面から拾う。推測で書かない(拾えなければ `【要確認】`)

```
× title「利用者Bの準備」/ steps「作ってログインできた」
○ title「利用者Bを作る」/ steps ["…でログインする", "…を押す", "…を入れて「追加」を押す"] / expect「招待メールのログイン ID で、自分の画面に入れる」
```

書き終えたら、次の4点を確かめる。

1. `steps` の各要素が、人の動作(開く・押す・入れる・選ぶ)で終わっているか
2. `expect` が、画面に見えることだけで、1項目に1〜2行か
3. 表を作っていないか(要る氏名・ID は、使う項目の中にあるか)
4. 項目を上から順にやるだけで、準備が終わるか(ほかの項目へ戻らずに済むか)

## 5. 重なった項目を、行わない項目にする

全ファイルの項目を見て、種別・節をまたいで同じ操作・同じ期待する結果の項目が無いかを見直す。**同じ画面を同じ操作で確かめる項目は、種別が違っても、1回行えば足りる。** 実施の手間と、同じ申請・同じデータを何度も使い切るぶつかりを減らすために、**下位のテストが上位のテストで賄えていれば、下位の項目を行わない項目にする**。

**消さずに、打ち消し線で残す。** 消すと「その観点を考えた証跡」が消え、次にレビューする人が同じ重なりに気づけない。

- 行う方(一番自然に説明できる方。たいていは先に出てくる観点)はそのまま残す
- もう一方に `"duplicateOf": "tc01-04"` を足す。証跡では打ち消し線で出て、正本には入らない。行わない項目にもふつうと同じ id を振る(行き先をはっきりさせるため)

### 5-1. 上位のテストで賄えている下位の項目を、行わない項目にする

**テストの階層(低い方から)**: 単体 → 結合 → 回帰・受け入れ。**下位の項目の操作と期待する結果が、上位の項目で確かめられていれば、下位の項目を行わない項目にする**(上位を残す)。

| 下位(行わない側) | 上位(残す側) |
|---|---|
| 単体 | 結合・回帰・受け入れ |
| 結合 | 回帰・受け入れ |

- 回帰と受け入れの間、同じ種別の中では、階層の上下は無い。同じ操作・同じ期待する結果なら、より自然に説明できる方を残す
- **受け入れの項目は、要件を確かめる唯一の拠り所になりうるので、軽々しく行わない項目にしない**(してよいのは、同じ要件を指す別の受け入れの項目が残る時だけ。`check-cases.mjs` が、すべての要件を指す受け入れの項目が残っているかを見る)

**判断の基準(「賄えている」とは)**
- 下位の**操作と期待する結果のすべて**が、1つ、または複数の上位の項目で確かめられる。上位の項目の `given`・`steps`・`expect` を**実際に読んで**決める(`title` や節の名前だけで決めない)
- `duplicateOf` は1件しか指せない。複数の項目にまたがる時は、**一番よく含む上位の項目1件**を指す
- 足りないところが小さければ、**上位の項目の手順・期待する結果に書き足してから**行わない項目にする。書き足しは、今の期待する結果を損なわない最小限にする。**受け入れの項目への書き足しは、要件の文の範囲に収まる時だけ**。収まらないなら、回帰・結合の項目に書き足して、そちらを指す
- **賄えていないものは、行わない項目にしない**。判断が割れる時も行う項目のままにして、わけを記録する。行う項目のままにする典型:
  - 上位に無い状態・分岐(0件、境界の値、初めの状態、例外、入力の変わり種)
  - 上位に無い画面の組み合わせ(足した2件目、条件付きで出る欄の切り替え など)
  - 結合が、画面をまたぐ**一連の流れ**として確かめているもの(申請 → 承認 → 通知のメールなど)、狭い幅、画面の外の出力(メール・CSV)
  - 単体だけが、画面から再現できない分岐を、コードの根拠(`basis`)で確かめているもの

**行わない項目にする前の照らし合わせ(必ず)**
- 行わない側の `expect` を**1つずつ**取り出し、残す側の `expect`(または手順)に**同じ確かめが含まれるか**を照らす。「操作が似ている」「題名が同じ」だけで決めない
- 含まれないものがあれば、**行わない項目にする前に、残す側へ書き足す**。書き足せない(要件の範囲を超える、別の利用者・別の状態で行う確かめ)なら、行わない項目にしない
- 見落としやすい例: 行わない側が「保存されていないこと(開き直しても元のまま)」を確かめているのに、残す側は画面の上の取り消しで終わっている/行わない側は別の利用者(名前が空の行など)で確かめている
- 判断の記録として、報告に「行わない側 id → 残す側 id、残す側に書き足したこと」を残す

**行わない側の扱い**
- `title`・`given`・`steps`・`expect` と、単体の `basis`(コードの根拠)は**残す**(証跡に打ち消し線で出る。根拠の証跡になる)
- 残す側(`duplicateOf` の先)は、**階層が同じか上の項目で、自身が `duplicateOf` を持たないこと**。行わない項目を指さない(指した先が、あとで行わない項目になる連鎖を作らない)。単体どうし・結合どうしで指さない

**整合を取る**
- 行わない項目にした id を、準備(件数・実施の順・注意)や、ほかの項目の前提が**行う項目として参照していないか**を確かめ、参照を残す側の id に置き換える
- 上位の項目に書き足したら、準備の件数(申請の数・使う利用者・使い切る項目)と実施の順が成り立つかを確かめる。**申請などを使い切る項目を、新しく足さない**
- 行わない項目にしたあとの件数(種別ごとの全件・行わない・行う)を数えて、ユーザーへの報告に含める
- 進め方: ① 下位の行う項目を一覧にする ② 1件ずつ、上位の項目を読んで、賄えているかを決める(`expect` の各要素を照らす。上の「照らし合わせ」) ③ 書き足しが要るものは書き足す ④ `duplicateOf` を付ける ⑤ `check-cases.mjs` を通す ⑥ 準備と前提の参照を直す。項目が多い時は、種別ごとにサブエージェントに任せてよい(判断の基準と、残す側・書き足しの決まりを、プロンプトに写す)

## 6. レビューのエージェントで漏れを見る

重なりの整理まで終えたら、`test-cases-review` を起動する。項目の書き手とは別の文脈で、**差分と要件に対して項目に漏れが無いか**を見る(読み取りだけ。直さず、指摘だけを返す)。

- 渡すもの: `<作業フォルダ>/cases/` のパス、対象のリポジトリのパスと差分の範囲、要件、作業フォルダの設計(あれば)。**行わない項目(`duplicateOf` 付き)の判断**(残す側が、行わない側の操作と期待する結果を含むか)と、**変わる側の確かめに対応する「今までどおり」の確かめがあるか**(5-1と、2節の「対になる確かめ」)も見てもらう
- 打ち消し線の付いた全件をビューアで見たい時は、先に `build-manifest.mjs <作業フォルダ> --trail` で `cases/manifest.json` を作っておく
- **ゴールの5つ(冒頭の「ゴール」)を、レビューの観点としてそのまま渡す。** 各ゴールについて「満たしている/満たしていない」と根拠を返してもらう。ゴール3(確かめられていない動きに項目があるか。確かめられている動きが高い優先度になっていないか。**確かめられていることを理由に、項目を消すことは求めない**)とゴール5(省ける手順・準備が残っていないか)も見てもらい、**項目を増やす指摘は、要件が判定できない・誤った期待する結果で誤って合格になる、といった重いものに限る**よう指示する(絞り込みの方針を壊さないため)
- 返ってくるもの: P1(漏れ。項目を足すのが必須)/ P2(期待する結果・前提・優先度の誤り)/ P3(よりよくする)の一覧と、足す・直す案
- 親は P1・P2 を直す。足す時は**末尾に足す**(id は変えない)。足したら `check-cases.mjs` を通す
- 直したら、P1 があった時に限りもう一度レビューさせる(2回まで)。2回目でも P1 が残るなら、ユーザーに判断を仰ぐ
- 書き手のサブエージェントは使い回さず、レビュアーには**書き手の途中の考えを渡さない**(できあがったものだけを見て決めさせる)

## 7. 実施する正本(manifest.json)を作る

6節までの下書き(種別ごとのファイル)は、「なぜこの項目が無いか」を追える**証跡**で、行わない項目が混ざり、種別ごとに並んでいるので、実施する人には見づらい。**行わない項目を除き、実施の順に並べ直したものを、1つの `manifest.json`(正本)にまとめる**(証跡のファイルは変えずに残す)。

置き場(すべて作業フォルダの中):
- 証跡: `cases/plan.json`・`setup.json`・`unit.json`・`integration.json`・`regression.json`・`acceptance.json`・`cleanup.json`(これまでどおり)
- **`cases/order.json`(手で書く)**: 実施の順。グループ → 項目の id の並び(形は [reference/format.md](reference/format.md)「実施の順」)
- **`evidence/<YYYY-MM-DD>-<内容>/manifest.json`(作るもの)**: 正本。`build-manifest.mjs` で、証跡と `order.json` から作る(手で直さない)。`<YYYY-MM-DD>` は作った日、`<内容>` は英小文字とハイフン(例: `2026-11-22-pr45`)
- 項目が少なく、種別の順のままで行えるなら、`order.json` は作らなくてよい(準備 → 単体 → 結合 → 回帰 → 受け入れ → 後始末 の順になる)

### 7-1. order.json を作る(実施の順の決め方)
- **行う項目(`duplicateOf` を持たない全部)を、文字列か、1つ以上の統合した項目に**並べる(漏れ、文字列での重なり、文字列と統合した項目の両方への指定、同じ統合した項目の中での重なり、行わない項目は `check-cases.mjs` が止める)
- **グループの並び**は、準備の「実施の順」に沿わせる。目安: ① 見るだけ(使う人の画面)→ ② 見るだけ(管理する人の画面)→ ③ 宛先の登録・通知を確かめるための申請など、データを作る → ④ 前もって作っておいたデータを使い切る項目(承認・差し戻し・修正の依頼)→ ⑤ 作り直したあとに使い切る項目 → ⑥ 入力・保存・提出 → ⑦ 最後(後始末のあとに行うもの。グループに `"afterCleanup": true`)
- **グループ**は、同じアカウント・同じ画面を続けて見るようにまとめる(アカウントや環境の切り替えを減らす)。おおむね3〜8項目。`who` に使うアカウントを書く
- **同じ人が同じ画面を、別々の項目で開き直す/同じ流れの中で続けて確かめられる項目は、`order.json` の統合した項目にまとめる。まとめても、元の項目の確かめ(`expect`)を1つも落とさない。元の項目は証跡として変えない**
- **元の項目が複数のアカウントにまたがる時は、アカウントごとの統合した項目に分け、同じ元の項目を複数の統合した項目の `merge` に入れてよい。その元の項目の確かめは、アカウントごとの統合した項目の `expect` に分けて書く。どの統合した項目にも書かれていない確かめがあってはならない**
- **項目は、1つの画面を1つの項目の小さな項目にする(操作→期待する結果を、項目ごとに完結させる)。前の項目から続く時は、手順を最初から書かず、前の統合した項目に `key` を付けて `@key` で「@key の続き」と書く(ログイン・画面を開く手順の繰り返しを避ける)**
- 各項目の `given` を読み、**前提となる状態(別の項目が作る・変える状態、申請などの使い切り)が、先に行う項目に含まれる順**にする。行わない項目が元の順の制約に出てくる時は、`duplicateOf` の先の行う項目に読み替える
- 各グループの `note` に、続けて行うわけ・始める前の注意(ログインするアカウント、このグループは申請を使い切る、など)を、画面の言葉で1〜3文書く
- 1つの項目に複数の時点の操作(申請 → 承認 など)が入っていて分けられない時は、そのまま1つのグループに置き、`note` で、どのアカウントがいつ何をするかを書く
- サブエージェントに任せてよい(準備と全項目を読ませ、`order.json` と、機械的な確かめの結果(行う項目が全部、文字列か1つ以上の統合した項目にあり、禁じた重なりが無いこと)を返させる)

### 7-2. 作って確かめる
1. `node "$DEV_WORKBENCH_HOME/skills/test-cases/scripts/check-cases.mjs" <作業フォルダ>`
2. `node "$DEV_WORKBENCH_HOME/skills/test-cases/scripts/build-manifest.mjs" <作業フォルダ> --trail --out <作業フォルダ>/evidence/<YYYY-MM-DD>-<内容>`(正本と、証跡の `cases/manifest.json` を作る)
3. `node "$DEV_WORKBENCH_HOME/skills/test-run/scripts/check-manifest.mjs" <作業フォルダ>/evidence/<YYYY-MM-DD>-<内容>`(`manifest.json` の形)
4. 証跡の項目を直したら、**正本を作り直して**から、`check-cases.mjs <作業フォルダ> --manifest <正本のフォルダ>` で合っているかを確かめる。正本にすでに結果があれば上書きされないので、[やり直し(`test-run/retest/`)](../test-run/retest/SKILL.md) の手順で新しいフォルダに作る

### 7-3. 正本で変わること
- 節は、準備 → `order.json` のグループ(見出しは `G01 <title>(<who>)`)→ 後始末 → `afterCleanup` のグループ、の順になる。グループの項目の種別が1つなら、節にその `kind` が付く
- 項目の id は下書きのまま。統合した項目は、`order.json` で決めた `id`(無ければ元の id を `+` でつないだもの)になり、`note` に「まとめた項目: …」が付く
- 本文の中の、行わない項目の id は `duplicateOf` の先の id に、統合した項目に入った id は統合した項目の id に、書き換わる。`@key` は、その `key` を持つ前の統合した項目の id に置き換わる
- `plan.json` の `notes`・`excluded`、節の `notes`、グループの `note` は、正本の全体の `notes` にまとまる(`manifest.json` には節ごとの説明の欄が無いため)
- `noScreen` は、項目の `note` に「画面で確かめられない理由: …」として出る

### 7-4. 報告
正本の件数(グループの数・行う項目の数)、`order.json` の並べ方の根拠(順の制約をどう反映したか)、順がぶつかって直した点を、ユーザーに報告する。あわせて、冒頭の**ゴールの見直し(5つ)の結果**を1行ずつ報告する(満たしていないものがあれば、直すか、ユーザーに判断を仰ぐ)。

## 8. 渡す

作業フォルダは Drive の同期フォルダの中にあるので、書いたものは同期で Drive に上がる(Drive のコネクタや API でファイルの中身を送らない)。

1. 正本のフォルダ(`evidence/<YYYY-MM-DD>-<内容>/`)の Drive のフォルダ ID を調べる。Drive のコネクタがあれば、フォルダの名前で探して ID を取る(中身は読まない)。無ければ、ユーザーにそのフォルダの URL(`https://drive.google.com/drive/folders/<ID>`)を聞く

3. ユーザーに、そのURLと件数(グループ・行う項目・種別ごとの全件/行わない)を渡す。証跡を見たい人には、`cases/` のフォルダ ID で同じ形のURLを作る
4. 共有は、作業の置き場の親フォルダの設定に任せる。フォルダごとに「リンクを知っている全員」の共有を足さない
