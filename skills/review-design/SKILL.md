# 設計のレビュー

`<作業フォルダ>`(`$DEV_WORKBENCH_DOCS/<リポジトリ名>/<イシュー番号>/`。設計の共通の決まりは `design` スキル)の成果物を読み、実装に入ってから困る点を、先に見つける。**指摘だけを返し、成果物は直さない**(直すかどうかは、ユーザーに確かめる)。
レビューの共通の進め方(見る範囲・重要度・出力の形)は `review` スキル。

## 使う時機
- フェーズ5(変更仕様)を書き終えた時
- フェーズ7(最終仕様)、フェーズ9(実装の方針・計画)、フェーズ10(テストの方針・計画)を書き終えた時
- ユーザーが、設計のレビューや、詰められていない点の確認を頼んだ時

## 手順
1. `<作業フォルダ>` の成果物を読む(`spec.md`、`impl.md`、`impl/`、`acceptance.md`、`test.md`、`test/`、`spec/`、`search/`、`images/`。途中のフェーズなら、あるものだけ)
2. 次の3つの観点で、指摘を洗い出す
3. 指摘を、重要度の高い順に並べて返す

## 観点

### 1. 詰め漏れ
ねらい: 実装に入ってから「ここが決まっていなかった」と分かる事態をなくす。

#### 進め方
1. 変更で、**利用者・運用者が見る・触る・待つもの**を、すべて書き出す(画面、メニュー、リンク、設定項目、ボタン、メール、バッチ、管理画面、通知、ログ)
2. 書き出したもの1つずつについて、下の観点を確かめる
3. 観点ごとに、「仕様に書いた」か「該当なし(理由)」かを決める。**「実装で決める」にしてよいのは、利用者・運用者に見えないものだけ**(テーブル名、カラムの形、内部の関数名など)。名前・置き場所・既定値・文言の方針は、仕様で決める
4. 決まっていないものは、QA.md に起こす(推奨案つき)

#### 観点

##### 見る・触るもの(画面・メニュー・管理画面)
- 名前は何か(画面名、ボタン名、項目名、タブ名)
- どこにあるか(どの画面のどこ。どのメニュー・リンクから開くか。新しい画面なら、URL の方針)
- 誰が使えるか(ロール、権限)
- 何が表示されるか(項目、並び、空の時、エラーの時、読み込み中、権限が無い時)
- 操作した後、何が表示されるか(成功、失敗、件数、注意書き)
- 今ある似た画面と、どこが違うか(違う理由)
- 画面の変更が大きい時は、画面イメージを作る(`spec.md` に相対パスで埋め込む)

##### 設定項目
- どこで設定するか、誰が設定するか
- 既定値と、設定が無い時の動き
- 入力の範囲・検証(空、0、負の数、上限、桁)。エラーの時の表示
- OFF・無効の時の動き(値は残るか、送られないだけか、別の動きに差し替わらないか)
- 保存の単位と、保存が失敗した時の動き(片方だけ保存されないか)
- 変更の履歴を残すか
- 設定を変えた後の、すでに動いている処理への影響(例: 送った後に日数を変えたら、どうなるか)

##### 対象・条件(何に対して動くか)
- 対象にする状態・対象から外す状態を、すべて書く(状態の組み合わせは表にする)
- 境界(以上・未満、当日を含むか、日付の数え方、タイムゾーン)
- 空・未設定・存在しない時
- 重複(同じ対象が複数ある、新旧が並ぶ)
- やり直した時、同じ対象に2回動かないか(動くなら、許すか)
- 既存データの実際にありうる状態(未登録、複数、消した、無効にした、など)
- 参照(外部キーなど)の先が、消された・無効・不正の時の動き

##### メール・通知
- 件名、本文、宛先、差出人、添付、BCC
- 件名・本文が空の時、未設定の時
- 差し込む値と、値が取れない時
- 本文・設定を順に探すもの(個別 → 全体共通 → 初期値など)は、各段を使うか使わないか(代わりに使うものの有無)
- 画面のプレビュー・テスト送信が、実際の送信と同じ見え方か
- 届かなかった時に、誰がどうやって知るか

##### 実行(定期の処理・バッチ)
- いつ動くか(きっかけ、時刻、タイムゾーン)
- 止める方法(全体を止める、一部を止める)。止める手段が無い時は、無いことを書く
- 失敗した時(1件の失敗、全体の失敗、気づく手段、もう一度試すか)
- 二重に動いた時
- 手で動かす方法(どこから、誰が、結果をどう確かめるか)
- 実行の記録(誰がいつ何をしたか、どこで見られるか)
- 処理の量が多い時の限界

##### 運用・リリース
- リリース直後の状態(何が有効になるか、誰に何が届くか)
- 初期データ・マイグレーションで入れる値と、その対象
- 問題が起きた時の止め方・戻し方
- 既存の機能・データへの影響(変えないものも書く)

#### 完了の条件
- 書き出したものすべてについて、すべての観点を確かめた
- 決まっていないものが、QA.md に起こされているか、「実装で決める」と書いてよい理由がある

フェーズ9・10 では、次も確かめる。
- 実装の方針・計画: データ構造に、新しいテーブルのすべての列(型・NULL・既定・制約)と各列の理由、既存のテーブルの追加・変更と理由があるか。手を加える機能のすべてに、入口(ファイルのパスと、クラス・関数・ルートの名前)があり、修正対象を特定できるか。手を加える既存の機能(一覧・取得・テスト送信・初期値の取得など、まわりの機能を含む)が洗い出され、「変更 / 変更なし」に分かれているか。作業の分け方に、順序の矛盾が無いか。画面の文言が先に決まっているか。データの流れに、失敗した時があるか
- テストの方針・計画: すべての AC に、層・手段(自動 / 手動)・担当・データの準備があるか。メール・通知・外部の API を外に出さない、日付を動かす、検証用データを使うなど、特殊な環境の準備が、方法・時期・確かめ方・戻し方つきで書かれているか。遮断を外してよい操作が限られているか。既存データの実際にありうる状態の作り方があるか。「変わらないこと」の確かめ方があるか。実機でしか確かめられないものの、時期と担当があるか

### 2. 成果物どうしの食い違い
- `spec.md` の決まったことに、`acceptance.md` の条件が対応しているか(漏れ)。`acceptance.md` の条件に、`spec.md` の根拠があるか(`spec.md` に無い条件が混じっていないか)
- `acceptance.md` の「`spec.md` の節」が、正しい節を指しているか
- `spec.md` の各項目が、`impl.md` の実装方針(データ構造・機能・データの流れ)の、どれかの変更に結びついているか(漏れ)。実装方針に、`spec.md` に無い動きが混じっていないか
- `acceptance.md` のすべての AC が `test.md` の計画に載り、層・手段・担当が決まっているか。計画に、AC に無いテストが混じっていないか
- `spec.md` と `impl.md` の中身が矛盾していないか。確定した文書(`spec.md`・`impl.md`・`test.md`・`acceptance.md`)に、未確認のことが混じっていないか(未確認は QA.md にあるか)
- `spec.md` と変更仕様(`spec/`)、`search/` の中身が矛盾していないか。取り消した決定が本文に残っていないか(下書きに残す時は、打ち消し線などで、取り消したことが分かるか)
- 仮・未決が、`QA.md` と対応しているか

### 3. 書き方の決まり
`design` スキルの共通の決まりに従う。
- 最終仕様 `spec.md` が、ほかのファイルを参照せず、1ファイルで完結しているか
- `spec.md`・`acceptance.md`・`test.md` に、コードの識別子・実装の方法が書かれていないか。確定した文書(`spec.md`・`impl.md`・`test.md`・`acceptance.md`)に、根拠の `path:line` が書かれていないか(根拠は `search/`・`impl/` にあるか)
- 「できないこと」「正常系以外の動き」が書いてあるか
- 根拠が `repo名:path:line` で残っているか。「未確認」が確定したことに混じっていないか
- 仮に「仮」と書いてあるか
- 記号(①②③・A/B など)だけで指していないか。略称(N・Y など)の意味が、初めに書いてあるか。同じものが、文書によって違う名前で書かれていないか
- Markdown の崩れ(閉じていないコードブロック、表の列のずれ)が無いか
- ビューアで読めるか: HTML(`<!-- -->` のコメントやタグ)が書かれていないか(文字のまま出る)。ひな形の説明(`> 書き方:`)が残っていないか。ほかの `.md` へのリンクと画像が相対パスか。画像のファイルが `images/` にあるか

## 出力

`review` スキルの出力の形で返す。観点は **詰め漏れ / 成果物どうしの食い違い / 書き方の決まり**。場所は `ファイル の「節」`。

```
### 設計のレビューの結果

**詰め漏れ**
- [ ] P1 `spec.md の「設定項目」` — <問題> — <影響・具体例>(提案)

**成果物どうしの食い違い**
- [ ] P1 `acceptance.md の AC-3` — <問題>(提案)

**書き方の決まり**
- [ ] P3 `impl.md の「データの流れ」` — <問題>(提案)

**見た範囲**: <読んだ成果物>
**問題の無かった観点**: <確かめて、問題が無かった観点>
```

- 指摘は、「何が、どこで、困るか」を、具体例つきで書く
- 推し量った指摘には、「推測」と書く
- 指摘のうち、決める人の判断が要るものは、`QA.md` に起こす形(質問・選択肢・推奨案)で提案する
