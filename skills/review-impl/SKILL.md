# 実装のレビュー

変更したコードを、設計どおりか・正しいか・作りがよいか・安全か・テストで守られているか、で確かめる。
共通の進め方(比べる先・見る範囲・重要度・出力の形)は `review` スキル。

## 対象の特定

1. 比べる先 `<base>` を決める(`review` スキルの「比べる先」)
2. 変更したファイルと差分を取る

```sh
git diff <base>...HEAD --name-only
git diff <base>...HEAD
```

3. 変更したファイルの全体と、変更したものを使っている所を読む
4. 設計を読む。作業フォルダ(`$DEV_WORKBENCH_DOCS/<リポジトリ名>/<イシュー番号>/`)があれば `spec.md`・`impl.md`・`acceptance.md`。無ければイシューと PR の本文(`gh issue view <番号> --comments`、`gh pr view`)
5. プロジェクトの決まりを読む(CLAUDE.md・`.claude/rules/`・コーディングの決まり・リポジトリの `docs/`)
6. `review` スキルの「見る範囲」の表で、見る範囲を挙げる

## 観点ごとのレビューも当てる

このスキルの観点とは別に、次を当てる(並行してよい)。結果は1つの報告にまとめる。

| スキル | 当てる時 |
|---|---|
| `review-regression` | いつも |
| `review-perf` | 処理・データの取り方・繰り返しを変えた時 |
| `review-ux` | 画面・文言・操作を変えた時 |

## 確認観点

### 設計との一致

- 設計(spec.md・impl.md・イシュー)で決めたことが、**すべて**実装されているか。1つずつ対応を取る(取れないものは漏れ)
- 設計に無い振る舞いが入っていないか(入っているなら、設計に戻すか、外すか)
- 受け入れ基準(acceptance.md・PR の受入確認)の各項目を、この実装で満たせるか
- 名前(画面・項目・ボタン・設定)が、設計と同じ言葉か

### 正しさ

- 正常系以外: 空・0件・1件・複数件・境界の値・未設定・権限の無い人・二重の操作・途中で失敗した時・通信そのものが失敗した時(例外)
- 失敗した時に、何をどう伝えるか(握りつぶしていないか、ログだけで終わっていないか)
- 状態を持つものの、初めて・やり直し・戻る・並行して動いた時
- 日付・時刻・数値の扱い(タイムゾーン、端数、桁、単位)

### 作り

- **責務**: 1つのものが2つの理由で変わるようになっていないか
- **依存の向き**: 下の層が上の層を知らないか(共通の部品が画面の事情を知る、表示の部品が通信を持つ、など)
- **差し替えられる継ぎ目**: 外のサービス・時刻・保存先など、テストで差し替えたいものを受け取れる形か
- **プロジェクトの決まり**: 置き場所・命名・層の分け方・使ってよいライブラリが、決まりに沿っているか。定数・パス・文言を直書きせず、決めてある所から引いているか
- 共通化・コード量は `review-perf` で見る(重ねて指摘しない)

### セキュリティ・見せてよい範囲

- 誰のものかを、**リクエストの値ではなく、ログインの情報(セッション)から**決めているか。新しい入口(API・ルート)が、権限の確認を通っているか
- 他人のものと、存在しないものを、同じ応え方にしているか(分けると、それだけで存在や ID の形が分かる)
- 受け取った値・外から来た文字を、そのまま画面に出していないか(HTML として解釈させない。文言にするのは既知のものに一致した時だけ)
- SQL・コマンド・パスに、受け取った値をそのまま組み込んでいないか
- 秘密の値(鍵・トークン・パスワード)をコード・ログ・画面側・リポジトリに置いていないか。画面側に出してよいものか
- 依存するパッケージを足したなら、必要なものか・出どころが確かか

### テスト

- 正常系・異常系が網羅されているか(失敗・空・境界・二重の操作・例外)。異常系は「落ちない」だけでなく、何をどう伝えるかまで
- **壊した時に落ちるか。** 定数をそのまま確かめるだけのもの、上位のテストと同じことを見ているものは外す
- 設計で決めたこと・受け入れ基準のうち、自動のテストで守るべきものに、テストがあるか
- 手で確かめる部分は、`test-cases` スキルのテストケースに回っているか

### 文書の更新

- 画面の文言・操作・手順・置き場所を変えたのに、README・`docs/`・ヘルプ・設計の文書が古いままになっていないか
- 同じことを2か所に書いていないか(1か所に置き、ほかはリンクで指す)
- PR の本文(変更の要約・受入確認・件数)が実装に追いついているか

### 環境への依存

- 時差: 日付を出す所と、それを確かめるテスト。UTC の文字列を直接書いていないか(深夜の時刻は土地によって前日になる)
- ロケール・OS: 並び順、改行、パスの区切り、大文字小文字の区別
- 手元にだけあるもの: 生成物・キャッシュ・環境変数・手元のファイルを前提にしていないか

### コメントと文書の書き方

- コードのコメント・文書に、**イシューや PR の番号**を書いていないか(番号を置いてよいのはコミットメッセージと PR の本文だけ)
- **過去の状態**(「以前は〜だった」「〜で困ったので」)を書いていないか。今どうあるべきかの理由だけを書く
  - 今そうである理由として読めるなら残す(「片付けないと次のテストが落ちる」)。出来事を指しているなら外す(「以前それで落ちた」)
  - grep では拾いきれない。「なぜそうしたか」を書いたコメントを順に読む。迷ったら、読む人を主語にして読み直す

## 出力

`review` スキルの出力の形で返す。観点は上の見出し。観点ごとのレビュー(回帰・性能・使い勝手)の結果を後ろに並べ、先頭に全体の P1 の件数を書く。

```
P1: 2件(実装 1 / 回帰 1)

### 実装のレビューの結果

**設計との一致**
- [ ] P1 `ファイル:行` — 指摘(改善案)(設計: spec.md の「<節>」)

**見た範囲**: ...
**問題の無かった観点**: ...

### 回帰のレビューの結果
...
```

指摘が無い時: 「実装のレビューで問題は見つかりませんでした」と書き、見た範囲と観点を残す。

直すところまで頼まれている時は、報告のあとに指摘の所を直し、直した所をわざと壊してテストが落ちることを確かめる。
