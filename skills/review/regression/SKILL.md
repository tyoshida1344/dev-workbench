# 回帰のレビュー

読む時: 変更によるデグレ(既存の機能への影響)が無いかを確かめるレビュースキル。 変更したファイルと、それを使っている所を読み、関数・API・部品の互換性、データの形と保存されたデータとの互換性、 条件分岐の変更がほかの場合に及ぼす影響、画面への影響、テストの整合を確かめる。 単体では報告だけ、呼び出し元から直すところまで頼まれた時は直す。 「デグレ確認して」「壊れてないか見て」「既存の機能に影響が無いか確かめて」と頼まれた時、 review / 実装のレビュー(`review/impl/`) から実装のレビューとして呼ばれた時に使う。

変更が、今まで動いていたものを壊していないかを確かめる。
共通の進め方(比べる先・見る範囲・重要度・出力の形)は `review` スキル。

## 対象の特定

1. 比べる先 `<base>` を決める(`review` スキルの「比べる先」)
2. 変更したファイルと差分を取る

```sh
git diff <base>...HEAD --name-only
git diff <base>...HEAD
```

3. 変更したファイルの全体を読む
4. 変更したものを**使っている所を grep で全部挙げて**読む。特に:
   - 変更した関数・API・コンポーネントを呼び出している所
   - 変更した型・データの形・設定のキーを参照している所
   - 変更した CSS のクラス・変数、イベント、保存のキー(localStorage・cookie・データベースの列など)を使っている所
5. 挙げた所が、どの画面・どの機能・どの利用者の操作につながるかを書き出す(差分に出てこない「ほかの用途」を見落とさないため)

## 確認観点

### 関数・API・部品の互換性

- 引数・戻り値・props・イベントの名前と型・既定値が変わっていないか。変えたなら、使っている所がすべて追従しているか
- 削除・名前を変えた関数・型・クラス・ファイルが、ほかで参照されていないか(文字列で組み立てて参照している所も grep する)
- 共通の部品・ユーティリティの振る舞いを変えた時、それを使うほかの画面・機能で期待どおりか
- 外へ出している API・URL・コマンドの形を変えていないか(使う側が別のリポジトリ・別の利用者にある時は特に)

### データの互換性

- データの形(型の定義・スキーマ・設定のファイル)と、それを読む所が一致しているか
- **すでに保存されているデータ**(データベース・localStorage・ファイル・キャッシュ)を、新しいコードが読めるか。キー名・形を変えたなら、移し替えか、古い形の読み方があるか
- 新しく足した項目に既定値があるか(古いデータに無い時に壊れないか)
- 消した項目を、まだ書き込んでいる・読んでいる所が無いか

### 条件分岐の影響

- 変更した条件が、**変更の目的ではない場合**の振る舞いを変えていないか(境界の値・0件・空・未設定・権限の無い人・古いデータ)
- 分岐を足した・まとめた時、元の分岐のどれかが通らなくなっていないか
- 例外・エラーの扱いを変えた時、呼び出し元がそれを前提にしていないか

### 画面の影響

- 変更した部品・CSS が、ほかの画面の見た目・配置を崩していないか(同じクラス・変数を使う所)
- 型・データの形の変更が、画面の表示と入力に反映されているか
- 画面の文言・URL・項目の並びを変えた時、それを前提にしているもの(ヘルプ・設計の文書・テスト・ブックマーク)が追従しているか

### テストの整合

- 既存のテストが、変更後も意図した場合を確かめているか(期待する値を、変更に合わせて書き換えただけになっていないか)
- 変更した振る舞いに対応するテストがあるか。**変えていない側の振る舞い**を守るテストがあるか
- テストを消した・飛ばしたなら、その理由が正しいか

## 出力

`review` スキルの出力の形で返す。指摘には、影響を受ける所を添える。

```
### 回帰のレビューの結果

**関数・API・部品の互換性**
- [ ] P1 `ファイル:行` — 指摘(影響を受ける所: `関連ファイル:行`)(改善案)

**見た範囲**: <変更したファイルと、grep で挙げた使っている所>
**問題の無かった観点**: ...
```

指摘が無い時: 「回帰のレビューで問題は見つかりませんでした」と書き、見た範囲と観点を残す。

直すところまで頼まれている時は、報告のあとに指摘の所を直す。
