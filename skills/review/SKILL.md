# レビュー

**見る範囲を先に数える → 観点ごとに当てる → 見つけたら同じ形を全部数える。**

一度で出し切れないと、同じ作業を何度も繰り返すことになる。繰り返す原因はいつも「**まだ開いていない場所が残っていた**」なので、範囲を先に決める。

## どのレビューを使うか

| 何をレビューするか | 読む手順 | 見るもの |
|---|---|---|
| 設計 | 設計のレビュー(`design/review/`) | 作業フォルダの設計の文書(詰め漏れ・成果物どうしの食い違い・書き方の決まり) |
| 実装 | 実装のレビュー(`review/impl/`) | **新しく入れた振る舞いと作り・安全・テスト**(設計との一致・正しさ・作り・セキュリティ・テスト・文書の更新・環境・コメントの書き方) |
| テストケース | テストケースのレビュー(`test-cases/review/`) | 作業フォルダの `cases/` のテストケース(漏れ・質・ゴール) |
| 性能とコード量 | 性能とコード量のレビュー(`review/perf/`) | **量・重さ・共通化**(コード量の削減・直書き・共通処理の再利用と切り出し・処理の軽量化・データの取り方) |
| 回帰 | 回帰のレビュー(`review/regression/`) | **変えていない側と、使っている所**(部品の互換性・保存されたデータ・目的でない場合の分岐・ほかの画面・既存のテスト) |
| 使い勝手 | 使い勝手のレビュー(`review/ux/`) | **利用者に見える形と言葉**(操作の手応え・エラーの伝え方・キーボード・見た目のそろい・狭い幅・アクセシビリティ・文言) |

観点どうしで重なりやすいものは、次の側で見る(もう片方には「→ 〜で見る」とだけ書く)。

- 依存の向き・層の分け方は実装。直書き(定数・パス・CSS の変数)は性能とコード量
- テストは、新しい振る舞いのものは実装、変えていない側を守るものは回帰
- 文書(README・`docs/`・ヘルプ・設計)の更新は実装
- 失敗の伝え方は、仕組み(握りつぶさない・呼び出し元へ返す)は実装、言葉とやり直せるかは使い勝手
- 名前・文言は使い勝手。実装は「設計と同じ名前か」だけを見る

## 当てるレビュー

- 「レビューして」とだけ言われたら、何が変わったか(作業フォルダの設計か、コードか、テストケースか)を見て選ぶ。迷ったらユーザーに聞く
- コードを変えた時は、実装のレビューに加えて、次を当てる(当てる条件は、ここだけで決める)

| 手順 | 当てる時 |
|---|---|
| 回帰のレビュー(`review/regression/`) | いつも |
| 性能とコード量のレビュー(`review/perf/`) | 処理・データの取り方・繰り返しを変えた時 |
| 使い勝手のレビュー(`review/ux/`) | 画面・文言・操作を変えた時 |

- 複数のレビューを当てる時は、それぞれを独立に行い(サブエージェントで並行してよい)、最後に1つの報告にまとめる。同じ指摘が重なったら1つにする

## 比べる先(コードのレビュー)

1. 呼び出し元(issue-handler など)が `<base>` を渡したら、それを使う
2. PR があれば、その base のブランチ: `gh pr view --json baseRefName --jq .baseRefName`
3. 無ければ、リポジトリの既定のブランチ: `gh repo view --json defaultBranchRef --jq .defaultBranchRef.name`
4. `git diff <base>...HEAD --stat` に、自分が変えていないファイルが大量に出る時は、比べる先が違う。プロジェクトの決まり(CLAUDE.md・リリースの手順など)で base を確かめ、分からなければユーザーに聞く

以下、この比べる先を `<base>` と書く。差分は `git diff <base>...HEAD`(まだコミットしていない変更も見るなら `git diff <base>`)で取る。

## 対象の特定(コードのレビュー)

どの観点でも、まずここまで読む。各観点の手順の「対象の特定」には、その観点で足すことだけを書く。

1. 比べる先 `<base>` を決める(上の「比べる先」)
2. 変更したファイルと差分を取る

```sh
git diff <base>...HEAD --name-only
git diff <base>...HEAD
```

3. 変更したファイルの**全体**を読む(差分だけでは前後の文脈が分からない)
4. 変更したものを**使っている所**を読む(呼び出し元、同じ部品・クラス・CSS のクラスを使う所。差分には出てこない)
5. プロジェクトの決まりを読む(CLAUDE.md・`.claude/rules/`・コーディングの決まり・リポジトリの `docs/`・既存のコード。下の「指摘の決まり」)

## 始める前に ── 見る範囲を数える

対象の特定で読んだもののほかに、見落としやすいもの。

| 見るもの | 見落とす理由 |
|---|---|
| テスト | 通っていても、その不具合を守れていないことがある |
| プロジェクトの決まりの中の例と前提 | 実装を変えると、決まりの例や前提が古くなる |
| 設計(作業フォルダの spec.md・acceptance.md など)とリポジトリの文書(README・`docs/`) | 画面の文言・手順・置き場所が実装とずれる |
| PR の本文 | 件数・受入確認が実装に追いつかない |
| 積んである他の PR・ブランチ | 同じ直しが他にも要ることがある |

**見た範囲を挙げられないうちは「他に無い」と言わない。** 言えるのは「どの範囲を見て、何が出なかったか」まで。

## 指摘の決まり

- **実際に効く指摘に絞る。** 観点を機械的に全部埋めない。「〜かもしれない」で出さず、読んで確かめる・動かす・測る・画面で見る。確かめきれないものは「推測」と書く
- **1件見つけたら、同じ形を全部数える。** 直す前に grep で横断する。1か所だけ直すと、同じ指摘が後からまた出る
- **その作業で自分が入れたものも対象にする。** 直前に書いたコードと文章が一番怪しい
- **プロジェクトの決まりを先に読む。** 観点に挙げた例(共通の部品、CSS の変数、命名など)は、そのプロジェクトで実際に何を使っているかを、CLAUDE.md と既存のコードから探して当てる
- 指摘には、**場所**(`ファイル:行` か、文書の節・項目の id)と**改善案**を付ける

### 重要度

| 重要度 | 意味 |
|---|---|
| P1 | 直さないと出せない。不具合・漏れ・壊れる・要件を満たさない・データや秘密が漏れる |
| P2 | 直した方がよい。分かりにくい・遅い・決まりから外れる・後で直しにくくなる |
| P3 | よりよくする。言葉の揺れ・好みの範囲 |

## 出力

どのレビューも、次の形で返す。観点の見出しの並びと、指摘に添えるものは、各手順の「出力」に書く。

```
### <レビューの名前>の結果

**<観点>**
- [ ] P1 `ファイル:行` — 指摘(改善案)
- [ ] P2 `ファイル:行` — 指摘(改善案)

**<観点>**
- [ ] ...

**見た範囲**: <見たファイル・文書・使っている所の範囲>
**問題の無かった観点**: <確かめて、問題が無かった観点>
```

- 観点の中は重要度の高い順に並べる。指摘の無い観点は、見出しごと省き、「問題の無かった観点」に挙げる
- すべて指摘が無い時は「<レビューの名前>で問題は見つかりませんでした」と書き、見た範囲と観点は残す(**「指摘なし」だけで終えない**)
- 複数のレビューをまとめる時は、レビューごとに上の形を並べ、先頭に全体の P1 の件数を書く(例: `P1: 2件(実装 1 / 回帰 1)`)

## 直すかどうか

- **単体で呼ばれた時は、報告だけ。** 直すかどうかはユーザーに確かめる
- 呼び出し元(イシュー対応の流れなど)や、ユーザーから直すところまで頼まれた時は、報告のあとに直す
  - **直したら、わざと壊して確かめる。** 元に戻してテストが落ちないなら、そのテストはその不具合を守っていない
  - 直さないと決めたものは、理由を添えて残す
- 設計の文書・テストケースのレビューは、指摘だけを返す(直すのはそれぞれの書き手のスキル)
